# 第 5 关 · ELF：游戏的地图压缩包

## 🎬 游戏开场

你下载了一款游戏，得到一个 `.exe`（Windows）或一个可执行文件（Linux）。双击它，游戏世界就展开了。

但那个文件本身，只是一堆躺在硬盘上的字节——它并不是游戏世界本身，而是一张**压缩的地图蓝图**。系统照着这张蓝图，在内存里把城市建起来。

Linux 上的这种"地图蓝图"格式叫 **ELF**（Executable and Linkable Format）。作为 Pwner，你必须会看这张蓝图——因为上面标着：

- 哪些区域放代码（不能写，只能读和执行）
- 哪些区域放数据（可读写）
- 游戏有哪些"传送门"可以借用（后面 ret2libc 的核心）

---

## 🧠 核心概念（游戏版）

### 1. ELF 文件 = 分层的地图

把 ELF 文件想成一个分层地图册，翻到不同页看到不同信息：

```
┌─────────────────────────────┐
│  ELF 头部                    │ ← 封面：这是什么游戏、几个关卡
├─────────────────────────────┤
│  程序头表（Program Headers）  │ ← 建造说明：怎么把蓝图变成城市
├─────────────────────────────┤
│  .text 段                    │ ← 代码区：所有指令（只读）
│  .rodata 段                  │ ← 只读数据：字符串常量等
│  .data / .bss 段             │ ← 数据区：全局变量（可读写）
├─────────────────────────────┤
│  .plt 段                     │ ← 传送门（后面讲）
│  .got 段                     │ ← 公告板（后面讲）
├─────────────────────────────┤
│  符号表 / 调试信息            │ ← 图例（可选，方便你读图）
└─────────────────────────────┘
```

**段（segment）和节（section）**：简单理解，"段"是给系统看的安装说明，"节"是给你看的分类标签。同一块内容可能既属于某段又属于某节。新手先不纠结区别。

### 2. 程序加载：蓝图变城市

你双击程序时，系统做了这些事：

1. 读 ELF 头部，确认"这是个合法游戏"。
2. 按程序头表，把各个段**映射**到内存的不同区域：
   - `.text` → 代码区（标记为**可读可执行，不可写**）
   - `.data`/`.bss` → 数据区（**可读可写**）
   - 栈、堆 → 运行时动态生成
3. 找到入口点（`entry point`），把 `rip` 指过去，游戏开始。

> 🎮 **关键规则**：代码区不可写！这是保护机制 NX 的基础。你不能直接往代码区塞自己的指令（第 6 关讲）。但数据区可写——如果能让它"被执行"就有戏，这是后话。

### 3. 主角登场：PLT 与 GOT

这是本关的重头戏，因为第 10 关 ret2libc 全靠它。

游戏里的函数分两种：

- **自己写的函数**（如 `add`）：位置固定在 `.text`，直接跳过去。
- **外部库函数**（如 `printf`、`puts`）：位置不固定！它在系统库（libc）里，而 libc 每次加载的位置可能变。

怎么调用一个"位置不固定"的函数？游戏用了两件套：

```
你的代码            PLT（传送门）           GOT（公告板）        libc（真正技能库）
  |                    |                      |                  |
  |-- call puts@plt -->|                      |                  |
  |                    |-- 查 puts 的公告板 -->|                  |
  |                    |   如果还没查过...    |                  |
  |                    |-- 让系统找 puts 的位置 ----------------->|
  |                    |   把位置写回公告板 --->|                  |
  |                    |-- 按公告板上的位置跳 -------------------->|
  |                    |                      |            执行 puts
```

- **PLT（Procedure Linkage Table，过程链接表）**：一段 small 的"传送门"代码。你的程序调用外部函数时，实际是 `call puts@plt`。
- **GOT（Global Offset Table，全局偏移表）**：一块**可写的**公告板，记录每个外部函数"真正的地址"。

**这两点为什么对 PWN 至关重要？**

1. **GOT 可写**：如果能改写 GOT 表项（比如把 `puts` 的地址改成 `system` 的地址），那么程序一调用 `puts`，实际执行的就是 `system`——这叫 **GOT 表劫持**。
2. **GOT 可泄露**：GOT 里存着 libc 函数的真实地址。把它打印出来，就能算出 libc 的"基地"在哪——这是 **ret2libc 泄露 libc 基址** 的原理。

记住：**GOT 是游戏里那块可写的公告板，上面写着所有外援的真实坐标。**

### 4. 静态 vs 动态

- **静态链接**：把所有外部代码都打包进游戏（文件大，但自给自足）。
- **动态链接**：只留传送门（PLT/GOT），运行时去系统库找（文件小，但依赖环境）。

CTF 题目几乎都是动态链接，所以 GOT/PLT 天天见。

## 🔧 真实世界对照

| 游戏说法 | 真实术语 |
| --- | --- |
| 地图蓝图 | ELF 文件 |
| 建造说明 | 程序头表（Program Header Table） |
| 代码区 | `.text` 段（rx） |
| 数据区 | `.data` / `.bss` 段（rw） |
| 传送门 | PLT |
| 公告板 | GOT |
| 系统技能库 | 共享库（libc.so） |
| 游戏入口 | entry point |

常用查看命令：

```bash
readelf -h hello          # 看封面（ELF头）
readelf -l hello          # 看建造说明（程序头/段）
readelf -S hello          # 看所有节
objdump -d hello          # 反汇编代码
checksec --file=hello     # 看开了哪些保护（下一关）
nm hello                  # 看符号表
```

## 🎯 闯关任务：找到传送门和公告板

用第 1 关编译的 `hello` 程序：

```bash
readelf -S hello | grep -E "plt|got"
```

你会看到 `.plt`、`.plt.sec`、`.got`、`.got.plt` 等节。它们就是传送门和公告板。

再看动态符号：

```bash
objdump -R hello
```

你会看到程序要用哪些外部函数（如 `puts@GLIBC_2.2.5`、`gets@GLIBC_2.2.5`）。这些名字后面的 `@GLIBC_版本`，就是游戏要求的"库版本"。

思考题：如果我把 GOT 表里 `puts` 的地址改成 `system`，下次程序打印 "hello" 时会发生什么？（提示：它实际上会执行 `system("hello")`——如果 "hello" 恰好是 `/bin/sh` 该多好。第 10 关揭晓。）

## 📌 本关小结

| 你学会了 | 一句话记忆 |
| --- | --- |
| ELF | 程序的地图蓝图，系统照它建城市 |
| 段/节 | 分类存放代码、数据等信息 |
| 代码区只读 | NX 保护的基础 |
| PLT | 传送门，调用外部函数的跳板 |
| GOT | 可写的公告板，记录函数真实地址 |

**核心伏笔**：GOT 表可写、可泄露——第 10 关 ret2libc 的两大支柱。看到 `printf@plt` 要条件反射想到"它背后有张公告板"。

**第 6 关 · 保护机制：游戏的难度旋钮**

同一个 BUG，为什么在朋友的电脑上能打通，到你就失败？因为游戏有**难度设置**。

- **Canary**：餐桌上的警报器
- **NX**：禁止在数据区跑代码
- **ASLR/PIE**：每次开局重新洗牌地图
- **RELRO**：用胶水把公告板固定住
