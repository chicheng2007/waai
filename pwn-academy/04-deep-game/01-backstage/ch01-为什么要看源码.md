# 第 1 关 · 走进游戏后台：为什么同一招在新版本失灵了

## 🎬 游戏开场

你带着基础篇学会的招式去打新题,却发现:

- 以前一招 `free(a); free(a)` 就能 double free,现在程序直接报错退出。
- 以前改 chunk 的 fd 指针直接写目标地址就行,现在写进去的值完全不对。
- 以前 House of Force 百试百灵,现在 malloc 直接拒绝。

你以为是自己的招式退步了?不。是**游戏后台升级了**。

基础篇我们一直站在"玩家视角"——看到 Bug,利用 Bug。但有个根本问题没回答:

> **这些 Bug 到底为什么存在?后台的管理规则是什么?规则变了,我怎么知道?**

这一季,我们切换到**后台视角**:去看游戏的源代码(glibc 的堆管理器源码),理解每一条规则、每一个检查。只有这样,你才能在新版本出来时,自己推导出新招式,而不是死记硬背旧 exp。

---

## 🧠 核心概念(游戏版)

### 1. 什么是 glibc?

你调用的 `malloc`、`free`、`printf`,都不是你自己写的——它们来自一个叫 **glibc** 的"官方标准库"。它就像游戏的**底层引擎**,所有人都用它。

引擎的版本一直在更新:

| glibc版本 | 大约年份 | 重要变化 |
| --- | --- | --- |
| 2.23 | 2016 | 老版本,检查少,招式简单 |
| 2.27 | 2018 | tcache 成熟 |
| 2.29 | 2019 | tcache 加入 key(防double free) |
| 2.31 | 2020 | 主流版本 |
| 2.32 | 2020 | safe-linking(指针打码) |
| 2.35 | 2022 | 现代主流,House of Apple 时代 |

**同一个 Bug,在不同版本里表现完全不同**——因为引擎规则变了。

### 2. 为什么要读源码?

游戏比喻:

- **玩家视角**(基础篇):我知道按这个顺序操作能卡出 BUG。
- **后台视角**(进阶篇):我看了游戏代码,知道这个 BUG 是因为第 3721 行的检查写漏了。

知道第 3721 行写漏了有什么好处?

1. **能自己找新招**:规则变了,你看新代码,立刻知道旧招哪里被堵、哪里还有洞。
2. **能精准绕过检查**:不是瞎试,而是看着检查逻辑,构造刚好通过检查的输入。
3. **能理解"为什么"**:不再死记"要改这个指针",而是懂"为什么要改它、改了之后系统会怎样"。

### 3. 我们的学习方法

读源码很容易劝退——glibc 的 malloc.c 有几千行。我们的策略是:

> **只看关键几十行,每一行用游戏语言翻译。**

比如 `malloc` 的核心逻辑,我们只关心它"先看哪个筐、怎么取 chunk",不关心内存对齐的细枝末节。每关我们提炼出一个"后台流程图",让你建立直觉,而不是淹没在代码里。

### 4. 本节要建立的后台模型

接下来的 5 关,我们依次看:

- **malloc 源码**:租赁系统接单的逻辑(第 2 关)
- **free 源码**:退租的完整流程(第 3 关)
- **tcache 源码**:快速筐的盖章与打码(第 4 关)
- **bins 源码**:回收站的链表维护(第 5 关)
- **检查机制年表**:反作弊升级史(第 5 关)

**怎么读源码?** 推荐在线看 glibc 源码:

```
https://sourceware.org/git/?p=glibc.git
搜索 malloc/malloc.c,_int_malloc 和 _int_free 函数
```

或用 GitHub 的 mirror,选对应 tag(如 glibc-2.35)。


记下你的版本号。后面所有关卡的源码细节都以版本为背景。如果题目给了 libc 文件,用 `strings libc.so.6 | grep "GNU C Library"` 看版本。
