# 第 12 关 · vtable：技能表与反作弊的军备竞赛

## 🎬 游戏开场

FILE 攻击的核心矛盾,全在"技能表"(vtable)上:

- **攻击者想**:把 vtable 指向我伪造的表,里面放 system,这样刷卡时就执行 system。
- **防御者想**:绝不能让你伪造技能表!

于是两边展开了漫长的军备竞赛。这一关,我们把这段演化史讲清楚——你会明白 House of Apple 为什么长成现在这个"怪样子"。

---

## 🧠 核心概念（游戏版）

### 1. vtable 检查的三次升级

**时代一:无检查(glibc < 2.24)**

攻击者可以随便伪造 FILE 和 vtable,指向堆上的假表 → 直接劫持。简单粗暴。

游戏翻译:游戏不查技能表真假,你画一张假的就能用。

**时代二:vtable 必须在合法区域(glibc 2.24+)**

glibc 加了检查:调用前验证 vtable 指针必须落在 `__libc_IO_vtables` 这段只读区域内。伪造在堆上的表被拒绝。

游戏翻译:游戏开始检查"技能表必须是官方印制的",你手画的假表作废。

**时代三:连 vtable 表项都检查(glibc 2.27+)**

进一步检查 vtable 的**具体函数指针**必须是合法的 IO 函数。攻击难度陡增。

游戏翻译:不只查表是不是官方的,还查表上每个按钮是不是官方按钮。

### 2. 攻击者的反击:合法偏移

面对"必须用官方表",攻击者想出绝招:

> **我不伪造表,我把 vtable 指针指向官方表的中间某个位置**(加一个 offset)。这样检查能通过(指针在合法区域),但被调用的函数变成了表中间的另一个函数。

比如 `_IO_wfile_jumps` 表里,某个偏移处是一个能利用 `_wide_data` 字段的函数。攻击者把 vtable 设成 `_IO_wfile_jumps + offset`,再精心构造 `_wide_data`,就能在一次合法的 vtable 调用中劫持控制流。

游戏翻译:我用官方技能表,但我把指针指向"表的中间某个按钮"——检查通过(是官方表),但这个按钮会去读我写好的"备注栏"(_wide_data),按我的意思办事。这就是 House of Apple 的精髓。

### 3. 为什么这个检查能被绕过?

因为 glibc 的检查只验证"vtable 指针在 `__libc_IO_vtables` 范围内",但**不验证 vtable 指针对齐到表的开头**。所以 `合法表 + offset` 仍在范围内,能通过检查。

这是设计上的疏忽,成了现代 IO 利用的基础。

游戏翻译:检查只问"这张表是不是官方的",没问"你指的是不是表的开头"——攻击者就钻这个空子,指向表中间。

### 4. 演化脉络总结

```
无检查 → 随便伪造vtable
  ↓ 加检查:必须在合法区
指向合法表的偏移 → 绕过区域检查
  ↓ 加检查:表项也要合法
利用合法表项 + 构造wide_data → House of Apple
```

回答:为什么把 vtable 设成 `_IO_wfile_jumps + 0x30` 能通过 glibc 的检查?

> 答:因为检查只验证指针落在 `__libc_IO_vtables` 区域内,`_IO_wfile_jumps + 0x30` 仍在这个区域内,所以通过;但它对应的函数变成了另一个可被利用的函数。
