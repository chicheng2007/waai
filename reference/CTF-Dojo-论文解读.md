## 执行摘要

这篇论文讨论的问题是：**如何训练一个能自主发现并利用漏洞的 AI Agent**。作者给出的答案不是继续扩大合成数据规模，而是反过来——先搭出一套可执行、可验证的环境，再从模型真实解题的多轮交互中收集成功轨迹作为训练数据。

整套流程可以拆成四步：

1. **环境构建**：把 pwn.college 归档里的 658 道 CTF 题目，通过自动流水线 CTF-Forge 转成 Docker 容器，让每道题都能被反复执行。650 道题（98%）连续三次通过构建与端口检查。
2. **轨迹采集**：让 Qwen3-Coder 和 DeepSeek-V3-0324 两个教师模型在这些环境里解题，用 flag 是否正确作为天然的验证信号，共得到 1,006 条成功轨迹，覆盖 274 道题。
3. **数据清洗**：限制轨迹长度、每题最多保留两条，最终得到 486 条 SFT 训练数据。
4. **监督微调**：用这 486 条轨迹对 Qwen3-8B/14B/32B 做 SFT，三个模型的平均 Pass@1 分别提升 4.7、7.1、11.6 个百分点，32B 最终达到 31.9%。

最值得注意的对比是：**Cyber-Zero 用了 9,464 条合成轨迹，8B/14B/32B 的平均成绩为 23.2%/29.1%/33.4%；CTF-Dojo 只用 486 条轨迹，就达到 18.9%/25.7%/31.9%**——样本量少 94.9%，32B 仅落后 1.5 个百分点。这说明在 Agent 训练里，**经过执行验证的高质量轨迹，比海量的弱标注数据更有效**。

> 整理者观点：这篇论文真正的方法论贡献，是把"数据构建"从"生成更多文本"转向"构建可验证的交互过程"。flag 作为二值验证信号，把主观的"解题质量"变成了客观的"对/错"，这是整个方法能成立的地基。

## 一、引言：安全 Agent 训练缺的是什么

论文标题叫 *Training Language Model Agents to Find Vulnerabilities*（训练能发现漏洞的语言模型 Agent），但它的出发点其实是一个很具体的工程痛点：**安全 Agent 的训练，缺的不只是题目，还包括能反复执行的环境、完整的交互过程，以及明确的结果验证。**

想象一次真实的 CTF 解题：模型要先读题目描述、检查附件、判断程序类型（是加密脚本、二进制程序还是 Web 服务），再选择工具、执行命令，根据报错不断调整策略，最后提交 flag。这中间产生的材料——包括最终的 flag，也包括每一步的推理（reasoning）、工具调用（tool call）、环境返回的报错与输出——合起来就是一条**轨迹（trajectory）**。真正有价值的训练数据，正是这一整段"从困惑到解出"的过程，而不只是最后那个 flag 字符串。

CTF 有一个天然优势：**flag 是否正确是一个完美的验证信号**——模型要么解对，要么解错，没有模糊地带。但公开的 CTF 材料通常只有题目描述、附件和零散的部署文件，无法直接用于大规模 rollout（批量试错）。依赖版本、服务端口、flag 注入方式、检查脚本，这些都需要先恢复出来。换句话说，**公开题目是"静态的"，而训练需要"动态的、可执行的"环境**。

论文围绕这个缺口构建了两部分：

- **CTF-Dojo**：658 个容器化的可执行 CTF 环境。
- **CTF-Forge**：把公开题目材料自动转换成 Docker 环境和任务元数据的流水线。

有了环境，模型才能反复尝试；有了 flag，成功轨迹才能被自动筛出来。这是后面一切工作的前提。

## 二、CTF-Dojo：把公开题目变成可执行环境

### 2.1 为什么选 pwn.college

作者比较了多个公开题库来源：Sajjadium CTF Archives、r3kapig Notion、CryptoHack、archive.ooo 和 pwn.college CTF Archive。最终选择 pwn.college，原因不是题目数量最多，而是**它的材料结构相对统一，并且保留了复现题目所需的说明**（比如 `REHOST.md`、`.init` 这类重新部署的线索）。其他来源要么维护不一致、格式差异大，要么只覆盖单一类别。

作者手动移除了 3 道与评测集重叠的题目，最终得到 **658 道训练题**，时间跨度 2011–2025 年，来自 50 场比赛，分布在六类题型中：

| 类别 | Crypto | Forensics | Pwn | Reverse | Web | Misc | 合计 |
|---|---|---|---|---|---|---|---|
| 题目数 | 228 | 38 | 163 | 123 | 21 | 85 | 658 |

可以看到，**Crypto、Pwn、Reverse 三类占了绝大多数（514 道，约 78%），Web 只有 21 道**。这个分布会直接影响后续训练覆盖了——模型学到的主要是密码学、二进制利用和逆向工程任务，而不是对真实安全场景的均衡覆盖。这一点在第七章的评测结果里会有直接体现。

### 2.2 两类 flag 机制

题目使用两类 flag：

- **预定义 flag**：系统保存其 SHA-256 哈希或检查脚本，模型提交后做比对。
- **动态 flag**：在容器运行时生成，写入 `/flag` 等位置。

第二类尤其重要，因为它**要求模型真正与环境交互**——flag 不在题目描述里，也不在附件里，必须真的连上服务、利用漏洞、读取运行时生成的文件才能拿到。这杜绝了模型靠"记住固定答案"来蒙混过关的可能。

## 三、CTF-Forge：自动生成运行配置

### 3.1 生成哪些文件

CTF-Forge 读取题目描述、附件和 rehost 信息，由 DeepSeek-V3-0324 分阶段生成三个文件：

```text
Dockerfile          # 选基础镜像、装依赖、复制文件、配置服务
docker-compose.yml  # 组织容器、端口、网络
challenge.json      # 题目元数据：描述、文件、容器、端口、flag 验证方式、类别
```

不同题型需要完全不同的运行方式：Web 题可能要 Apache、Nginx 或 Python/Node.js 服务；Pwn 题通常需要对应架构的二进制、动态库和 `socat`；Crypto 题可能提供交互式脚本；Reverse 和 Forensics 更多是离线文件分析。CTF-Forge 会**先判断是否需要远程服务，再选择对应的 Docker 配置**。

需要强调的是，LLM 在这里只负责把已有材料"翻译"成统一的运行配置，**题目本身和漏洞机制仍然来自公开 CTF 材料**，模型并不发明新题。

### 3.2 生成 Dockerfile 时模型看到了什么

根据论文附录 H，生成 Dockerfile 的 Prompt 输入包括：题目名称、类别、可用文件清单、文件分析、题目描述、`REHOST.md` 和 `.init`。其中 `REHOST.md` 提供重新部署的线索，`.init` 可能包含初始化命令、依赖、路径和运行配置。CTF-Forge 把这些信息与题型规则一起放进 Prompt，让模型恢复题目原来的运行条件。

论文给了两个很具体的例子，能看出这项工作的"手艺"成分：

- **Pwn 题**：32 位程序跑在 64 位系统上时，要安装对应的 32 位依赖；交互式程序通过 `run.sh` 和 `socat` 暴露成网络服务，并用 `stdbuf` 减少输入输出缓冲。**一个二进制直接执行后没输出，不一定是程序坏了，也可能是在等网络侧输入**——所以要通过连接服务来检查行为。
- **Python 服务**：要区分"每次连接启动一个交互程序"和"先启动持续监听的服务器"两种情况。后一种情况下，Prompt 要求先在后台启动 Python 服务，再用 `socat` 转发到内部端口，避免每次连接都重启服务器。

### 3.3 验证材料如何与玩家材料隔离

这是设计上很关键的一点：Dockerfile 的 Prompt **明确禁止**复制 `flag.sha256`、flag checker 和可用文件清单之外的文件。`challenge.json` 里的 `files` 字段描述玩家能拿到的附件，`compose` 表示是否需要服务，`flag` 只用于任务验证。题目描述面向玩家，不应暴露 checker 信息。

Docker Compose 则根据已生成的 Dockerfile 提取端口，把服务接入 `ctfnet` 网络，并生成题目对应的 DNS alias。这样一来，**Agent 看到的只有附件和可连接的题目服务，验证材料留在任务管理侧**。当然，这些是 Prompt 层面的约束，实际环境是否真的满足条件，还要靠运行检查来兜底。

### 3.4 环境真的能跑起来吗

生成配置后，作者对 658 道题**独立运行三次构建**，每次检查两件事：镜像能否成功构建并启动；容器中的服务能否在预期端口响应。结果是 **650 道题三次全部通过，占 98%**。作者又抽取 10% 的任务，手动测试环境中的可执行文件。

效率方面，CTF-Forge 平均用 **0.5 秒**生成一个容器配置，而人工处理一道题可能需要约一小时。不过要注意，0.5 秒只算配置生成时间；98% 这个数字来自三次构建、启动和端口检查的完整流程。

## 四、从环境到训练轨迹：EnIGMA+ 与轨迹采集

### 4.1 EnIGMA+：管理多轮解题

有了环境，还需要一个框架来驱动模型与环境交互。**EnIGMA+** 负责管理这个多轮过程：模型通过 Bash 操作隔离容器，框架记录每一步的命令、输出和推理，直到拿到 flag 或达到 **40 轮**上限。

相比原始版 EnIGMA，EnIGMA+ 做了三点改进：可以并行执行不同容器；用固定的交互轮数替代 API 成本限制；使用更轻量的 summarizer（摘要器），避免二进制反编译之类的超长输出快速填满上下文。

除了通用的 Bash，附录 G 还列出了几类专用工具：

| 工具 | 用途 |
|---|---|
| `decompile` / `disassemble` | 静态分析（反编译 / 反汇编） |
| `debug_start` + 断点、单步命令 | 管理调试会话 |
| `connect_start` / `connect_sendline` | 管理远程交互 |
| `submit` | 提交 flag，正确时结束任务 |

框架把这些接口提供给模型，但**不保证每条轨迹都会用到专用工具**——模型完全可以选择纯 Bash 路线。

### 4.2 教师模型与采样设置

轨迹由 **Qwen3-Coder** 和 **DeepSeek-V3-0324** 两个教师模型生成。DeepSeek-V3-0324 的采样参数是 temperature 0.6、top-p 0.95，每道题 rollout 6 次；两个教师合计为每道题提供 **12 次尝试**。

但直接采样遇到两个问题：**不少题目一次也解不出**（弱模型找不到路径），**少数简单题却产生了多条成功轨迹**（数据会集中在有限任务上）。作者为此加入了两种增强手段：writeup 提示和运行时增强。

### 4.3 Writeup：提高教师成功率

作者从 CTFtime 收集了 **8,361 篇 writeup**（解题报告），通过比赛和题目元数据做模糊匹配，得到 **252 篇匹配材料，覆盖 150 道题**，约占 CTF-Dojo 的 23%。处理流程非常严谨：

1. 删除 writeup 中可能出现的 flag；
2. 由两位作者检查匹配关系和 flag 泄漏；
3. 把一篇匹配 writeup 放进 Prompt，要求模型**只把它当作解题思路**；
4. 轨迹采集完成后，**移除 writeup 内容**；
5. 随机抽查 20% 的轨迹，确认推理过程没有复述或改写提示文本。

最终 SFT 数据里**不保留 writeup 文本**，保留的只是教师在提示帮助下得到的执行过程。简单说，writeup 的作用是"提高成功轨迹的产出率"，而不是"给模型抄答案"。

### 4.4 Runtime augmentation：改变环境表面特征

另一种增强手段是在每次 rollout 时改变环境的表面特征：

- 随机端口；
- 调整文件路径；
- 注入不影响功能的干扰代码；
- 修改时间戳、已安装软件等系统元数据；
- 对动态 flag 重新设置随机种子。

**核心漏洞和解题条件不变**，变的是端口、路径、flag 和干扰代码。这样做有两个好处：一是减少模型对固定环境线索（比如"flag 永远在 /flag"）的依赖；二是能通过重新生成配置，避开部分持续性的构建错误。

## 五、从 1,006 到 486：数据筛选逻辑

两类教师共得到 **1,006 条原始成功轨迹，覆盖 274 道题**。但这些数据不能直接拿去训练，作者做了两层筛选：

1. **长度过滤**：只保留不超过 32,768 tokens 的样本；
2. **单题采样上限**：每道题最多保留 2 条轨迹，避免少数简单题在训练数据里出现太多次。

最终得到 **486 条训练数据**。把几个关键数字串起来：

```text
658 道题 → 650 道环境稳定 → 教师解出 274 道
        → 1,006 条成功轨迹 → 筛选后 486 条训练数据
```

其中 650 是"稳定环境数"，274 是"已解题目数"，486 是"最终轨迹数"——三者含义不同，不能混用。

论文附录 B 的图显示：**多数成功轨迹包含 5–15 轮交互，长尾达到 40 轮**；很多题目在 12 次 rollout 里只成功一次。这正是"每题最多保留两条"这条规则的用武之地——它保证了训练数据不会过度集中在容易题上。

> 整理者观点：486 这个数字看似很小，但它是"净成功"数据——每一条都经过 flag 验证、都排除了 writeup 泄漏、都做了长度和重复控制。这种"少而精"数据集的价值，正在被越来越多 Agent 训练工作验证。

## 六、Agent SFT：训练方法

训练采用的是 **rejection sampling fine-tuning（拒绝采样微调）**：教师在环境里多次尝试，只接收成功拿到 flag 的轨迹，再用这些轨迹对学生模型做 SFT。

学生模型是 **Qwen3 的 8B、14B 和 32B 三个版本**，三组训练用完全相同的配置：

| 配置项 | 取值 |
|---|---|
| 训练框架 | NVIDIA NeMo |
| 硬件 | A100 GPU |
| global batch size | 16 |
| 学习率 | 5 × 10⁻⁶ |
| epoch | 2 |
| 训练数据 | 486 条轨迹 |

**flag 在这里只用来筛选轨迹，没有作为强化学习（RL）的 reward**。最终优化目标仍然是标准的 SFT loss。

需要指出，论文披露了训练框架、样本长度和这些超参数，但**没有展开**诸如"不同角色的 token 是否参与 loss 计算""轨迹如何归一化"这类细节。所以这份工作没法像某些开源项目那样，还原出完整的 token 级训练配方——这也是复现时需要注意的空白处。

## 七、实验结果

### 7.1 三种规模都提升

评估同样用 EnIGMA+：模型操作 Linux Bash 终端，每个 rollout 最多 40 轮，由 Simple Summarizer 控制长输出。三个测试集是：

- **InterCode-CTF**：论文实际用 91 道题，主要来自 picoCTF，难度偏高中级；
- **NYU CTF Bench**：实际用 192 道题，来自 CSAW 2017–2023，难度偏大学级；
- **Cybench**：40 道题，来自 HackTheBox、Sekai CTF、Glacier 和 HKCert，难度更接近专业比赛。

每道题采样三次 rollout，指标是 Pass@1。下表的 Average 是三个 benchmark 的算术平均，不按题目数量加权。

| 模型 | InterCode-CTF | NYU CTF | Cybench | 三项平均 |
|---|---|---|---|---|
| Qwen3-8B | 46.5 | 0.8 | 5.0 | 14.2 |
| CTF-Dojo-8B | 53.8 | 4.2 | 10.0 | 18.9 |
| Qwen3-14B | 55.0 | 2.6 | 12.5 | 18.6 |
| CTF-Dojo-14B | 71.4 | 5.7 | 17.5 | 25.7 |
| Qwen3-32B | 60.0 | 4.7 | 5.0 | 20.3 |
| CTF-Dojo-32B | 83.5 | 10.4 | 17.5 | 31.9 |

相对各自基座，8B、14B、32B 的平均 Pass@1 分别提升 **4.7、7.1、11.6 个百分点**——**模型越大，增益越大**。32B 在 InterCode-CTF 上单集提升 23.5 个百分点（60.0 → 83.5），在 NYU CTF 上提升 5.7，在 Cybench 上提升 12.5。CTF-Dojo 数据向 InterCode-CTF 的迁移最明显，这与两者题目来源接近（都含大量 picoCTF 类题目）不无关系。

### 7.2 数据规模曲线

论文 Figure 3 显示，三种模型都随训练轨迹数量增加而提升：32B 从零轨迹时的 20.3% 逐步升到 31.9%。在 0–486 条轨迹范围内，三条曲线**近似线性上升**，且模型越大，加入相同数量轨迹后的提升越明显。这意味着在 486 这个量级上，数据还没出现饱和——如果继续扩充经过验证的轨迹，可能还有提升空间。

## 八、哪些设计真正提高了轨迹产出

论文做了几组消融，回答"到底是哪一步在起作用"。

### 8.1 Writeup 对弱模型更有效

加入 writeup 后，六个教师模型的解题率全部上升：

| 模型 | 无提示 | 有提示 | 提升 |
|---|---|---|---|
| Claude-3.7-Sonnet | 36.2 | 46.4 | +10.2 |
| Claude-3.5-Sonnet | 33.0 | 39.7 | +6.7 |
| DeepSeek-V3-0324 | 30.4 | 33.9 | +3.5 |
| Qwen3-Coder | 23.9 | 32.5 | +8.6 |
| Qwen3-32B | 17.2 | 24.3 | +7.1 |
| Qwen3-14B | 12.9 | 21.1 | +8.2 |

Crypto、Reverse 和 Misc 的提升更明显——这些任务经常依赖特定工具链或常见解题路径，writeup 能让教师更快进入有效探索方向。平均解出的题目数从 168 增加到 217（多 49 道）。按 168 计算是 29.2% 的相对提升；原文给出的 7.4% 对应的是 49/658（占总题数的比例），两种算法口径不同，引用时需注意。

### 8.2 随机化环境带来更多成功任务

论文 Figure 4 对比了静态环境与增强环境（实线为增强，虚线为静态）。在 4 次 rollout 下：

- Qwen3-Coder：从静态环境的 169 题解出，提升到增强环境的 211 题，相对提升约 24.9%；
- DeepSeek-V3-0324：从 156 题提升到 217 题，约提升 39.1%。

随着 rollout 数增加，增强环境与静态环境的差距还会扩大。原因很直观：**固定环境里的失败会在多次采样间重复**，而端口、路径、flag 的变化为 Agent 提供了不同的执行条件，相当于增加了"重试"的多样性。注意，这里统计的是采集阶段"至少成功一次"的题目数，对应训练数据覆盖，不是学生模型的 benchmark 分数。

### 8.3 两个教师覆盖不同任务

Qwen3-Coder 和 DeepSeek-V3-0324 共同解出 181 道题，各自另有 44 道和 49 道独有任务，合并后覆盖 274 道。只用单一教师或合并两者训练，效果差异明显：

| 教师数据 | 32B 平均 Pass@1 | 8B 平均 Pass@1 |
|---|---|---|
| 仅 Qwen3-Coder | 29.4 | 17.3 |
| 仅 DeepSeek | 31.3 | 17.6 |
| 两者合并 | 31.9 | 18.9 |

可见合并数据的主要作用是**扩大任务覆盖**，而不是给同一道题堆更多相似轨迹。

## 九、讨论、局限与启示

### 9.1 "发现漏洞" vs "做 CTF 题"

论文标题用了 "Find Vulnerabilities"，但实验任务其实是**容器化的 CTF**：模型根据题目描述和附件，在 40 轮内拿到 flag。任务确实包含漏洞识别、利用和工具使用，但**并没有测试在大型真实代码库中发现未知漏洞的能力**。CTF-Dojo 提供的是一组可重复执行、结果可验证的安全任务，适合训练探索、调试和利用的流程，也让不同数据构建方法能在同一基准上比较——但把它等同于"自动挖漏洞"是过度解读。

### 9.2 三种验证要分清

论文里有三种不同的"检查"，容易被混淆：

1. **环境可用性检查**：构建、启动、端口响应，650/658 道题连续三次通过；
2. **任务完成检查**：flag 是否正确，最终接收 486 条成功轨迹；
3. **去重检查**：训练集与 benchmark 是否直接重叠，作者手动移除了 3 道题。

其中第三项只处理了当前训练集与测试集的**直接重叠**，**没有测量基础模型在预训练阶段是否见过这些公开题目**。CTF 题目和 writeup 都是公开材料，数据污染（data contamination）的风险无法完全排除。不过 writeup 在轨迹落盘前已被移除，并对 20% 样本做了人工复查，这部分控制是到位的。

### 9.3 对后来者的启示

> 整理者总结三点可迁移的经验：

1. **验证信号优先于数据规模**。在设计 Agent 训练数据时，先问"我能不能自动判断这条轨迹成功了吗"。有干净的二值验证信号（如 flag、单元测试、编译通过），就不怕数据少。
2. **环境也是数据的一部分**。可重复执行、可随机化的环境，能让有限的题目产出远多于其数量的训练样本。runtime augmentation 本质上是给"重试"增加多样性。
3. **教师互补优于单题堆叠**。多个教师带来的不同解题风格和任务覆盖，比在同一道题上反复采样更有价值。

## 十、总结

CTF-Dojo 做了一件朴素但扎实的事：把 658 道公开题目变成可执行环境（CTF-Forge 生成 Dockerfile / compose / challenge.json），再用两个教师模型在环境里解题，配合 writeup 提示和环境随机化，从 1,006 条成功轨迹中筛出 486 条训练数据。三个 Qwen3 模型经 SFT 后平均 Pass@1 分别提升 4.7、7.1、11.6 个百分点，32B 最终达到 31.9%，用 486 条数据就接近了 Cyber-Zero 用 9,464 条数据的效果。

这项工作最重要的信息是：**Agent 训练数据不一定要先堆到几万条。先把环境、执行过程和结果验证做好，少量但可验证的成功轨迹，也足以明显改变模型的行为。** 在"数据即算力"的叙事之外，它提醒我们：数据的**质量维度**——可执行、可验证、有过程——可能比数量更值得投入。

当然，从 CTF 到真实漏洞发现还有距离，预训练数据污染的风险也在。但作为一份方法论示范，CTF-Dojo 把"如何把公开材料变成高质量 Agent 训练数据"这条路，走得相当清楚。
