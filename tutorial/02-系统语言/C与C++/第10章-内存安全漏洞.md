# 第 10 章 内存安全漏洞：栈溢出、堆溢出、UAF

## 本章目标

- 深入理解栈溢出漏洞的原理和利用思路
- 理解堆溢出、Use-After-Free、Double Free
- 理解格式化字符串漏洞
- 理解现代防护机制（Canary、NX、ASLR）

**这是 C/C++ 安全部分的核心章节。** 前面学的指针、内存布局、数组越界，在这里汇合。理解这些，你就理解了绝大多数二进制漏洞的本质。

## 10.1 栈溢出漏洞深入

### 10.1.1 漏洞原理回顾

```c
#include <string.h>

void vuln(char *input) {
    char buf[64];
    strcpy(buf, input);   // 无长度检查 → 溢出
}

int main(int argc, char **argv) {
    vuln(argv[1]);
    return 0;
}
```

栈帧布局：

```
高地址
[ 调用者的栈帧 ]
[ 返回地址        ] ← 溢出目标
[ 保存的寄存器    ]
[ buf[64] 缓冲区  ] ← 从这里开始溢出
低地址
```

当输入超过 64 字节，溢出的数据会覆盖返回地址。函数返回时，`ret` 指令会跳到攻击者覆盖的地址。

### 10.1.2 攻击思路（概念层面）

攻击者构造输入：

```
[ 64字节填充 ][ 覆盖的返回地址 ]
```

- 前 64 字节：填满 buf
- 接下来的 8 字节：精心构造的返回地址（指向恶意代码或某个函数）

这叫 **ret2text**（返回到程序已有的代码）或 **ret2shellcode**（返回到注入的 shellcode）。

> **CTF 场景**：这是 PWN 题的基础。学习需要配合 dtypes、gdb、pwntools 等工具，在专门的靶场练习。

### 10.1.3 ROP（返回导向编程）

现代系统开启了 NX（栈不可执行），shellcode 放栈上没法直接执行。攻击者改用 **ROP**：

- 不注入新代码，而是复用程序里已有的代码片段（gadget）
- 每个 gadget 以 `ret` 结尾
- 把多个 gadget 地址串起来，形成攻击链

这体现了攻防的持续对抗。

## 10.2 堆漏洞

### 10.2.1 堆溢出

```c
#include <stdlib.h>
#include <string.h>

void heap_overflow() {
    char *buf = malloc(16);      // 堆上分配 16 字节
    strcpy(buf, "超长字符串超长字符串超长字符串...");  // 溢出！
    free(buf);
}
```

堆溢出会破坏堆管理器的元数据（chunk header），可能导致：

- 任意地址写入
- 覆盖相邻堆块的数据（如函数指针、对象虚表）

### 10.2.2 Use-After-Free（UAF）

```c
class Document {
public:
    virtual void show() { printf("Document\n"); }
};

void uaf_example() {
    Document *doc = new Document();   // 分配
    delete doc;                       // 释放
    // doc 现在是悬垂指针
    doc->show();   // UAF！访问已释放内存
}
```

**UAF 攻击原理**：

1. 释放对象 A，其内存回到堆管理器
2. 分配同样大小的对象 B，占据了 A 原来的内存
3. 攻击者控制 B 的内容（比如伪造虚表指针）
4. 再通过悬垂指针 A 调用虚函数 → 跳转到攻击者控制的地址

这是浏览器漏洞（Chrome、Firefox）中最常见的利用类型。

### 10.2.3 Double Free

```c
char *p = malloc(32);
free(p);
free(p);   // 重复释放！
```

Double Free 会破坏堆的空闲链表（fastbin/tcache），攻击者可以借此实现任意地址分配，进而写入任意内容。

## 10.3 格式化字符串漏洞

```c
#include <stdio.h>

void vuln(char *input) {
    printf(input);   // 用户输入作为格式字符串！
}

int main(int argc, char **argv) {
    vuln(argv[1]);
    return 0;
}
```

**攻击方式**：

- 输入 `%x %x %x`：泄露栈上的数据（栈内容被打印出来）
- 输入 `%s`：把栈上的值当地址，读取任意内存
- 输入 `%n`：向栈上值指向的地址写入数据（任意地址写！）

> **%n 是最危险的**：它能写内存，攻击者可以覆盖返回地址、GOT 表项，实现代码执行。

**修复**：

```c
printf("%s", input);   // 把用户输入当作普通字符串参数
```

## 10.4 整数溢出

```c
#include <stdio.h>

void copy_data(char *input, int len) {
    char buf[64];
    // len 是从外部传入的，攻击者可以传负数或超大值
    if (len < sizeof(buf)) {
        memcpy(buf, input, len);   // 如果 len 是负数？
    }
}

int main() {
    // len = -1 时，-1 < 64 成立（有符号），但 memcpy 的 size_t 参数会把 -1 当巨大值！
    copy_data("AAAA...", -1);
    return 0;
}
```

**整数溢出/符号错误**是常见的绕过检查手法：检查用有符号数，实际使用转无符号，就能绕过长度检查导致溢出。

**修复**：统一用 `size_t`（无符号）做长度检查，检查上界。

## 10.5 现代防护机制

| 机制 | 作用 | 绕过思路 |
|------|------|---------|
| Stack Canary | 栈上放随机值，溢出会破坏它，函数返回前检测 | 泄露 canary |
| NX/DEP | 栈/堆不可执行 | ROP |
| ASLR | 地址随机化 | 地址泄露 + 相对偏移 |
| PIE | 程序本身地址也随机 | 泄露基址 |
| RELRO | GOT 表只读 | 部分 RELRO 可绕过 |

> **攻防本质**：防护机制不断提高攻击门槛，但 attacker 总在找新的绕过方法。这就是为什么安全是一场持续的军备竞赛。作为防守方，要开启所有防护；作为研究者，要理解绕过原理。

**编译时开启防护**：

```bash
gcc -fstack-protector-all -D_FORTIFY_SOURCE=2 -Wl,-z,relro,-z,now program.c -o program
```

## 10.6 安全编码实践

### 10.6.1 避免危险函数

| 危险函数 | 安全替代 |
|---------|---------|
| strcpy | strncpy / snprintf / strcpy_s |
| strcat | strncat / strcat_s |
| sprintf | snprintf |
| gets | fgets / getline |
| scanf("%s") | 指定宽度 %Ns |

### 10.6.2 始终检查边界

```c
// 好的实践
int safe_copy(char *dst, size_t dst_size, const char *src) {
    if (!dst || !src || dst_size == 0) return -1;
    size_t len = strlen(src);
    if (len >= dst_size) return -1;   // 检查
    memcpy(dst, src, len + 1);
    return 0;
}
```

### 10.6.3 使用现代 C++ 特性

- 用 `std::string` / `std::vector` 自动管理内存
- 用智能指针避免 UAF / 内存泄漏
- 用 `at()` 代替 `[]` 做边界检查
- 开启编译器警告 `-Wall -Wextra`

### 10.6.4 静态分析与动态检测

```bash
# 静态分析（代码扫描）
clang --analyze program.c

# 动态检测（运行时）
gcc -fsanitize=address program.c -o program   # ASan 检测内存错误
```

**AddressSanitizer (ASan)** 能在运行时检测越界、UAF、Double Free，是开发和测试的利器。

## 10.7 漏洞分析实战：用 gdb 观察栈溢出

理解漏洞最好的方式是用调试器亲眼看到内存被覆盖。以下实验请在自己的 Linux 环境完成：

```c
// vuln_demo.c
#include <stdio.h>
#include <string.h>

void vulnerable(char *input) {
    char buf[64];
    strcpy(buf, input);
    printf("buf 内容: %s\n", buf);
}

int main(int argc, char **argv) {
    if (argc > 1) vulnerable(argv[1]);
    return 0;
}
```

实验步骤：

```bash
# 关闭防护，方便观察（仅实验用！）
gcc -g -fno-stack-protector -z execstack -o vuln_demo vuln_demo.c

# 用 gdb 加载，传入超长参数
gdb ./vuln_demo
(gdb) run $(python3 -c "print('A'*100)")
# 程序崩溃，观察崩溃地址 0x41414141

(gdb) info registers rip    # 查看指令指针，被覆盖成 0x41414141
(gdb) x/20gx $rsp-100      # 查看栈内容，看到满屏的 0x41
```

你会亲眼看到：输入覆盖了 buf，一路覆盖了保存的返回地址，导致程序跳转到 0x41414141（'A' 的 ASCII 码）。这就是栈溢出的本质。

> **注意**：这只是一次受控的教学实验。真实环境中的利用需要考虑 Canary、ASLR、PIE 等防护，需要更复杂的技术（地址泄露、ROP 链构造）。这些知识在 CTF 的 PWN 方向系统学习。

## 10.8 CERT C 安全编码规范

CERT C 是美国计算机应急反应小组发布的安全编码标准，是 C 语言安全编程的权威指南。几个关键规则：

| 规则 | 内容 |
|------|------|
| MSC34-C | 不要使用已弃用/不安全的函数（strcpy、gets 等） |
| ARR00-C | 理解数组的内存表示，不要越界 |
| STR31-C | 保证字符串有足够空间存放数据和终止符 |
| MEM00-C | 在同一模块同一抽象层分配和释放内存 |
| MEM30-C | 不要访问已释放的内存 |
| FIO30-C | 不要把用户输入直接作为格式化字符串 |

把这些规则内化成编码习惯，比掌握任何攻击技术都重要——**防守者的价值在于让漏洞根本不出现**。

## 10.9 静态分析工具

除了 ASan，还有更多工具帮你发现漏洞：

```bash
# Clang 静态分析器
clang --analyze vuln.c

# CodeQL（GitHub 出品，工业级）
# 能查询代码中的漏洞模式，GitHub Code Scanning 集成

# cppcheck
cppcheck --enable=all vuln.c

# 模糊测试（libFuzzer）—— 自动生成输入找崩溃
clang -fsanitize=fuzzer,address fuzz_target.c -o fuzz
./fuzz   # 自动变异输入，寻找崩溃
```

> **模糊测试（Fuzzing）** 是现代漏洞挖掘的核心技术。给程序喂大量随机/变异输入，观察是否崩溃。Google 的 OSS-Fuzz 项目用这个方式在开源软件里发现了上万个漏洞。这也是安全研究的重要技能。

## 10.10 本章总结

| 漏洞类型 | 原理 | 防御 |
|---------|------|------|
| 栈溢出 | 覆盖返回地址 | Canary、边界检查、安全函数 |
| 堆溢出 | 破坏堆元数据 | 检查边界、ASan |
| UAF | 使用已释放内存 | 释放后置NULL、智能指针 |
| Double Free | 重复释放 | 释放后置NULL |
| 格式化字符串 | 用户输入作格式串 | printf("%s", input) |
| 整数溢出 | 检查与使用类型不一致 | 统一用 size_t，检查上界 |
| 防护机制 | Canary/NX/ASLR/PIE | 全开启 + 安全编码 |
| 分析工具 | gdb、ASan、CodeQL、Fuzzing | 主动发现漏洞 |
