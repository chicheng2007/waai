# 第 15 章 逻辑漏洞与条件竞争

## 本章目标

读完这一章，你将能够：

- 理解逻辑漏洞的本质："代码没写错，但业务流程设计错了"
- 识别常见逻辑漏洞（越权、验证码绕过、支付篡改、密码重置）
- 理解条件竞争的原理与利用
- 掌握用 Burp 重放、改包发现逻辑漏洞的方法
- 知道如何设计安全的业务逻辑

> 前面所有漏洞都是"让代码执行了不该执行的东西"。逻辑漏洞不同——代码老老实实按写的跑了，但**写业务逻辑的人考虑不周**，导致流程可以被钻空子。它像"脑筋急转弯"，考的是对业务流程的理解。这是第三卷的收官，也是从"技术漏洞"到"思维漏洞"的过渡。

---

## 15.1 本质：当"按规矩办事"也能钻空子

一个生活类比：

> 超市搞活动"买一送一"，规则是"付款后凭小票去服务台领赠品"。有人发现：服务台只检查"有没有小票"，不检查"小票是不是今天用的"——于是他捡了一张别人扔掉的旧小票，反复去领赠品。

**代码没错**（服务台确实检查了小票），**但流程设计漏了**（没检查小票是否已使用）。逻辑漏洞就是这个道理。

**核心一句话**：**系统按设计正常运行，但设计本身有缺陷，让攻击者能用"合法"的方式达成非法目的。**

这类漏洞无法靠 WAF、参数化查询等技术手段防御——必须从**业务流程设计**上堵住。

## 15.2 常见逻辑漏洞

### 15.2.1 越权（回顾第 12 章）

- **水平越权**：改 `user_id` 看别人的数据（服务器没验证归属）
- **垂直越权**：普通用户访问管理员接口（服务器没验证权限）

**CTF 考法**：给你两个账号，让你用 A 看到 B 的数据；或改一个参数就进后台。

### 15.2.2 验证码绕过

| 手法 | 原理 |
|------|------|
| 验证码不失效 | 用过的验证码还能重复使用 |
| 验证码在前端 | 前端生成/校验，直接绕过 |
| 验证码可预测 | 用时间戳/简单算法生成，能推算 |
| 不校验空值 | 删掉验证码参数反而通过 |
| 爆破 | 4 位数字验证码，用 burp 爆破（1 万次） |

### 15.2.3 支付金额篡改

**场景**：下单时，客户端提交 `price=1`（商品实际 100 元）。如果服务器**相信客户端传来的价格**，直接用它生成订单——1 元买到 100 元商品。

**正确做法**：价格从服务器数据库取，绝不信客户端传来的金额。

**CTF 考法**：抓包改 `price`、`amount`、`discount` 等参数，看订单金额是否变化。

### 15.2.4 密码重置漏洞

**场景**：找回密码流程，需要输入手机号+验证码。如果服务器只在**前端**判断"验证码是否正确"，或重置链接的 token 可预测/不失效——攻击者能重置他人密码。

**经典手法**：
- 改包把"成功"的响应改成"失败"，或用别人的手机号+自己的验证码
- 重置链接 token 是时间戳/MD5(用户名)，可推算
- 重置后旧密码仍可用（逻辑混乱）

### 15.2.5 登录绕过

- 修改响应包：把 `{"success":false}` 改成 `true`（前端信任后端响应的极端情况）
- SQL 注入万能密码（第 6 章）
- 条件竞争：并发请求绕过次数限制

## 15.3 条件竞争（Race Condition）

### 15.3.1 概念

**场景**：一个操作需要"检查 → 执行"两步。如果在检查和执行的**时间差**内并发大量请求，就可能让检查失效。

**生活类比**：转账时系统先查"余额够不够"，再扣钱。如果趁它查余额的瞬间同时发起 100 笔转账，每笔检查时都看到余额够——结果 100 笔都通过，余额被扣成负数。

### 15.3.2 CTF 中的条件竞争

**典型一：文件上传条件竞争**（第 8 章提过）

服务器"先保存上传文件 → 再检查是否合法 → 不合法则删除"。攻击者并发上传 + 访问 WebShell，抢在删除前执行。

**典型二：积分/金额竞争**

- 领取优惠券：并发请求，让"限领一次"的检查被绕过，领到多张
- 转账/购买：并发让余额检查失效

**典型三：验证码/次数限制竞争**

- 短信验证码发送次数限制：并发请求绕过限制

### 15.3.3 利用方法

用 Burp Suite 的 Intruder 模块，或写并发脚本（Python 的 `requests` + 多线程，第 24 章基础）：

```python
import requests, threading

url = "http://target.com/claim"
def attack():
    requests.get(url)

# 同时发 100 个请求
threads = [threading.Thread(target=attack) for _ in range(100)]
for t in threads: t.start()
for t in threads: t.join()
```

在 CTF 里，条件竞争题通常需要"恰好"的并发时机，多试几次才能成功。

## 15.4 发现逻辑漏洞的方法

逻辑漏洞没有固定 payload，靠的是**对业务流程的敏感**。方法：

1. **画流程图**：把业务流程画出来（每一步做什么、检查什么），找"检查缺失"或"检查可绕过"的环节
2. **改每一个参数**：用 Burp 把请求里所有参数都改一遍，看服务器是否信任
3. **换身份测试**：用 A 的令牌访问 B 的资源
4. **跳步骤**：直接访问流程的后面步骤（如跳过支付直接访问成功页）
5. **重放请求**：把关键请求重复发（验证码、优惠券、转账）
6. **并发请求**：条件竞争测试

**心法**：**像"钻规则空子"的人一样思考**——对每个"系统相信的东西"问一句："它凭什么信？我能不能伪造/绕过？"

## 15.5 逻辑漏洞的防御

| 措施 | 说明 |
|------|------|
| **服务端权威** | 所有关键数据（价格、身份、权限）从服务端取，不信客户端 |
| **每次都校验** | 每个请求都独立验证权限/状态，不依赖前端或前一步结果 |
| **状态机设计** | 用严格的状态流转，防止跳步骤 |
| **一次性令牌** | 验证码/coupon/token 用后即失效 |
| **加锁/事务** | 并发操作用数据库事务/锁防竞争 |
| **幂等设计** | 关键操作防重放（如请求带唯一 ID） |

**根本原则**：**永远不信客户端，每个环节都独立校验。** 这和第 12 章鉴权防御一脉相承。

## 15.5 深度拓展：业务逻辑漏洞的更多场景

15.1–15.5 讲了逻辑漏洞的核心类型。这一节补充真实业务中常见的更多场景——这些也是 CTF 逻辑题的灵感来源。

### 15.5.1 前端校验依赖

**场景**：很多限制只在前端做（JS 校验），服务端完全信任。

- 只能选"普通用户"，前端 JS 禁用了"管理员"选项 → 用 Burp 改包提交 `role=admin`
- 数量限制"最多买 5 件"，前端限制但服务端没校验 → 改包提交 `num=-1` 或 `num=1000`
- 文件类型前端校验 → 第 8 章讲过，改包绕过

**通用思路**：**凡是在前端看到的限制，都要怀疑服务端有没有真正校验**。用 Burp 绕过前端，直接发请求。

### 15.5.2 参数篡改与隐藏字段

- **价格篡改**：第 15.2.3 节讲过，改 `price`、`amount`、`discount`
- **用户 ID 篡改**：改 `user_id`、`uid`、`account` 越权（第 15.2.1 节）
- **隐藏字段**：表单里的 `<input type="hidden" name="is_admin" value="0">`，改成 1
- **数量负数**：`num=-1` 可能导致"反向退款"或逻辑混乱
- **状态码篡改**：改响应包里的 `{"success":false}` 为 `true`（极端情况前端信任后端响应）

### 15.5.3 验证码与 tokens 的逻辑缺陷

| 缺陷 | 利用 |
|------|------|
| 验证码不失效 | 用过的验证码重复使用 |
| 验证码在响应包里返回 | 抓包直接看 |
| 验证码与会话不绑定 | A 的验证码能用于 B 的会话 |
| Token 可预测 | token = MD5(用户名+时间戳)，可推算 |
| Token 不失效 | 重置过的 token 还能再用 |
| 并发绕过次数限制 | 第 15.3 节条件竞争 |

### 15.5.4 业务流程跳跃

**场景**：流程是"下单 → 支付 → 确认 → 发货"，但服务器没校验每一步的前置状态。

- 跳过支付直接访问"确认成功"页面
- 直接调用发货接口，不经过支付
- 修改订单状态参数 `status=paid`

**防护**：服务端用**状态机**严格管理流程，每一步都校验当前状态是否合法，不能跳步。

### 15.5.5 数据竞争的其他场景

除了第 15.3 节的例子：

- **余额并发**：同时发起多笔转账，每笔检查时余额都"够"
- **库存超卖**：并发下单，库存检查被绕过，卖出超过库存的商品
- **积分翻倍**：并发领取积分，领取记录没加锁
- **优惠券复用**：并发使用同一张优惠券

**防护核心**：数据库事务 + 锁（悲观锁/乐观锁）+ 唯一约束。这是对开发者的要求，也是 CTF 条件竞争题的设计原理。

### 15.5.6 发现逻辑漏洞的思维清单

拿到一个业务系统，逐项检查：

```
□ 每个前端限制，服务端是否也校验了？
□ 每个客户端传来的参数（价格/身份/数量/状态），服务端是否信任？
□ 每个多步骤流程，是否能跳步？
□ 每个"一次性"的东西（验证码/token/优惠券），是否真的用后失效？
□ 每个涉及"次数/余额/库存"的操作，是否能并发绕过？
□ 用 A 的身份，能否访问/操作 B 的数据？
□ 响应包里的东西，前端是否盲目信任？
```

**这张清单是发现逻辑漏洞的"检查表"**——CTF 逻辑题基本都落在某一项上。养成逐项检查的习惯，你就能系统地发现这类漏洞。

### 15.5.7 逻辑漏洞为什么难以自动化防御

这是逻辑漏洞和注入类漏洞的根本区别：

- **SQL 注入、XSS**：有明确的"恶意特征"（特殊字符、脚本标签），WAF 能拦截
- **逻辑漏洞**：请求看起来**完全合法**——正常的参数、正常的格式，只是"值"被改了（price=1 而不是 100）

WAF 无法判断 `price=1` 是合法优惠还是攻击——因为它不懂业务。所以逻辑漏洞**只能从业务设计上防御**，这也是为什么它长期位列 OWASP Top 10（失效的访问控制、业务逻辑滥用）。

**对 CTF 选手的启示**：遇到注入/XSS 打不通的题，考虑是不是逻辑漏洞——它往往"藏得更深"，但一旦想到就很简单。

## 15.6 第三卷总结：Web 进阶漏洞全景

学完第 10–15 章，你已覆盖 Web 进阶的核心漏洞：

| 章节 | 漏洞 | 本质 |
|------|------|------|
| 10 | SSRF | 服务器按用户 URL 发起请求 |
| 11 | 反序列化 | 还原对象时自动执行代码 |
| 12 | JWT/鉴权 | 信任客户端身份标识 |
| 13 | SSTI | 用户输入被当模板代码执行 |
| 14 | XXE | XML 解析器读取用户定义的外部资源 |
| 15 | 逻辑漏洞 | 业务流程设计有缺陷 |

你会发现，这些漏洞和基础卷一样，**本质仍是"信任了不该信任的输入"或"数据与指令混淆"**，只是场景更复杂、利用更精巧。抓住这个本质，面对新漏洞也能快速理解。

**Web 方向学习到这里，你已经具备了系统的知识体系。** 接下来第五卷学工具与脚本（把手工能力自动化），第六卷做综合实战（把知识串起来打真题）。而第四卷的 Misc 方向可以穿插学习。

## 15.7 本章总结

| 知识点 | 核心要点 |
|--------|---------|
| 逻辑漏洞本质 | 代码没错，业务流程设计有缺陷 |
| 常见类型 | 越权、验证码绕过、支付篡改、密码重置、登录绕过 |
| 条件竞争 | 检查与执行的时间差；并发请求绕过限制 |

| 防御 | 服务端权威 + 每次校验 + 一次性令牌 + 事务锁 |
