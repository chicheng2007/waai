# 第 12 章 JWT 与身份验证漏洞

## 本章目标

读完这一章，你将能够：

- 理解 JWT 是什么、由哪三部分组成
- 掌握 JWT 的编码原理与验证机制
- 识别并利用 JWT 的常见漏洞（alg=none、弱密钥爆破、算法混淆、密钥泄露）
- 理解水平越权与垂直越权
- 知道鉴权系统的正确设计原则

> JWT（JSON Web Token）是现代 Web 应用最常用的身份认证方案。CTF 里 JWT 题几乎是"必考项"，而且它的漏洞往往很"优雅"——改一个字符就能冒充管理员。这一章带你彻底看懂它。

---

## 12.1 一个生活类比：带防伪章的通行证

想象一个景区发通行证：通行证上写着你的名字和权限（普通游客/VIP），并盖了一个**特殊的防伪章**。你每次进园区，保安只看防伪章是真的，就相信上面写的权限。

**JWT 就是这张通行证**：服务器签发一个"令牌"（token），里面写着你的身份和权限，并用**密钥签名**（相当于防伪章）。之后你每次请求都带着这个令牌，服务器验证签名有效，就相信你的身份——不用每次都查数据库。

**漏洞在哪**？
- 如果防伪章的"配方"（密钥）太简单，攻击者能自己仿造一个
- 如果保安根本不检查防伪章（alg=none），你写啥都行
- 如果你能改通行证上的"权限"字段而防伪章不失效……

## 12.2 JWT 的结构：三段式

一个 JWT 看起来像这样（三段用 `.` 分隔）：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VybmFtZSI6ImFkbWluIiwicm9sZSI6InVzZXIifQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
└──────────── Header ────────────┘ └──────── Payload ────────┘ └──── Signature ────┘
```

三部分：

### 12.2.1 Header（头部）

解码后是 JSON，说明算法和类型：

```json
{"alg": "HS256", "typ": "JWT"}
```

- `alg`：签名算法（HS256 是对称加密，RS256 是非对称）
- `typ`：类型，JWT

### 12.2.2 Payload（载荷）

解码后是 JSON，存放"声明"（身份信息）：

```json
{"username": "admin", "role": "user", "exp": 1234567890}
```

- `username`：用户名
- `role`：角色（user/admin）—— **攻击者最想改的字段**
- `exp`：过期时间

**关键点**：Payload 只是 Base64URL 编码，**不是加密**！任何人都能解码看到内容。所以 JWT 里不能放密码等敏感信息。

### 12.2.3 Signature（签名）

签名 = 用密钥对 `Header.Payload` 计算哈希：

```
HMACSHA256(
  base64url(header) + "." + base64url(payload),
  secret
)
```

服务器用密钥验证签名：如果令牌内容被篡改，签名就对不上，验证失败。**签名的安全性完全依赖密钥的保密性。**

**小白问：Base64URL 编码怎么解？**
> 用 CyberChef 或 jwt.io 网站，把每段粘贴进去就能解码。Base64URL 是 Base64 的变体（把 `+` `/` 换成 `-` `_`，去掉 `=`），解码本质一样。第 16 章会详细讲 Base64。

## 12.3 JWT 的常见漏洞

### 12.3.1 漏洞一：alg=none（无算法）

早期 JWT 库支持 `alg: none`——表示"不签名"。如果服务器没禁止，攻击者把 Header 改成 `{"alg":"none"}`，签名部分留空，服务器就接受一个完全伪造的令牌：

```
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJ1c2VybmFtZSI6ImFkbWluIiwicm9sZSI6ImFkbWluIn0.
（注意最后有个点，签名部分是空的）
```

Payload 里把 `role` 改成 `admin`——冒充管理员成功。

### 12.3.2 漏洞二：弱密钥爆破

HS256 是对称算法，签名和验签用**同一个密钥**。如果密钥很弱（如 `123456`、`secret`、`admin`），攻击者可以**离线爆破**——用字典尝试所有可能的密钥，看哪个算出的签名和令牌里的签名一致。

工具：

```bash
# hashcat 爆破 JWT
hashcat -m 16500 jwt.txt wordlist.txt

# 或用专门的 jwt 工具
jwt_tool
```

**CTF 常见**：题目提示"弱密钥"或密钥在源码/配置里泄露，爆破出来后就能伪造任意令牌。

### 12.3.3 漏洞三：算法混淆（Algorithm Confusion）

如果服务器用 RS256（非对称：私钥签名，公钥验签），但实现有缺陷——攻击者拿到公钥后，把 Header 的 `alg` 改成 HS256，然后用**公钥当密钥**重新签名。

因为服务器误用公钥去验证 HS256（对称）签名，而攻击者用公钥签的名能通过验证——绕过成功。这是个经典且隐蔽的漏洞。

### 12.3.4 漏洞四：密钥泄露

密钥可能泄露在：
- 源码（`.git` 泄露、备份文件，见第 5 章）
- 报错信息
- 公开的密钥（有些库有默认密钥）

拿到密钥 = 能伪造任意用户的令牌 = 完全控制鉴权。

### 12.3.5 漏洞五：逻辑缺陷

- **不检查签名**：服务器只解码 Payload 不验签（直接改 role 就行）
- **exp 不生效**：过期令牌仍被接受
- **kid 参数注入**：Header 里的 `kid`（密钥 ID）被用来拼文件路径或 SQL，可注入

## 12.4 实战流程

拿到一个用 JWT 的站（Cookie 或 Authorization 头里有三段式字符串）：

```
① 观察：用 jwt.io 解码三段，看 Header 的 alg 和 Payload 的内容
② 假设：根据特征判断可能的漏洞
③ 验证：
   - 试 alg=none（改 Header，清空签名）
   - 试直接改 Payload 的 role（如果服务器不验签）
   - 弱密钥爆破（hashcat/jwt_tool）
④ 深入：伪造管理员令牌，访问 /admin 拿 flag
```

**CTF 典型 flag 位置**：伪造 admin 令牌后，管理页面里的 flag，或用 admin 身份才能读的数据。

## 12.5 越权漏洞：鉴权的另一面

JWT 漏洞常和"越权"一起考。越权分两类：

### 12.5.1 水平越权

**同级别用户之间互相访问**。比如你是用户 A，通过改参数（如 `?user_id=B`）访问到用户 B 的数据。

**例子**：`/api/userinfo?id=123`，你把 id 改成别人的，就能看别人的信息——服务器没验证"这个 id 是不是当前登录用户的"。

### 12.5.2 垂直越权

**低权限用户访问高权限功能**。比如普通用户通过改 role 字段、访问隐藏的管理接口，获得管理员权限。

**JWT 题里**：把 Payload 的 `role` 从 `user` 改成 `admin`（如果能绕过签名）就是垂直越权。

### 12.5.3 越权的本质

**服务器信任了客户端传来的身份标识，而没有独立验证**。这是所有鉴权漏洞的共同根源——和前面漏洞"信任用户输入"一脉相承。

---

## 12.6 JWT 与鉴权的防御

| 措施 | 说明 |
|------|------|
| **强密钥** | 用足够长、随机的密钥，定期轮换 |
| **禁用 alg=none** | 库配置里强制指定算法 |
| **算法固定** | 验签时明确指定算法，不接受 Header 里的 alg |
| **保护密钥** | 不放源码、不进 git、用密钥管理服务 |
| **校验 exp/iss/aud** | 检查过期时间、签发者、受众 |
| **服务端鉴权** | 每次敏感操作都验证权限，不只看令牌声明 |
| **不信任客户端身份** | 关键数据从服务端 session/DB 取，不从请求参数取 |

**根本原则**：**客户端传来的身份信息都不可信，服务端必须独立验证权限。**

## 12.6 深度拓展：JWT 工具与进阶攻击

12.1–12.6 覆盖了 JWT 的主流漏洞。这一节补充实战工具和一些进阶场景。

### 12.6.1 jwt_tool：JWT 测试瑞士军刀

```bash
# 安装
pip install jwt-tool

# 基本扫描（自动检测常见漏洞）
python3 jwt_tool.py <JWT令牌> -X a        # 扫描所有攻击向量
python3 jwt_tool.py <JWT令牌> -X n        # alg=none 攻击
python3 jwt_tool.py <JWT令牌> -C -d wordlist.txt   # 弱密钥爆破

# 篡改 Payload（改 role 为 admin）
python3 jwt_tool.py <JWT令牌> -T
# 进入交互界面，可改 Header/Payload，用已知密钥重签名
```

**CTF 用法**：拿到 JWT 先用 `-X a` 全扫描，它会自动尝试 alg=none、算法混淆、常见弱密钥——快速定位漏洞类型。

### 12.6.2 弱密钥爆破的完整流程

```bash
# 1. 把 JWT 保存成文件
echo "eyJhbGci..." > jwt.txt

# 2. hashcat 爆破 HS256（类型 16500）
hashcat -m 16500 jwt.txt /usr/share/wordlists/rockyou.txt

# 3. 爆出密钥后，用 jwt.io 或 Python 伪造令牌
```

Python 伪造：

```python
import jwt
token = jwt.encode(
    {"username": "admin", "role": "admin"},
    "爆破出的密钥",
    algorithm="HS256"
)
print(token)
```

### 12.6.3 算法混淆（RS256→HS256）深入

这是最精妙的 JWT 攻击，值得详细理解：

**前提**：服务器用 RS256（非对称），但代码有缺陷——验签时从 Header 读 `alg` 字段，且 HS256 和 RS256 共用同一个"密钥变量"。

**攻击步骤**：

```
1. 拿到服务器的公钥（通常公开，如 /jwks.json 或 .git 泄露）
2. 把 Header 的 alg 改成 HS256
3. 用"公钥的文本内容"作为 HMAC 密钥，重新签名
4. 服务器验签：读 alg=HS256 → 用配置里的"公钥"当 HMAC 密钥验证 → 通过！
```

**为什么会中招**：服务器把"验签用的公钥"同时当成了"HS256 的共享密钥"。攻击者用公钥签名，服务器用公钥验签，正好匹配。

**防御**：验签算法在服务端**硬编码**（固定用 RS256），绝不从用户可控的 Header 读取 `alg`。

### 12.6.4 JKU / KID 注入

- **JKU（JWK Set URL）**：Header 里的 `jku` 字段指定去哪拿公钥。如果服务器信任这个 URL，攻击者可以指向自己的服务器，提供自己生成的公钥——然后用对应私钥签名，服务器就用攻击者的公钥验证了。
- **KID（Key ID）**：Header 里的 `kid` 字段指定密钥编号。如果服务器把它拼进文件路径（如 `/keys/{kid}`）或 SQL 查询，注入 `../../etc/passwd` 或 SQL 语句可能导致任意文件读取/注入。

**CTF 里遇到 Header 有 jku/kid/x5u 字段时，优先怀疑这些攻击。**

### 12.6.5 JWT 与其他漏洞的组合

JWT 漏洞常和其他漏洞组合出题：

| 组合 | 思路 |
|------|------|
| JWT + 信息泄露 | `.git`/备份文件里泄露密钥或 JWT 签发逻辑 |
| JWT + SQL 注入 | `kid` 字段注入 SQL，绕过密钥验证 |
| JWT + SSTI | 密钥是模板渲染生成的，可能可预测 |
| JWT + 越权 | 改 role 后访问管理接口拿 flag |

**解题提示**：如果一道题既有 JWT 又有别的功能，别只盯着 JWT——线索可能在别处（如源码里硬编码的密钥）。

### 12.6.6 认证机制的整体思考

把 JWT 放进认证体系里看，理解它的位置：

```
传统 Session 认证：
  登录 → 服务器存 Session → Cookie 里放 Session ID → 每次查服务器
  优点：服务端可控、可随时失效
  缺点：需要存储、分布式部署麻烦

JWT 认证：
  登录 → 服务器签发 JWT（含身份+签名）→ 客户端存 JWT → 每次带 JWT
  优点：无状态、易分布式、跨域方便
  缺点：无法主动失效（除非等过期）、密钥泄露后果严重
```

**CTF 意义**：理解 JWT 的"无状态"特性，就知道为什么它一旦被伪造就很难防御——服务器没有任何"黑名单"机制，只能靠签名。这也是为什么密钥安全如此重要。

## 12.7 本章总结

| 知识点 | 核心要点 |
|--------|---------|
| JWT 结构 | Header.alg + Payload（Base64，非加密）+ Signature |
| 签名 | 依赖密钥保密；内容改了签名就失效 |
| 漏洞 | alg=none、弱密钥爆破、算法混淆、密钥泄露、逻辑缺陷 |
| 工具 | jwt.io 解码、hashcat/jwt_tool 爆破 |
| 越权 | 水平（同级互访）、垂直（低权限用高权限）；本质是信任客户端身份 |
| 防御 | 强密钥 + 固定算法 + 服务端独立鉴权 + 不信任客户端身份 |
