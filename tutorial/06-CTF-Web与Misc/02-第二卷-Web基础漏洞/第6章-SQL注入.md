# 第 6 章 SQL 注入：原理、探测与实战

## 本章目标

读完这一章，你将能够：

- 用大白话讲清楚 SQL 注入是怎么发生的
- 理解"拼接 SQL 语句"为什么危险，参数化查询为什么安全
- 掌握注入点探测、闭合判断、联合查询注入的完整流程
- 学会用 sqlmap 辅助，但理解它每一步在做什么
- 理解盲注（布尔/时间）的思路
- 知道如何防御 SQL 注入

> SQL 注入是 Web 安全"四大名著"之首，CTF 里出现频率极高，真实世界危害巨大。这一章写得长、写得细，因为它是你理解"代码漏洞"的第一个完整案例。请务必跟着动手。

## 6.1 一个生活类比：被篡改的账单

想象你去餐厅点餐，服务员给你一张**填空题**菜单：

```
我要点【____】这道菜。
```

你在空格里填："宫保鸡丁"。正常，服务员给你上宫保鸡丁。

但如果你填的是："宫保鸡丁，另外把厨房保险柜里的钱也拿出来给我"——如果服务员**傻到把你填的每个字都当成指令照做**，灾难就发生了。

**SQL 注入就是这个道理**：程序把用户输入"拼"进一条数据库指令（SQL 语句）里，如果用户输入被当成指令执行，而不是当成普通数据，攻击者就能让数据库做它不该做的事——比如把所有用户密码吐出来。

**核心一句话**：**数据和指令混在一起，是 SQL 注入的根源。**

---

## 6.2 背后的数据库：SQL 是什么

SQL（Structured Query Language）是操作数据库的语言。CTF 里最常见的是 MySQL。你不需要精通 SQL，懂几条基本语句就够：

```sql
-- 查询：从 users 表里找 id=1 的用户
SELECT * FROM users WHERE id = 1;

-- 结果显示：id=1, username=admin, password=123456

-- 其他常用
SELECT username, password FROM users WHERE username='admin';
INSERT INTO users VALUES (2, 'tom', 'pass');
UPDATE users SET password='new' WHERE id=1;
DELETE FROM users WHERE id=2;
```

**关键点**：SQL 语句里，字符串要加引号（`username='admin'`），数字不用（`id=1`）。记住这一点，后面"闭合"就靠它。

数据库里有个特殊的"库"叫 `information_schema`，它记录了所有数据库、表、列的信息。注入时常用它来"探查"数据库结构：

```sql
SELECT table_name FROM information_schema.tables WHERE table_schema=database();
-- 列出当前数据库的所有表名
```

## 6.3 漏洞是怎么产生的：一段有问题的代码

看一段典型的 PHP 代码（很多漏洞都长这样）：

```php
<?php
$id = $_GET['id'];  // 从 URL 参数拿到用户输入
// 把用户输入直接拼进 SQL 语句
$sql = "SELECT * FROM users WHERE id = $id";
$result = mysqli_query($conn, $sql);
?>
```

**问题在哪**？`$id` 是用户完全可控的。正常访问 `?id=1`，SQL 变成：

```sql
SELECT * FROM users WHERE id = 1
```

正常。但如果我访问 `?id=1 OR 1=1`，SQL 变成：

```sql
SELECT * FROM users WHERE id = 1 OR 1=1
```

`OR 1=1` 永远为真，于是**返回 users 表的所有行**！我只改了 URL 里的一个参数，就让数据库吐出了全部用户数据。

这就是 SQL 注入：**用户输入改变了 SQL 语句的结构/逻辑**。

**小白问：为什么叫"注入"？**
> 因为你把额外的 SQL 代码"注射"进了原本的语句里，就像给正常的指令里偷偷塞了私货。

## 6.4 注入点探测：找到"门"

### 6.4.1 判断是否存在注入

对每个可疑参数（URL 里的 `?id=1`、POST 表单字段），做这几步测试：

| 输入 | 期望的异常 | 说明 |
|------|-----------|------|
| `1'` | 报错 / 页面异常 | 引号没闭合，SQL 语法出错 → 可能有注入 |
| `1 and 1=1` | 页面正常 | 条件为真，结果不变 |
| `1 and 1=2` | 页面异常/空 | 条件为假，结果变化 → 说明条件被当真执行了 |
| `1 or 1=1` | 返回所有数据 | 经典绕过 |

**最关键的一步：加单引号 `'`**。如果页面报错（或明显异常），说明用户输入被拼进了 SQL 且引号没被正确处理——**存在注入的概率极高**。这是最快的探测法。

### 6.4.2 判断是数字型还是字符型

- **数字型**：`id = $id`（不带引号）。测试 `1 and 1=2`，若结果变化，是数字型
- **字符型**：`id = '$id'`（带引号）。测试 `1' and '1'='2`，若结果变化，是字符型

判断方法：

```
输入：1' and '1'='1   → 正常（字符型闭合成功）
输入：1' and '1'='2   → 异常（字符型，条件为假）
输入：1 and 1=2       → 异常（数字型，条件为假）
```

### 6.4.3 注释符：让后面的代码失效

SQL 里注释符是 `-- `（注意空格）、`#`、`/* */`。在注入时用它"吃掉"原语句后面的内容：

```
原始：$sql = "SELECT * FROM users WHERE id = '$id' AND active=1"
输入：1' OR 1=1 -- 
结果：SELECT * FROM users WHERE id = '1' OR 1=1 -- ' AND active=1'
                                              ↑ 后面全被注释掉了
```

`--` 后面的 `' AND active=1'` 被注释，语句成功闭合，注入生效。

## 6.5 联合查询注入（Union Injection）：最强大的手法

### 6.5.1 原理

`UNION` 操作符能把两个查询的结果合并。利用它，我们可以让数据库"额外"返回我们想查的数据：

```sql
SELECT * FROM users WHERE id = 1
UNION
SELECT username, password FROM users
```

如果页面把查询结果展示出来，第二条 SELECT 的结果就会显示在页面上——**数据被"联合"出来了**。

### 6.5.2 完整实战流程（在 sqli-labs 上练）

假设有个注入点 `?id=1`，目标是拿到数据库里的 flag。按四步走：

**第一步：判断列数（ORDER BY）**

```sql
?id=1' ORDER BY 1--    正常
?id=1' ORDER BY 2--    正常
?id=1' ORDER BY 3--    正常
?id=1' ORDER BY 4--    报错 → 说明原查询有 3 列
```

`ORDER BY n` 按第 n 列排序，n 超过实际列数就报错。找到临界值就知道了列数（这里是 3）。

**第二步：找到显示位**

```sql
?id=-1' UNION SELECT 1,2,3--
```

把 id 设成一个不存在的值（`-1`），让原查询返回空，这样 UNION 的结果才能显示。页面上会出现数字 `2`、`3` 的位置——那就是"显示位"（页面会显示查询结果的第 2、3 列）。

**第三步：爆数据库信息**

```sql
?id=-1' UNION SELECT 1, database(), version()--
```

在显示位上，数据库名和版本就显示出来了。

**第四步：爆表名**

```sql
?id=-1' UNION SELECT 1, group_concat(table_name), 3 
   FROM information_schema.tables 
   WHERE table_schema=database()--
```

`group_concat` 把多个表名拼成一个字符串显示出来。你会看到类似 `users, flags, news`。

**第五步：爆列名**

```sql
?id=-1' UNION SELECT 1, group_concat(column_name), 3 
   FROM information_schema.columns 
   WHERE table_name='flags'--
```

看到 `flag` 表有列 `id, flag_value`。

**第六步：拿数据**

```sql
?id=-1' UNION SELECT 1, group_concat(flag_value), 3 FROM flags--
```

flag 就显示在页面上了！

**这就是联合注入的完整链条**：判断列数 → 找显示位 → 爆库 → 爆表 → 爆列 → 拿数据。每一步都建立在上一步的信息上，这正是第 3 章"四步循环"的体现。

**小白问：为什么要 `id=-1`？**
> 如果 id=1 能查到数据，页面只显示第一行（真实的那个用户），UNION 出来的第二行可能不显示。用 `-1` 让原查询返回空，UNION 的结果就成了第一行，能显示出来。

## 6.6 报错注入：让数据库"自己说出来"

有些场景页面不显示查询结果（没有显示位），但会显示**报错信息**。可以故意制造报错，让错误里带上要查的数据：

```sql
?id=1' AND updatexml(1, concat(0x7e, database()), 1)--
```

`updatexml` 函数第二个参数要求特殊格式，传入非法值会报错，报错内容里会包含 `concat` 的结果——也就是数据库名。`0x7e` 是 `~` 的十六进制，用作分隔符让结果更明显。

常见报错注入函数：`updatexml()`、`extractvalue()`、`floor()+rand()+group by`。

**CTF 里报错注入常见于**：页面不显示查询结果，但把数据库报错原样输出到页面上。

## 6.7 盲注：没有回显时的"猜谜游戏"

最棘手的情况：页面既不显示查询结果，也不显示报错——你只能通过页面"正常/异常"、"响应快/慢"来推断。这就是**盲注**，像猜谜一样一位位试出数据。

### 6.7.1 布尔盲注

利用条件真假导致页面差异：

```sql
?id=1' AND (SELECT SUBSTRING(database(),1,1)='s')--
```

含义："如果数据库名的第一个字母是 's'，页面正常；否则异常"。通过逐个字母试（a、b、c……），就能一位位"猜"出数据库名。

配合函数：
- `SUBSTRING(str, pos, 1)`：取字符串第 pos 个字符
- `ASCII(char)`：取字符的 ASCII 码
- `LENGTH(str)`：字符串长度

先猜长度，再逐位猜字符，虽然慢（要试很多次），但有效。

### 6.7.2 时间盲注

页面连真假差异都没有时，用延时来判断：

```sql
?id=1' AND IF(SUBSTRING(database(),1,1)='s', SLEEP(5), 0)--
```

如果第一个字母是 's'，数据库会 `SLEEP(5)`（延迟 5 秒响应）；否则立即返回。你通过**测量响应时间**来判断猜测是否正确。

这就是第 2 章说的"时间盲注"——用时间差当"是/否"的信号。手工做极慢，所以用 sqlmap 自动化（见 6.9）。

## 6.8 其他注入场景（了解）

| 类型 | 位置 | 思路 |
|------|------|------|
| POST 注入 | 表单字段 | 用 Burp 抓包改 body 里的参数 |
| Cookie 注入 | Cookie 值 | 改 Cookie 里的字段 |
| Header 注入 | User-Agent / Referer / XFF | 服务器把头拼进 SQL |
| 宽字节注入 | 用了 GBK 编码 | 用 `%bf%27` 绕过转义 |
| 二次注入 | 存入数据库后再被查询 | 先存恶意数据，触发时生效 |

这些本质都是"找到可控输入 → 判断是否拼进 SQL → 构造 payload"，只是位置不同。基础打牢后，这些都能举一反三。

## 6.9 sqlmap：自动化注入工具

手工理解原理后，用 sqlmap 提效。它能自动完成探测、爆库、爆表、拿数据的全流程。

```bash
# 基本探测
sqlmap -u "http://target.com/news?id=1"

# 自动爆所有数据库
sqlmap -u "http://target.com/news?id=1" --dbs

# 爆表
sqlmap -u "http://target.com/news?id=1" -D dbname --tables

# 爆列
sqlmap -u "http://target.com/news?id=1" -D dbname -T tablename --columns

# 拿数据
sqlmap -u "http://target.com/news?id=1" -D dbname -T tablename --dump

# POST 请求（抓包保存到文件）
sqlmap -r request.txt

# 指定参数是注入点
sqlmap -u "http://target.com/news?id=1" -p id
```

**新手警告**：
1. **先手工，后工具**。你已经在 6.4–6.7 学过手工流程，再用 sqlmap 就知道它在干什么。一上来就用 sqlmap，你永远只会敲命令，换个场景就懵。
2. **只在授权靶场用**。sqlmap 会发大量请求，对未授权站点用是违法的。
3. **理解输出**。sqlmap 会告诉你注入类型、DBMS 类型、payload 是什么——这些正是你该学习的。

## 6.10 如何防御 SQL 注入（最重要的一节）

学会攻击，更要学会防御。**参数化查询（预编译语句）是根治 SQL 注入的方法。**

### 6.10.1 错误做法：拼接

```php
// 危险！用户输入被拼进 SQL
$sql = "SELECT * FROM users WHERE id = $id";
```

### 6.10.2 正确做法：参数化查询

```php
// 安全：SQL 语句和参数分开
$stmt = $conn->prepare("SELECT * FROM users WHERE id = ?");
$stmt->bind_param("i", $id);   // "i" 表示整数类型
$stmt->execute();
```

**为什么安全**？因为 SQL 语句在 `prepare` 时就已经确定结构，参数 `?` 是后来绑定的**纯数据**——无论用户输入什么，都只会被当成值，不可能改变 SQL 结构。你输入 `' OR 1=1--`，数据库只会查找 id 等于字符串 `"' OR 1=1--"` 的用户（大概率没有），不会执行任何额外逻辑。

这就是 6.1 说的"数据和指令分离"——从根本上堵死了注入。

### 6.10.3 其他防御措施

| 措施 | 作用 |
|------|------|
| 参数化查询 | 根本解法，必做 |
| 输入验证/白名单 | 如 id 必须是数字，限制格式 |
| 最小权限 | 数据库账号只给必要权限，不用 root |
| 关闭详细报错 | 避免报错泄露结构（但 CTF 里这是线索） |
| WAF | 辅助拦截常见 payload，不能替代参数化 |

**小白问：我在 CTF 里看到防御等级高的题注入不了，是为什么？**
> 因为出题人用了参数化查询或严格的过滤——这才是正确的防御。DVWA 的 Impossible 等级就是这么做的，它"注入不了"恰恰说明防御有效。理解这一点，你就同时理解了攻和防。

## 6.10 深度拓展：从"会注入"到"懂注入"

前面 6.1–6.10 覆盖了 CTF 里 90% 的 SQL 注入场景。这一节补充一些进阶但重要的知识，帮你在遇到"变形题"时不慌。

### 6.10.1 注入的本质再思考

回到最根本的问题：**为什么参数化查询能根治注入，而转义不能？**

转义（如把 `'` 变成 `\'`）的思路是"把危险字符变无害"。但它依赖"转义逻辑覆盖所有情况"——一旦有遗漏（如宽字节、二次注入、不同数据库的转义规则差异），就会被绕过。而参数化查询改变了**SQL 语句的编译时机**：语句结构在 `prepare` 阶段就固定了，参数只是后来填入的"值"，无论值里有什么字符，都不可能再改变语句结构。

**这是"堵漏"和"改架构"的区别**。理解了这一点，你就明白为什么安全界一致推荐参数化查询，而不是"把所有特殊字符过滤掉"。

### 6.10.2 不同数据库的注入差异

CTF 里主要是 MySQL，但了解其他数据库能应对变形题：

| 数据库 | 注释符 | 爆结构方式 | 特殊点 |
|--------|--------|-----------|--------|
| **MySQL** | `-- `、`#`、`/**/` | `information_schema` | `group_concat` 拼接结果 |
| **PostgreSQL** | `--` | `information_schema` / `pg_catalog` | 字符串要转 `::text` |
| **Oracle** | `--` | `all_tables` / `user_tab_columns` | 用 `||` 拼接字符串，`rownum` 分页 |
| **SQLite** | `--` | `sqlite_master` | 无 `information_schema`，用 `sqlite_master` 查表 |
| **MSSQL** | `--` | `sysobjects` / `syscolumns` | 堆叠注入支持好 |

**CTF 判断技巧**：通过报错信息（如 `You have an error in your SQL syntax` 是 MySQL）或 `version()` 的输出判断数据库类型，再选对应的爆库语句。

### 6.10.3 堆叠注入（Stacked Queries）

用分号 `;` 分隔，一次执行多条 SQL 语句：

```
?id=1'; INSERT INTO users VALUES(99,'hacker','pass');--
```

如果服务器允许多语句执行（如 PHP 的 `multi_query`），就能插入数据、修改数据甚至删表。MySQLi/PDO 默认可能不允许，但 CTF 里偶尔出现。

**与联合注入的区别**：UNION 只能执行 SELECT 并把结果合并显示；堆叠注入能执行任意语句（INSERT/UPDATE/DROP），但不显示结果。

### 6.10.4 二次注入

有些应用会在存入数据库时转义（看似安全），但读取时**从数据库取出的值没再转义**就直接拼进 SQL：

```
第一步：注册用户名 admin'-- （存入时被转义成 admin\'--，数据库里存的是 admin'--）
第二步：修改密码功能用 SELECT ... WHERE username='从数据库取的值'
        → 取出的是 admin'--，拼进 SQL 导致注释掉后面
```

**防御关键**：从数据库取出的数据同样不可信，取出后拼进 SQL 时仍要参数化。

### 6.10.5 注入点在哪里（扩大搜索面）

新手只盯 URL 参数，但实际注入点可能在：

- **POST body**：登录表单、搜索表单（第 4 章）
- **Cookie**：`Cookie: user_id=1`（改它测试）
- **HTTP 头**：User-Agent、Referer、X-Forwarded-For（服务器可能把它们记进数据库再查询）
- **JSON 请求体**：现代 API 常用，格式是 `{"id": 1}`，改 JSON 里的值
- **路径参数**：RESTful 风格 `/user/1/profile` 里的 `1`

**方法**：把 Burp HTTP History 里每个请求都看一遍，凡是"值会被服务器拿去查数据库"的参数，都值得加 `'` 测试。

### 6.10.6 waf 绕过思路（了解）

出题人常模拟 WAF 过滤 `union`、`select`、空格等。绕过思路（和 XSS 绕过同源）：

```
大小写：      UnIoN SeLeCt
注释插空：    un/**/ion  sel/**/ect
双写：        ununionion → 过滤一次后变 union
编码：        %75nion（u 的 URL 编码）
等价于空格：  /**/、%0a、%0d
等价函数：    不用 information_schema，用 sys.schema_table_statistics（MySQL 5.7）
```

**核心**：过滤是"具体的字符串匹配"，绕过是"找语义等价但字符串不同的写法"。这是所有注入绕过的通用思路。

## 6.11 本章总结

| 知识点 | 核心要点 |
|--------|---------|
| 注入本质 | 用户输入被当成 SQL 指令执行；数据与指令未分离 |
| 探测 | 加 `'` 看报错；and 1=1/1=2 看差异；判断数字/字符型 |
| 闭合 | 字符型用 `'` 闭合，注释符 `-- ` 吃掉后面代码 |
| 联合注入 | ORDER BY 判列数 → UNION 找显示位 → 爆库/表/列 → 拿数据 |
| 报错注入 | updatexml/extractvalue 让报错带出数据 |
| 盲注 | 布尔（真假差异）/ 时间（SLEEP 延时），逐位猜解 |
| sqlmap | 自动化提效；先手工理解，只在授权靶场用 |
| 防御 | **参数化查询（根治）** + 输入验证 + 最小权限 + 关报错 |

5. 思考：`?id=1' OR 1=1--` 里，如果网站对单引号做了转义（`\'`），会怎样？怎么绕过？（提示：宽字节注入）
6. 用 Burp 抓一个 POST 登录请求，尝试在用户名字段做注入测试（在自己的 DVWA 上）。
