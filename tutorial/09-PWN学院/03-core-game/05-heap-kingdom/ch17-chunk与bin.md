# 第 17 关 · chunk 与 bin：柜子标签与回收站

## 🎬 游戏开场

上一关我们知道了:每个柜子(chunk)前面挂着标签牌,退租的柜子会被送进"回收站"。

但回收站不是乱扔的——它有一套**精密的分类系统**。不同大小的柜子进不同的格子,有的格子先进先出,有的后进先出,有的还会合并。

作为玩家,如果你想骗系统,就得先搞懂这套分类规则。因为**所有堆利用技术,本质上都是利用这套规则里的漏洞**。

这一关偏理论,但它是堆篇的地基。我会尽量用游戏语言讲清楚。

---

## 🧠 核心概念(游戏版)

### 1. chunk 标签牌的完整结构

一个被使用的 chunk:

```
  ┌─────────────────────────┐
  │ prev_size (8字节)        │ 前一个chunk的大小(仅前chunk空闲时有效)
  ├─────────────────────────┤
  │ size (8字节)             │ 本chunk总大小 + 3个标志位
  ├─────────────────────────┤ ← mem地址(malloc返回的)
  │ 用户数据                 │
  └─────────────────────────┘
```

**size 字段的低三位是标志位**:

| 位 | 名字 | 含义 |
| --- | --- | --- |
| bit0 | PREV_INUSE | 前一个 chunk 是否在使用 |
| bit1 | IS_MMAPPED | 是否是 mmap 分配的 |
| bit2 | NON_MAIN_ARENA | 是否属于非主 arena |

游戏比喻:标签牌上的数字,最后 3 位不是"大小"的一部分,而是**三个小开关**,记录"前一个柜子有人吗"等状态。堆利用中经常要伪造这些开关。

**空闲的 chunk** 呢?用户数据区会被系统拿来存"回收站的链表指针":

```
  ┌──────────────────┐
  │ prev_size        │
  │ size             │
  ├──────────────────┤ ← 空闲chunk的用户区被当成:
  │ fd 指针          │ ← 指向回收站里的下一个空闲chunk
  │ bk 指针          │ ← 指向上一个空闲chunk
  └──────────────────┘
```

游戏比喻:柜子退租后,系统在你柜子里贴了两张纸条——"上一个空格在哪"(fd)、"下一个空格在哪"(bk),把所有空格串成一条链。

### 2. 回收站的分类:bin 家族

系统把空闲 chunk 按大小分到不同的"格子"(bin):

| 格子名 | 收什么柜子 | 特点 | 游戏比喻 |
| --- | --- | --- | --- |
| **tcache** | 小chunk(默认≤0x410) | 每类最多7个,单链表,LIFO | 门口的快速回收筐 |
| **fastbin** | 很小的chunk(≤0x80) | 单链表,LIFO,不合并 | 小柜专用筐 |
| **unsorted bin** | 刚free的先来这 | 双向链表,FIFO | 待分类中转站 |
| **small bin** | 中等大小(<0x400) | 双向链表,FIFO | 中柜分类架 |
| **large bin** | 大chunk(≥0x400) | 双向链表,按大小排序 | 大柜分类架 |
| **top chunk** | 剩余的大块 | 堆的"边角料" | 还没切的整块料 |

**新版本 glibc(2.26+)新增了 tcache**,它优先级最高——你 malloc 时,系统先看快速回收筐里有没有,有就直接给你。这个特性深刻改变了堆利用,是进阶版的重点。

### 3. free 一个柜子时发生什么?(简化版)

```
你 free(p):
  1. 如果大小适合 tcache 且筐没满(少于7个) → 放进 tcache
  2. 否则如果很小 → 放进 fastbin
  3. 否则 → 放进 unsorted bin
  4. 检查前后邻居是否也空闲 → 是就合并成大chunk
```

malloc 时相反:

```
你 malloc(size):
  1. tcache 里有合适的? → 直接拿(最快)
  2. fastbin/small bin 里有? → 拿
  3. unsorted bin 里翻翻 → 找到就拿,顺便分类
  4. large bin 找 → 找
  5. 都没有 → 从 top chunk 切一块
```

### 4. 为什么这些规则能被利用?

因为系统**信任 chunk 标签牌上的信息**,而且**回收站的链表指针存在 chunk 自己的数据区里**。

想想看:

- 如果我能篡改一个空闲 chunk 的 `fd` 指针,让它指向我希望的地址——那么下次 malloc 时,系统可能就从那个地址"取柜子",相当于**我能骗系统在任意地址分配一个 chunk**!(这是 tcache/fastbin attack 的核心)

- 如果我能让同一个 chunk 被 free 两次——链表里就有两个相同的指针,系统可能把同一个柜子租给我两次,或者返回一个指向任意地址的"假柜子"!(double free)

游戏比喻:你偷偷改了回收站柜子里的"下一个空格"纸条,系统信以为真,带你去了一个你指定的"假柜子"。

**这就是堆利用的精髓:篡改系统信任的元数据,让它帮你完成任意地址读写。**

## 🔧 真实世界对照

| 游戏说法 | 真实术语 |
| --- | --- |
| 标签牌 | chunk header (prev_size, size) |
| 三个开关 | PREV_INUSE / IS_MMAPPED / NON_MAIN_ARENA 标志位 |
| 上一个/下一个纸条 | fd / bk 指针 |
| 快速回收筐 | tcache |
| 小柜筐 | fastbin |
| 中转站 | unsorted bin |
| 分类架 | small bin / large bin |
| 边角料 | top chunk |
| 合并 | coalesce |

## 🎯 闯关任务:观察 fd/bk 指针

写程序,free 一个较大的 chunk(进 unsorted bin),观察里面的指针:

```c
// bins.c
#include <stdio.h>
#include <stdlib.h>
int main() {
    char *a = malloc(0x500);   // 大chunk,会进unsorted bin
    char *b = malloc(0x20);    // 防止a和top chunk合并
    strcpy(a, "AAAAAAAA");
    free(a);                   // a进unsorted bin
    printf("a = %p\n", a);
    // a的前16字节现在应该是fd/bk指针
    unsigned long *p = (unsigned long*)a;
    printf("fd = %p\nbk = %p\n", p[0], p[1]);
}
```

```bash
gcc -g bins.c -o bins
./bins
```

你会看到 fd 和 bk 都指向同一个地方(main_arena 里的某个地址)。这证明了**回收站的链表指针就存在被释放的 chunk 里**——这是后面攻击的落脚点。

理论讲完了,开始实战第一个堆漏洞!

UAF(Use-After-Free)= 你把柜子退租了,却**偷偷留着钥匙**,继续往里塞东西、或者继续用。而系统可能已经把这个柜子租给了别人——你的旧钥匙还能开新柜子的门!

这招在真实漏洞里极其常见,浏览器漏洞里一大半都是 UAF。下一关,我们把它玩明白。
