# 第 18 关 · UAF：退租后偷留的钥匙

## 🎬 游戏开场

你去储物柜中心租了个柜子，把书包放进去，拿到钥匙。用完后你退租了——但**偷偷把钥匙复制了一份没还**。

退租后，系统把这个柜子租给了另一个玩家。而你，拿着旧钥匙，趁新玩家不注意：

- 打开柜子，把里面的东西换成你的（**use-after-free 写入**）
- 或者看看新玩家在里面存了什么（**use-after-free 读取**）

因为柜子还是那个柜子，你的旧钥匙照样能开！

这就是 **UAF(Use-After-Free)**：**指针指向的内存已经被 free 了，但程序还在继续使用这个指针。**

---

## 🧠 核心概念（游戏版）

### 1. 漏洞的本质

```c
char *p = malloc(32);     // 租柜子
free(p);                  // 退租 —— 但 p 还留着！
strcpy(p, "hacker");      // 继续用 p 写入！← UAF！
```

`free(p)` 之后，系统认为这块内存空闲了，可能重新分配。但变量 `p` 里的地址没变，程序如果再次用 `p` 读写，就是在操作一块"已经不属于它"的内存。

游戏比喻：**退了租还留着钥匙**。

### 2. 为什么危险？

因为 free 之后，这块内存会被系统"征用":

- 系统会往里面写回收站指针（fd/bk，回顾第 17 关）。
- 如果这块内存被重新 malloc 给别人，里面就是别人的数据。

所以 UAF 的攻击通常是:

```
1. 申请 chunk A
2. free(A)      → A 进了回收站，但指针 p 还在
3. 再次 malloc  → 系统可能把 A 重新分出来（因为回收站里有）
4. 现在 p 和新指针指向同一块内存！
5. 通过 p 写入 → 就改了新对象的数据（或反之）
```

### 3. 经典 UAF 利用：劫持函数指针

这是 CTF 里最常见的 UAF 场景。程序有个结构:

```c
struct Obj {
    void (*func)(char*);   // 函数指针(游戏里的"技能按钮")
    char data[24];
};
```

流程:

1. 申请一个 Obj,func 指向正常函数(比如打印数据)。
2. free 掉它,但指针还在。
3. 趁机再次 malloc 同样大小,系统会返回同一块内存。用你的输入填满它,把 func 字段改成 `system` 的地址,data 填 `/bin/sh`。
4. 程序调用旧指针的 func——现在它是 system,而且参数是 `/bin/sh`!

游戏比喻:你退租后重新租回同一个柜子,把柜子里"技能按钮"的标签从"打印"偷偷换成"开 shell",然后城管(程序)按旧钥匙来按这个按钮——中招。

### 4. UAF 的两大类型

| 类型 | 游戏说法 | 利用 |
| --- | --- | --- |
| UAF 读 | 用旧钥匙偷看 | 泄露内存数据(如 libc 地址) |
| UAF 写 | 用旧钥匙塞东西 | 篡改新对象的数据/函数指针 |

### 5. 注意 tcache 的影响

新版本 glibc 里,free 的小 chunk 先进 **tcache**(第 17 关)。tcache 有个 key 机制防止重复 free,但 UAF 依然可行——你只需巧用 tcache 的"再次 malloc 返回同一块"特性。进阶版会详解。

## 🔧 真实世界对照

| 游戏说法 | 真实术语 |
| --- | --- |
| 退租留钥匙 | free 后 retention 的悬垂指针(dangling pointer) |
| 旧钥匙开新柜 | 再次 malloc 返回同一 chunk |
| 换技能按钮 | 改写函数指针为 system |

**真实案例**:浏览器(UAF 是 Chrome 漏洞的头号类型)、内核、各种 C++ 程序的虚函数表 UAF。

## 🎯 闯关任务:你的第一个 UAF

写一个有 UAF 的程序:

```c
// uaf.c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

char *p;

void add() { p = malloc(0x20); }
void edit() { printf("输入内容:"); read(0, p, 0x20); }
void show() { printf("%s\n", p); }
void del()  { free(p); /* 注意:没有把 p 置 NULL! */ }

int main() {
    // 简化菜单,让你手动调用 add/edit/show/del
    // 用 gdb 观察:free后再malloc,p是否指向同一块
}
```

任务:

1. add → show → del → add(再次申请),用 gdb 观察两次 malloc 返回的地址是否相同。
2. 如果相同,说明你拿回了同一个柜子——这就是 UAF 的基础。
3. 尝试在 del 之后,通过旧指针 p 写入数据,看会不会影响新对象。

(真实的 UAF 题会有更完整的菜单交互和函数指针结构,这里先理解原理。)

## 🎬 下一关预告

**第 19 关 · Double Free：退租两次的骗局**

UAF 是"退租后偷用钥匙"。Double Free 更骚——你**把同一个柜子退租两次**!

正常系统会发现"这柜子已经退过了"然后拒绝。但 glibc 的某些检查有漏洞(尤其在 tcache 和 fastbin 里),通过一些技巧可以绕过,让回收站里出现两个相同的指针。

结果:你 malloc 两次,系统给你**同一个柜子**——然后你就能构造出指向任意地址的"假柜子",实现任意地址写!
