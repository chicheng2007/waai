# 第 7 章 二进制保护机制全家福

> 现代操作系统和编译器在程序里埋下了一道道防线：栈不可执行、栈哨兵、地址随机化、GOT 只读……了解它们，你才能知道「哪些门被锁了，哪些窗还开着」。

---

## 7.1 先看 checksec 的输出

拿到一个二进制文件，第一件事永远是跑 checksec：

```bash
checksec --file=./vuln
```

典型输出：

```text
    Arch:     amd64-64-little
    RELRO:    Partial RELRO
    Stack:    Canary found
    NX:       NX enabled
    PIE:      PIE enabled
```

逐项解释：

| 项目 | 含义 | 对利用的影响 |
| --- | --- | --- |
| Arch | 架构（amd64/i386/arm） | 决定用 64 位还是 32 位的 payload |
| RELRO | GOT 表保护级别 | Full RELRO → GOT 不可写，无法 GOT 覆写 |
| Stack | Canary 栈保护 | 有 Canary → 不能直接覆盖返回地址，需先泄露或绕过 |
| NX | 栈不可执行 | NX on → 栈上的 shellcode 不会执行，需要 ROP |
| PIE | 地址随机化 | PIE on → 代码地址随机，需要先泄露基址 |

---

## 7.2 NX / DEP：栈不可执行

### 7.2.1 原理

**NX（No eXecute）** 在 Windows 里叫 **DEP（Data Execution Prevention）**。它的原理很简单：把栈和堆标记为「不可执行」，只有 `.text` 段有执行权限。

在 ELF 中，这通过 Program Header 的 `GNU_STACK` 段实现：

```bash
readelf -l ./vuln | grep GNU_STACK
```

如果输出里有 `RWE`，说明栈可执行；如果是 `RW`，说明栈不可执行。

### 7.2.2 为什么有 NX

没有 NX 时，攻击者可以把 shellcode 写入栈，然后让返回地址指向栈上的 shellcode——就像第 4 章描述的那样。NX 让这条路走不通：跳到栈上执行会触发段错误（SIGSEGV）。

### 7.2.3 绕过思路

NX 诞生后，攻击者想出了 **ROP（Return-Oriented Programming）**：不执行栈上的代码，而是复用程序已有的代码（gadget），通过精心布置的栈来「拼凑」出想要的逻辑。这就是第 11 章的内容。

> 💡 **历史小知识**：NX 和 ROP 的攻防是二进制安全史上最精彩的篇章之一。NX 出现后，人们一度认为栈溢出被终结了，直到 ROP 横空出世——它证明了「只要能控制返回地址，就能控制程序」。

## 7.3 Canary：栈上的哨兵

### 7.3.1 原理

**Stack Canary**（栈金丝雀）的名字来自煤矿里的金丝雀——矿工用金丝雀来检测瓦斯泄漏，金丝雀死了就赶紧跑。

它的实现是：在函数开始时，从 TLS（线程本地存储）里读取一个随机值，存到栈上局部变量和返回地址之间；函数返回前检查这个值是否被改变，如果变了就调用 `__stack_chk_fail` 终止程序。

栈布局变成：

```text
[ 局部变量 ][ Canary ][ 保存的 rbp ][ 返回地址 ]
```

汇编层面：

```asm
; 函数序言
mov  rax, QWORD PTR fs:0x28    ; 从 TLS 读取 canary
mov  QWORD PTR [rbp-0x8], rax  ; 存到栈上

; 函数尾声
mov  rax, QWORD PTR [rbp-0x8]
xor  rax, QWORD PTR fs:0x28    ; 与原始值比较
jne  __stack_chk_fail          ; 不同 → 程序终止
```

### 7.3.2 关键特性

1. **随机性**：Canary 每次程序启动都不同（由 `atexit` 或内核随机生成）
2. **低位为 0**：Canary 的最低字节通常是 `\x00`，这是为了防止通过字符串拷贝泄露它
3. **检查时机**：在函数返回前检查，所以如果溢出发生在检查之后（比如某些异常路径），可能绕过

### 7.3.3 绕过思路

- **泄露 Canary**：用格式化字符串漏洞或越界读把 Canary 读出来，然后在 payload 里把它原样填回去
- **逐字节爆破**：在可以多次尝试且崩溃不影响服务的情况下（如 fork 型服务），逐字节猜测 Canary
- **伪造 Canary**：如果能控制 TLS 或 Canary 的检查过程
- **错位覆盖**：不覆盖 Canary，只覆盖它后面的数据（某些特殊场景）

第 12 章会详细讲这些手法。

## 7.4 ASLR 与 PIE：地址随机化

这两个概念经常被混为一谈，但它们不是一回事。

### 7.4.1 ASLR

**ASLR（Address Space Layout Randomization）** 是操作系统层面的机制。它随机化：

- 栈的起始地址
- 堆的起始地址
- 共享库（libc）的加载地址
- mmap 区域

ASLR 由内核参数控制：

```bash
cat /proc/sys/kernel/randomize_va_space
# 0 = 关闭, 1 = 部分随机（堆和栈）, 2 = 完全随机（含 mmap）
```

### 7.4.2 PIE

**PIE（Position Independent Executable）** 是编译器/链接器层面的机制。它让**程序自身的代码段和数据段**也随机化加载。

```bash
# 编译 PIE 程序
gcc -fPIE -pie -o vuln_pie vuln.c

# 关闭 PIE
gcc -no-pie -o vuln_nopie vuln.c
```

关闭 PIE 时，程序的 `.text`、`.data`、GOT 等地址是**固定的**（比如 `0x400000` 开头）。开启 PIE 后，这些地址每次运行都不同（比如 `0x55a1b2c3d000` 开头）。

### 7.4.3 两者关系

- ASLR 开启、PIE 关闭：程序自身地址固定，但栈、堆、libc 地址随机
- ASLR 开启、PIE 开启：所有地址都随机，包括程序自身
- ASLR 关闭：无论 PIE 开不开，地址都不随机

### 7.4.4 绕过思路

地址随机化的核心绕过思路只有一个字：**泄露**。

- 泄露 libc 中某个函数的地址 → 减去偏移 → 得到 libc 基址
- 泄露栈上某个指针 → 得到栈地址
- 泄露程序自身的某个地址（如返回地址） → 得到 PIE 基址

泄露的手法包括：格式化字符串、函数调用时打印 GOT 内容、利用堆布局等。

## 7.5 RELRO：保护 GOT 表

**RELRO（Relocation Read-Only）** 保护 GOT 表不被篡改。

### 7.5.1 Partial RELRO

```bash
gcc -Wl,-z,relro -o vuln vuln.c
```

Partial RELRO 将 `.init_array`、`.fini_array` 等设为只读，但 `.got.plt` 仍然**可写**。

后果：可以覆写 GOT 表中的函数指针（如把 `puts@got` 改成 `system` 的地址）。

### 7.5.2 Full RELRO

```bash
gcc -Wl,-z,relro,-z,now -o vuln vuln.c
```

Full RELRO 在程序启动完成所有重定位后，把整个 GOT 表设为只读。

后果：GOT 覆写彻底失效。攻击者需要找其他可写的函数指针，比如：

- `__free_hook` / `__malloc_hook`（libc 中的钩子函数）—— 注意：glibc 2.34 之后这些 hook 被移除了
- `_IO_list_all`、`_IO_2_1_stdout_` 等 FILE 结构
- `__exit_funcs`（exit 处理函数链表）

这些是 IO_FILE 利用和 House of 系列技术的基础。

### 7.5.3 怎么判断

checksec 显示 `RELRO: Full RELRO` 就是全保护，`Partial RELRO` 就是部分保护。

## 7.6 FORTIFY_SOURCE

**FORTIFY_SOURCE** 是 GCC 的一个安全特性，它在编译时检查一些危险函数（`memcpy`、`strcpy`、`sprintf` 等）的调用，如果能确定目标缓冲区大小，就插入边界检查。

```bash
# 开启 FORTIFY（需要 -O 优化）
gcc -O2 -D_FORTIFY_SOURCE=2 -o vuln vuln.c
```

关键影响：

- 如果编译器能推断出缓冲区大小，溢出会被检测到并终止程序
- 如果无法推断（比如通过指针传递），则检查无效
- 对 `printf` 类函数，FORTIFY 会禁止 `%n` 格式符出现在可写的内存中（限制格式化字符串攻击）

在 CTF 题中，FORTIFY 通常不是主要障碍，因为它依赖编译器的静态推断能力。但在实际软件中，它能拦住不少低级错误。

## 7.7 更新的防线：CET 与 Shadow Stack

这是较新的防护技术（Intel CET / AMD Shadow Stack），在部分新系统上有：

- **Shadow Stack**：额外维护一个只保存返回地址的栈，与正常栈分离。攻击者覆盖了正常栈上的返回地址，但 Shadow Stack 里的值没变，函数返回时会检测到不一致并终止。
- **IBT（Indirect Branch Tracking）**：限制间接跳转的目标必须是 `endbr64` 指令开头，防止 ROP 链跳到任意位置。

目前 CTF 题目中遇到 CET 的情况还不多（需要硬件和内核同时支持），但随着普及，未来的 PWN 会越来越依赖其他绕过技术（如 SROP、signal handler 等）。

## 7.8 保护机制对照表

把这一章的内容浓缩成一张表：

| 保护 | 编译开关 | 防什么 | 主要绕过手段 |
| --- | --- | --- | --- |
| NX | `-z noexecstack`（默认） | 栈上 shellcode | ROP、ret2libc |
| Canary | `-fstack-protector` | 直接覆盖返回地址 | 泄露 Canary、爆破 |
| ASLR | 内核参数 | 地址可预测 | 泄露地址、爆破（32 位） |
| PIE | `-fPIE -pie` | 程序地址固定 | 泄露 PIE 基址 |
| Partial RELRO | `-Wl,-z,relro` | 部分 GOT 改写 | 覆写 .got.plt |
| Full RELRO | `-Wl,-z,now` | GOT 覆写 | hook 函数、IO_FILE |
| FORTIFY | `-D_FORTIFY_SOURCE=2` | 危险函数溢出 | 编译器推断失败时绕过 |
| CET | 硬件+内核支持 | ROP | 尚未普及 |

## 7.9 实战：看你手里的程序穿了什么盔甲

```bash
# 对第二章编译的四个程序分别 checksec
checksec --file=./vuln64
checksec --file=./vuln32

# 自己编译几个不同保护级别的程序对比
gcc -g -O0 -no-pie -fno-stack-protector -z execstack -o naked vuln.c
gcc -g -O0 -no-pie -fstack-protector-all -z noexecstack -o canary vuln.c
gcc -g -O0 -pie -fstack-protector-all -z noexecstack -Wl,-z,relro,-z,now -o armored vuln.c

checksec --file=./naked
checksec --file=./canary
checksec --file=./armored
```

观察三个程序 checksec 输出的差异，理解每个编译开关对应哪一项保护。

## 7.10 小结

这一章我们系统梳理了保护机制：

- **NX** 让栈不可执行 → 用 ROP 绕过
- **Canary** 在栈上放哨兵 → 泄露或爆破 Canary
- **ASLR** 随机化栈/堆/libc → 泄露地址计算基址
- **PIE** 随机化程序自身 → 泄露 PIE 基址
- **RELRO** 保护 GOT → Full RELRO 下改用 hook/IO_FILE
- **CET/Shadow Stack** 是未来的防线，目前 CTF 中少见

到这里，**筑基篇（第一篇）圆满结束**。你已经建立了完整的知识框架：C 语言 → 汇编 → ELF → 栈 → 保护机制。接下来的第二篇，我们终于要开始「真正的 PWN」——栈溢出利用了。
