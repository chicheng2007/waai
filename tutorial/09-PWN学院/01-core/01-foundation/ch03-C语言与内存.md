# 第 3 章 C 语言与内存模型

> 如果说 PWN 是一座大厦，那 C 语言和内存模型就是它的地基。这一章可能看起来和「漏洞利用」没什么关系，但你后面写的每一个 payload，本质上都是在和 C 程序留下的内存痕迹打交道。

---

## 3.1 为什么 PWN 需要 C 语言

你可能会问：我不是要学漏洞利用吗，为什么要学 C 语言？

原因很简单：**绝大多数有漏洞的程序都是用 C/C++ 写的**。C 语言把内存管理的权力完全交给了程序员——这既是它的强大之处，也是无数漏洞的根源。

在 C 语言里，你可以：

- 直接访问任意内存地址（通过指针）
- 手动申请和释放内存（malloc / free）
- 不检查数组边界就往里写数据

这些特性在系统编程中非常高效，但也意味着：**程序员稍有疏忽，就会留下可被利用的漏洞**。而 Python、Java 这类语言有垃圾回收和边界检查，就不太容易出现这类问题。

所以，学 PWN 必须懂 C 语言。但你不需要成为 C 语言专家，只需要理解那些和内存密切相关的概念。这正是本章要做的事。

---

## 3.2 从 Hello World 到可执行文件

先从最熟悉的程序开始：

```c
#include <stdio.h>

int main() {
    printf("Hello, world!\n");
    return 0;
}
```

你敲下 `gcc hello.c -o hello` 然后运行，屏幕上打印出 `Hello, world!`。但在这之间，发生了什么？

一个 C 程序变成可执行文件，要经过四个阶段：

```
源文件 hello.c
    │
    ├─ 预处理（cpp）：处理 #include、#define 等
    │      → hello.i
    │
    ├─ 编译（cc1）：翻译成汇编语言
    │      → hello.s
    │
    ├─ 汇编（as）：翻译成机器码（目标文件）
    │      → hello.o
    │
    └─ 链接（ld）：把库函数和多个目标文件合并
           → hello（可执行文件）
```

这个流程里有一个关键点：**编译后的程序不再有变量名，只剩下一堆内存地址和机器指令**。当你写 `int x = 5;` 时，编译器会决定把 `5` 放在内存的某个位置，之后所有对 `x` 的访问都会变成对这个地址的读写。

PWN 要做的事，就是在机器码层面理解这些地址，然后想办法改变程序的行为。

## 3.3 变量与内存地址

把内存想象成一个巨大的、按字节编号的旅馆。每个房间有一个门牌号（地址），每个房间能住 1 字节（8 位）的数据。

```text
地址        内容
0x1000    ┌──────┐
0x1001    │      │
0x1002    │      │
0x1003    │      │
   ...    │  ... │
```

在 C 语言里声明一个变量：

```c
char a;      // 占 1 字节
int b;       // 通常占 4 字节
long c;      // 通常占 8 字节（64 位系统）
double d;    // 占 8 字节
```

编译器会在内存里给它们分配空间。假设 `a` 被分配在地址 `0x1000`，那么往 `a` 里写数据，就是往 `0x1000` 这个房间写 1 字节。

几个重要概念：

- **字节（Byte）**：内存的基本单位，1 字节 = 8 位
- **地址（Address）**：内存位置的编号，通常用十六进制表示（比如 `0x7fffffffe000`）
- **字长（Word）**：CPU 一次能处理的位数，64 位系统的字长是 8 字节
- **对齐（Alignment）**：数据存放的地址通常是其大小的整数倍（比如 4 字节的 int 通常放在能被 4 整除的地址上）

> 💡 **提示**：你在 gdb 里看到地址时，64 位程序的地址通常是 `0x7ffff` 开头的 12 位十六进制数（比如 `0x7fffffffe000`），32 位程序的地址通常是 `0xff` 开头的 8 位数（比如 `0xffffd000`）。这在后面判断泄露出来的地址属于栈还是 libc 时很有用。

## 3.4 指针：PWN 的基石

指针是 C 语言的灵魂，也是 PWN 的核心。**如果你对指针的理解还停留在「指针就是地址」的层面，请认真读这一节。**

### 3.4.1 什么是指针

```c
int x = 42;
int *p = &x;
```

这里：

- `x` 是一个 int 变量，值是 42
- `&x` 是取 `x` 的地址
- `p` 是一个指针变量，它的值是 `x` 的地址

可以这样理解：`x` 是一个房间，`42` 是房间里住的人；`p` 是另一张纸条，上面写着 `x` 这个房间的门牌号。

```
变量 x:  [ 42 ]      ← 地址 0x1000
           ↑
           │ &x
           │
变量 p:  [0x1000]    ← 地址 0x2000
```

要读取 `p` 指向的值，用解引用操作符 `*`：

```c
printf("%d\n", *p);   // 输出 42
```

### 3.4.2 指针的类型决定了解引用时的读取长度

这是新手最容易忽略的一点。指针是有类型的，`int *p` 和 `char *p` 虽然都存储一个地址，但解引用时读取的字节数不同：

```c
int x = 0x41424344;   // 4 字节
char *c = (char *)&x;
int  *i = &x;

printf("%c\n", *c);   // 读 1 字节，输出 'D'（小端序，低位在前）
printf("%x\n", *i);   // 读 4 字节，输出 41424344
```

**指针类型决定了编译器生成什么指令去读内存**——是读 1 字节（`movzx`）还是 4 字节（`mov`）。这在后面构造任意地址读写时非常关键。

### 3.4.3 指针运算

```c
int arr[5] = {1, 2, 3, 4, 5};
int *p = arr;      // p 指向 arr[0]

p + 1;             // 指向 arr[1]，地址增加了 sizeof(int) = 4 字节
p + 2;             // 指向 arr[2]，地址增加了 8 字节
```

指针加 1，不是地址加 1，而是地址加「一个元素的大小」。这个特性在数组遍历和漏洞利用中经常用到。

### 3.4.4 危险指针

- **空指针（NULL）**：值为 0 的指针，解引用会导致程序崩溃
- **野指针（Dangling Pointer）**：指向已经释放的内存——这正是 UAF 漏洞的根源（堆篇会详细讲）
- **未初始化指针**：值随机，解引用可能导致任意地址读写

## 3.5 数组与字符串

### 3.5.1 数组在内存中是连续的一段

```c
int arr[5] = {10, 20, 30, 40, 50};
```

内存布局（假设 arr 起始地址是 `0x1000`）：

```text
地址      内容        索引
0x1000    10          arr[0]
0x1004    20          arr[1]
0x1008    30          arr[2]
0x100c    40          arr[3]
0x1010    50          arr[4]
0x1014    ???         越界！
```

数组名 `arr` 在大多数情况下会退化成「指向第一个元素的指针」，所以 `arr[i]` 等价于 `*(arr + i)`。

**关键问题：C 语言不检查数组边界。** 如果你写 `arr[5] = 60;`，程序会老老实实地往 `0x1014` 写 60，哪怕那不是数组的一部分。如果 `0x1014` 正好是函数的返回地址……恭喜，你就有了栈溢出。

### 3.5.2 字符串就是字符数组，以 \0 结尾

```c
char str[] = "Hello";
```

内存布局：

```text
地址      内容
0x1000    'H'  (0x48)
0x1001    'e'  (0x65)
0x1002    'l'  (0x6c)
0x1003    'l'  (0x6c)
0x1004    'o'  (0x6f)
0x1005    '\0' (0x00)  ← 字符串结束标志
```

字符串以空字符 `\0`（字节值 0）结尾。这个约定带来两个后果：

1. **格式化字符串漏洞**：如果字符串没有正确结尾，printf 会一直读下去（后面章节详讲）
2. **截断问题**：如果字符串中间出现 `\0`，很多函数会认为字符串在这里结束

### 3.5.3 危险的输入函数

回到第二章的 `vuln.c`，它用了 `gets()`：

```c
char buf[64];
gets(buf);    // 危险！
```

`gets()` 会一直读取输入直到换行，完全不检查目标缓冲区有多大。如果你输入 100 个字符，它就会往 64 字节的缓冲区里塞 100 字节——多出来的 36 字节会覆盖相邻的内存，包括返回地址。

类似的危险函数还有：

| 函数 | 危险原因 |
| --- | --- |
| `gets()` | 完全不检查长度（已在 C11 中移除，但老程序还在用） |
| `strcpy()` | 不检查目标缓冲区大小 |
| `strcat()` | 同上 |
| `sprintf()` | 不检查目标缓冲区大小 |
| `scanf("%s", buf)` | 不限制输入长度（可以用 `%64s` 限制） |
| `printf(user_input)` | 格式化字符串漏洞 |

看到这些函数，就要警觉起来——它们往往是漏洞的入口。

## 3.6 结构体与内存对齐

结构体让 C 语言能定义复杂的数据类型：

```c
struct Person {
    char name[20];   // 20 字节
    int age;         // 4 字节
    double height;   // 8 字节
};
```

你可能会以为 `sizeof(struct Person)` 是 20 + 4 + 8 = 32 字节，但实际上是 **40 字节**。这是因为 CPU 访问内存时要求数据对齐，`double` 需要放在 8 的倍数地址上，编译器会在 `age` 和 `height` 之间插入 4 字节的填充：

```text
偏移     内容
0-19     name[20]
20-23    age
24-27    填充（padding）
28-35    height
```

**对齐规则**：每个成员的起始地址必须是其大小的整数倍（char 是 1，int 是 4，double 是 8）。

为什么这很重要？因为在堆利用中，我们需要精确计算结构体的大小和成员偏移，才能正确构造伪造的结构体。

> 💡 **提示**：可以用 `#pragma pack(1)` 强制取消对齐，但会略微降低性能。CTF 题目里有时会遇到这种情况。

## 3.7 函数与参数传递

函数调用时，参数是怎么传过去的？在 x86-64 架构下（遵循 System V AMD64 ABI），前 6 个整数/指针参数通过寄存器传递：

```text
rdi, rsi, rdx, rcx, r8, r9
```

超过 6 个的参数才会放到栈上。

```c
int add(int a, int b) { return a + b; }
int result = add(3, 4);   // a 在 edi，b 在 esi
```

这个细节在 ROP 构造时至关重要——如果你想调用 `system("/bin/sh")`，就必须把 `"/bin/sh"` 的地址放进 `rdi` 寄存器，而不能简单地把它压到栈上。

> ⚠️ **注意**：32 位程序（x86）的参数全部通过栈传递，调用约定不同（cdecl）。教程会同时覆盖两种架构，请留意标注。

## 3.8 大端与小端

这是一个初学者容易迷糊的概念。

假设有一个 32 位整数 `0x12345678`，它在内存里是怎么存的？

- **小端序（Little Endian）**：低位字节存在低地址（x86、x86-64 都用它）

```text
地址      内容
0x1000    0x78   ← 最低位
0x1001    0x56
0x1002    0x34
0x1003    0x12   ← 最高位
```

- **大端序（Big Endian）**：高位字节存在低地址（网络协议、某些 ARM/MIPS 架构）

```text
地址      内容
0x1000    0x12   ← 最高位
0x1001    0x34
0x1002    0x56
0x1003    0x78   ← 最低位
```

**PWN 中几乎 always 是小端序**。这意味着当你在 payload 里写一个地址 `0x7fffffffe000` 时，实际发送的字节顺序是 `\x00\xe0\xff\xff\xff\x7f`（低位在前）。

用 pwntools 可以自动处理：

```python
from pwn import *
p64(0x7fffffffe000)   # b'\x00\xe0\xff\xff\xff\x7f'
p32(0x08048000)       # b'\x00\x80\x04\x08'
```

## 3.9 重新看 vuln.c：栈溢出的 C 语言视角

现在，我们有了足够的知识来审视第二章那个程序：

```c
void vulnerable() {
    char buf[64];
    gets(buf);
    printf("You said: %s\n", buf);
}
```

`buf` 是栈上的一个 64 字节数组。`gets()` 会无限读取输入。当你输入超过 64 字节时，多出来的数据会向高地址方向覆盖。栈的布局大致是：

```text
高地址
+------------------+
|  调用者的栈帧     |
+------------------+
|  返回地址         |  ← 覆盖这里就能控制程序跳转
+------------------+
|  保存的 rbp       |
+------------------+
|  buf[63]         |
|  ...             |
|  buf[0]          |  ← buf 的起始地址（低地址）
+------------------+
低地址
```

所以，如果你发送 64 个字节的填充 + 8 字节的伪造 rbp + 8 字节的目标地址，就能让函数返回时跳转到你想去的地方。这就是栈溢出的本质——**利用 C 语言不检查数组边界的漏洞，覆盖栈上的返回地址**。

（偏移量的精确计算会在第 8 章讲，现在你只需要建立这个概念。）

## 3.10 小结

这一章我们讲了很多基础概念，来回顾一下重点：

- **C 语言把内存管理权交给程序员**，这是漏洞的根源，也是 PWN 存在的原因
- **变量在内存中占据一段连续空间**，地址用十六进制表示
- **指针存储地址，类型决定解引用时读取的长度**——这是任意读写的理论基础
- **数组是连续内存，C 语言不检查边界**，越界写可能导致栈溢出
- **字符串以 \0 结尾**，printf 类函数遇到它没有 \0 会一直读
- **结构体有内存对齐**，计算偏移时要注意 padding
- **x86-64 的参数通过寄存器传递**（rdi、rsi、rdx...）
- **x86 架构使用小端序**，payload 中的地址要按字节反转（用 p64/p32）

如果这些概念你还觉得模糊，没关系——后面的章节会不断用到它们，你会逐渐熟练。**现在最重要的是理解：程序在内存中就是一堆字节，而 C 语言允许你直接操作这些字节。**

下一章，我们要学习汇编语言。它看起来比 C 语言更「底层」、更「难懂」，但实际上指令就那么几十条，一旦入门，你会发现它比 C 语言更诚实——每条指令做什么都一目了然。
