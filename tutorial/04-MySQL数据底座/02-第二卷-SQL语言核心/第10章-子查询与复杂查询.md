# 第 10 章 子查询与复杂查询

## 本章目标

读完这一章，你将能够：

- 理解子查询的概念和分类
- 在 WHERE、FROM、SELECT 中使用子查询
- 掌握 EXISTS / NOT EXISTS
- 理解 IN vs EXISTS 的选择
- 用 ANY / ALL 做比较
- 知道什么时候用子查询、什么时候用 JOIN

---

## 10.1 什么是子查询

**子查询（Subquery）** 就是"嵌套在另一条 SQL 里的 SELECT"。里面的叫子查询（内层），外面的叫主查询（外层）。

```sql
SELECT ip, username, login_time
FROM login_logs
WHERE ip IN (
    SELECT ip FROM threat_intel WHERE severity >= 4
);
```

内层的 `SELECT ip FROM threat_intel...` 先执行，找出高危威胁 IP；外层再用这些 IP 过滤登录日志。

> **小白问**：子查询是不是很慢？
> 不一定。简单的子查询 MySQL 优化得很好。但相关的、嵌套太深的子查询可能慢。第 22 章讲怎么分析和优化。先学会写，再学优化。

---

## 10.2 子查询的分类

按返回结果分：

| 类型 | 返回 | 用法 |
|------|------|------|
| 标量子查询 | 单个值（一行一列） | 用在比较运算右侧 |
| 列子查询 | 一列多行 | 配合 IN / ANY / ALL |
| 行子查询 | 一行多列 | 配合行比较 |
| 表子查询 | 多行多列 | 用在 FROM 后（派生表） |

按是否依赖外层分：

- **非相关子查询**：内层独立执行，只执行一次
- **相关子查询**：内层引用外层列，每行都执行一次

## 10.3 WHERE 中的子查询

### 标量子查询

```sql
-- 找出失败次数超过平均值的 IP
SELECT ip, COUNT(*) AS fail_count
FROM login_logs
WHERE result = 'FAILED'
GROUP BY ip
HAVING fail_count > (
    SELECT AVG(cnt) FROM (
        SELECT COUNT(*) AS cnt FROM login_logs
        WHERE result = 'FAILED' GROUP BY ip
    ) AS avg_table
);
```

这个例子嵌套了两层，稍微复杂。看个简单的：

```sql
-- 找出扫描目标等于最高优先级任务目标的主机
SELECT host, port FROM scan_results
WHERE host = (
    SELECT target FROM scan_tasks ORDER BY priority DESC LIMIT 1
);
```

标量子查询必须只返回一行一列，否则报错。

### 配合 IN

```sql
-- 查出高危威胁 IP 的登录记录
SELECT * FROM login_logs
WHERE ip IN (
    SELECT indicator FROM threat_intel
    WHERE type = 'IP' AND severity >= 4
);
```

### 配合 NOT IN

```sql
-- 找出不在威胁情报库里的 IP（正常 IP）
SELECT DISTINCT ip FROM login_logs
WHERE ip NOT IN (
    SELECT indicator FROM threat_intel WHERE type = 'IP'
);
```

> **⚠️ NOT IN 的 NULL 陷阱**：如果子查询返回的结果里有 NULL，`NOT IN` 永远返回空！因为 `x NOT IN (a, NULL)` 的结果是 UNKNOWN。解决：子查询里加 `WHERE indicator IS NOT NULL`，或改用 NOT EXISTS。

## 10.4 FROM 中的子查询（派生表）

子查询的结果当一张临时表用：

```sql
-- 先算出每个 IP 的失败次数，再从结果里找出超过 50 次的
SELECT ip, fail_count
FROM (
    SELECT ip, COUNT(*) AS fail_count
    FROM login_logs
    WHERE result = 'FAILED'
    GROUP BY ip
) AS stats
WHERE fail_count > 50
ORDER BY fail_count DESC;
```

内层子查询起了别名 `stats`（必须起别名）。这种写法在读复杂的统计逻辑时很清晰——分两步：先算，再筛。

---

## 10.5 SELECT 中的子查询

```sql
SELECT
    ip,
    username,
    (SELECT COUNT(*) FROM threat_intel WHERE indicator = login_logs.ip) AS threat_hits
FROM login_logs
LIMIT 10;
```

每行都执行一次子查询，算这个 IP 在威胁库里命中几次。这是**相关子查询**（内层引用了外层的 `login_logs.ip`），每行执行一次，数据量大时可能慢。

## 10.6 EXISTS / NOT EXISTS

EXISTS 判断子查询**是否返回至少一行**，返回布尔值。

```sql
-- 找出有高危漏洞的任务
SELECT id, target FROM scan_tasks t
WHERE EXISTS (
    SELECT 1 FROM scan_results r
    WHERE r.task_id = t.id AND r.severity IN ('HIGH', 'CRITICAL')
);
```

解读：对每个任务，检查是否存在（EXISTS）属于它且高危的结果。存在就保留这个任务。

`SELECT 1` 是惯例——EXISTS 只关心有没有行，不关心具体值，写 1 最简单。

### NOT EXISTS

```sql
-- 找出没有任何扫描结果的任务
SELECT id, target FROM scan_tasks t
WHERE NOT EXISTS (
    SELECT 1 FROM scan_results r WHERE r.task_id = t.id
);
```

等价于前面学的 LEFT JOIN + IS NULL，但写法不同。

### EXISTS vs IN

```sql
-- IN 写法
SELECT * FROM scan_tasks
WHERE id IN (SELECT task_id FROM scan_results);

-- EXISTS 写法
SELECT * FROM scan_tasks t
WHERE EXISTS (SELECT 1 FROM scan_results r WHERE r.task_id = t.id);
```

| 对比 | IN | EXISTS |
|------|----|--------|
| 适用 | 子查询结果集小 | 外表小、子查询结果大 |
| NULL 问题 | NOT IN 有 NULL 陷阱 | NOT EXISTS 无此问题 |
| 执行 | 先执行子查询，再用结果过滤 | 对外表每行检查子查询 |
| 优化器 | 现代 MySQL 优化得都很好 | 现代 MySQL 优化得都很好 |

**建议**：NOT IN 尽量换成 NOT EXISTS，避免 NULL 陷阱。其他情况两者性能差不多，选你读着顺的。

## 10.7 ANY / ALL 比较

```sql
-- 找出失败次数大于任意一个 IP 的（大于最小值即可）
SELECT ip, fail_count FROM ...
WHERE fail_count > ANY (SELECT ...);

-- 找出失败次数大于所有 IP 的（大于最大值）
WHERE fail_count > ALL (SELECT ...);
```

| 运算 | 含义 |
|------|------|
| `> ANY (...)` | 大于子查询结果中的最小值 |
| `< ANY (...)` | 小于子查询结果中的最大值 |
| `> ALL (...)` | 大于子查询结果中的最大值 |
| `< ALL (...)` | 小于子查询结果中的最小值 |
| `= ANY (...)` | 等价于 IN |

ANY/ALL 用得不多，了解即可。

## 10.8 相关子查询详解

相关子查询是最难理解也最容易写错的部分。它是**逐行执行**的。

```sql
-- 查出每个任务，及其漏洞数量
SELECT
    t.id,
    t.target,
    (SELECT COUNT(*) FROM scan_results r WHERE r.task_id = t.id) AS vuln_count
FROM scan_tasks t;
```

执行过程：

1. 取任务的第 1 行，把 `t.id` 传给子查询，子查询数一下
2. 取第 2 行，再执行一次子查询
3. ... 每行都执行一次

这就是为什么相关子查询数据量大时慢——执行次数 = 外表行数。

**用 LEFT JOIN + GROUP BY 改写通常更快：**

```sql
SELECT t.id, t.target, COUNT(r.id) AS vuln_count
FROM scan_tasks t
LEFT JOIN scan_results r ON t.id = r.task_id
GROUP BY t.id, t.target;
```

一次性 JOIN 完再分组，只扫描一次。

> **经验**：能用 JOIN 写的，优先考虑 JOIN；子查询适合"判断存在性"（EXISTS）和逻辑分步骤（派生表）的场景。

---

## 10.9 子查询 vs JOIN 怎么选

| 场景 | 推荐 |
|------|------|
| 单纯过滤（IP 在威胁库里） | IN 或 EXISTS 均可 |
| 判断存在性 | EXISTS（语义清晰） |
| NOT 逻辑 | NOT EXISTS（避开 NULL 陷阱） |
| 需要显示另一张表的列 | JOIN |
| 分步骤统计（先算再筛） | 派生表（FROM 子查询） |
| 每行都要算一个值 | 相关子查询或 JOIN+GROUP BY |
| 大数据量 | 优先 JOIN，子查询容易慢 |

## 10.10 完整案例：安全分析综合查询

把第二卷所有知识串起来：

```sql
USE security_lab;

-- 找出疑似暴力破解的 IP：
-- 过去 7 天失败次数 > 50，且不在白名单里，且至少尝试过 3 个不同用户名
SELECT
    l.ip,
    COUNT(*) AS fail_count,
    COUNT(DISTINCT l.username) AS user_count,
    GROUP_CONCAT(DISTINCT l.username ORDER BY l.username) AS tried_users
FROM login_logs l
WHERE l.result = 'FAILED'
  AND l.login_time >= NOW() - INTERVAL 7 DAY
  AND l.ip NOT IN (SELECT ip FROM whitelist WHERE ip IS NOT NULL)
GROUP BY l.ip
HAVING fail_count > 50 AND user_count >= 3
ORDER BY fail_count DESC
LIMIT 20;
```

这条查询用到了：WHERE 时间过滤、NOT IN 子查询（还处理了 NULL）、GROUP BY、COUNT、DISTINCT、GROUP_CONCAT、HAVING、ORDER BY、LIMIT。这是第二卷的集大成之作——能独立写出这种查询，你的 SQL 水平就已经超过大多数人了。

## 10.11 本章总结

| 知识点 | 内容 |
|--------|------|
| 子查询 | 嵌套的 SELECT；分标量子查询、列子查询、行子查询、表子查询 |
| WHERE 中 | 标量比较、IN / NOT IN（注意 NULL 陷阱） |
| FROM 中 | 派生表，必须起别名；分步骤统计很清晰 |
| SELECT 中 | 标量子查询，每行执行 |
| EXISTS / NOT EXISTS | 判断存在性；NOT EXISTS 避开 NULL 陷阱 |
| ANY / ALL | 与子查询比较；了解即可 |
| 相关子查询 | 引用外层列，逐行执行；大数据量慢 |
| 选择策略 | 显示他表列用 JOIN；存在性用 EXISTS；先算后筛用派生表 |
