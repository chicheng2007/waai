# 第 15 章 触发器与事件

## 本章目标

读完这一章，你将能够：

- 理解触发器的概念——数据的"自动响应机制"
- 创建 BEFORE/AFTER 触发器
- 理解触发器里的 NEW 和 OLD
- 创建事件（定时任务）
- 知道触发器和事件的适用场景与坑

---

## 15.1 触发器：数据的自动响应

**触发器（Trigger）** 是绑定在表上的"自动动作"：当你对表执行 INSERT/UPDATE/DELETE 时，触发器自动执行。

典型场景：

- 插入日志时，自动更新"每日统计表"
- 删除任务时，自动删除关联结果（类似外键 CASCADE）
- 更新数据前，自动记录"变更前的值"到审计表

> **小白问**：触发器是不是和"编程里的事件监听"一样？
> 很像。你监听表的 INSERT/UPDATE/DELETE 事件，事件发生时自动跑一段 SQL。

---

## 15.2 创建触发器

语法：

```sql
CREATE TRIGGER 触发器名
BEFORE/AFTER  INSERT/UPDATE/DELETE
ON 表名
FOR EACH ROW
BEGIN
    -- 触发器逻辑
END;
```

关键要素：

| 要素 | 说明 |
|------|------|
| BEFORE / AFTER | 在操作前/后触发 |
| INSERT / UPDATE / DELETE | 触发的操作类型 |
| FOR EACH ROW | 每行触发一次（MySQL 只支持行级触发） |
| NEW | 代表新数据（INSERT/UPDATE 时） |
| OLD | 代表旧数据（UPDATE/DELETE 时） |

---

## 15.3 示例：插入日志时自动计数

场景：每次插入一条登录日志，自动更新统计表的计数。

先建统计表：

```sql
CREATE TABLE login_stats (
    stat_date DATE PRIMARY KEY,
    total_count INT DEFAULT 0,
    fail_count INT DEFAULT 0
);
```

建触发器：

```sql
DELIMITER $$

CREATE TRIGGER trg_after_login_insert
AFTER INSERT ON login_logs
FOR EACH ROW
BEGIN
    INSERT INTO login_stats (stat_date, total_count, fail_count)
    VALUES (DATE(NEW.login_time), 1, IF(NEW.result = 'FAILED', 1, 0))
    ON DUPLICATE KEY UPDATE
        total_count = total_count + 1,
        fail_count = fail_count + IF(NEW.result = 'FAILED', 1, 0);
END$$

DELIMITER ;
```

解读：

- `AFTER INSERT ON login_logs`：插入日志后触发
- `NEW.login_time`、`NEW.result`：新插入行的数据
- `ON DUPLICATE KEY UPDATE`：统计表当天已有记录就累加，否则插入新记录

之后每次插入日志，统计表自动更新，不用手动维护。

## 15.4 示例：审计触发器（安全场景）

场景：更新用户信息时，把"变更前后的值"记录到审计表——这是安全审计的基础。

```sql
CREATE TABLE user_audit (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id INT,
    old_username VARCHAR(64),
    new_username VARCHAR(64),
    changed_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    changed_by VARCHAR(64)
);

DELIMITER $$

CREATE TRIGGER trg_before_user_update
BEFORE UPDATE ON users
FOR EACH ROW
BEGIN
    IF OLD.username <> NEW.username THEN
        INSERT INTO user_audit (user_id, old_username, new_username, changed_by)
        VALUES (OLD.id, OLD.username, NEW.username, USER());
    END IF;
END$$

DELIMITER ;
```

解读：

- `BEFORE UPDATE`：更新前触发
- `OLD.username`：更新前的用户名
- `NEW.username`：更新后的用户名
- `USER()`：当前数据库用户（谁改的）
- `IF OLD.username <> NEW.username`：只有用户名真变了才记录

这样每次改用户名都有痕迹，可追溯。安全合规常要求这种审计。

---

## 15.5 NEW 和 OLD 的区别

| 操作 | NEW | OLD |
|------|-----|-----|
| INSERT | ✅ 可用（新插入的行） | ❌ 不存在 |
| UPDATE | ✅ 可用（更新后的值） | ✅ 可用（更新前的值） |
| DELETE | ❌ 不存在 | ✅ 可用（被删除的行） |

## 15.6 管理触发器

```sql
SHOW TRIGGERS;                      -- 查看所有触发器
SHOW CREATE TRIGGER 触发器名;        -- 查看定义
DROP TRIGGER 触发器名;               -- 删除
```

---

## 15.7 触发器的坑

**1. 隐式执行，容易忽略**

触发器自动执行，代码里看不到，排查问题时容易漏掉。"数据怎么变了？哦，触发器改的。"

**2. 性能影响**

每行都触发，批量插入 10000 行就触发 10000 次。大批量操作会很慢。

**3. 调试困难**

触发器里的错误可能导致主操作失败，报错信息不直观。

**4. 不能修改 NEW（部分情况）**

BEFORE 触发器可以修改 NEW 的值（自动填充、规范化），AFTER 不行。

```sql
-- BEFORE INSERT 里自动转小写
SET NEW.username = LOWER(NEW.username);
```

**5. 事务中的触发器**

触发器里的操作和主操作在同一事务中，主操作回滚，触发器里的修改也回滚。

> **现代实践**：和存储过程类似，很多公司把触发器的逻辑放应用层（更可控、易调试）。但触发器的"自动、无法绕过"特性在某些场景（审计、强制统计）很有价值。了解原理，按需使用。

## 15.8 事件（Event）：数据库里的定时任务

**事件**是 MySQL 定时自动执行的操作，类似 Linux 的 crontab。

### 开启事件调度器

```sql
-- 查看状态
SHOW VARIABLES LIKE 'event_scheduler';

-- 开启
SET GLOBAL event_scheduler = ON;
```

### 创建事件

场景：每天凌晨 2 点清理 30 天前的日志。

```sql
DELIMITER $$

CREATE EVENT evt_cleanup_logs
ON SCHEDULE EVERY 1 DAY
STARTS '2026-01-01 02:00:00'
DO
BEGIN
    DELETE FROM login_logs
    WHERE login_time < NOW() - INTERVAL 30 DAY;
END$$

DELIMITER ;
```

解读：

- `EVERY 1 DAY`：每天执行
- `STARTS '2026-01-01 02:00:00'`：从何时开始
- `DO BEGIN...END`：执行的 SQL

### 一次性事件

```sql
CREATE EVENT evt_one_time
ON SCHEDULE AT '2026-12-31 23:59:59'
DO INSERT INTO audit_log (msg) VALUES ('年末归档');
```

### 事件的周期写法

```sql
EVERY 1 SECOND          -- 每秒
EVERY 5 MINUTE          -- 每 5 分钟
EVERY 1 HOUR            -- 每小时
EVERY 1 DAY             -- 每天
EVERY 1 WEEK            -- 每周
EVERY 1 MONTH           -- 每月
```

### 管理事件

```sql
SHOW EVENTS;
SHOW CREATE EVENT evt_cleanup_logs;
ALTER EVENT evt_cleanup_logs DISABLE;   -- 暂停
ALTER EVENT evt_cleanup_logs ENABLE;    -- 恢复
DROP EVENT evt_cleanup_logs;            -- 删除
```

## 15.9 事件的安全应用

1. **定期清理**：过期日志、过期会话、过期 token
2. **定期统计**：每小时汇总一次数据到统计表
3. **定时检测**：定期检查异常（如连续失败的 IP）并写入告警表
4. **数据归档**：定期把冷数据移到归档表

示例：每小时检测暴力破解并告警：

```sql
DELIMITER $$

CREATE EVENT evt_detect_bruteforce
ON SCHEDULE EVERY 1 HOUR
DO
BEGIN
    INSERT INTO security_alerts (alert_type, ip, detail, created_at)
    SELECT 'BRUTE_FORCE', ip,
           CONCAT('失败次数: ', COUNT(*)),
           NOW()
    FROM login_logs
    WHERE result = 'FAILED' AND login_time >= NOW() - INTERVAL 1 HOUR
    GROUP BY ip
    HAVING COUNT(*) > 50;
END$$

DELIMITER ;
```

每小时跑一次，把过去一小时失败超过 50 次的 IP 写入告警表。这就是一个简单的自动化威胁检测。

## 15.10 本章总结

| 知识点 | 内容 |
|--------|------|
| 触发器 | INSERT/UPDATE/DELETE 时自动执行；FOR EACH ROW |
| BEFORE/AFTER | 操作前/后触发 |
| NEW/OLD | 新值/旧值；不同操作可用不同 |
| 触发器应用 | 自动计数、审计追溯、自动规范化 |
| 触发器的坑 | 隐式执行、性能影响、调试难、事务中同生共死 |
| 事件 | 定时任务；需开启 event_scheduler |
| 事件写法 | `ON SCHEDULE EVERY ... DO ...`；一次性用 AT |
| 事件应用 | 清理、统计、检测、归档 |
