# 第 13 章 索引原理与 B+ 树

## 本章目标

读完这一章，你将能够：

- 理解索引的本质——用空间换时间的"目录"
- 理解 B+ 树为什么适合做数据库索引
- 掌握 CREATE INDEX 的写法
- 知道聚簇索引和二级索引的区别
- 理解最左前缀原则
- 知道索引不是越多越好

---

## 13.1 从一个比喻开始

想象一本 1000 页的书，你要找"暴力破解"这个词。

**没有索引**：从第一页翻到最后一页，一页页找——这就是**全表扫描**。

**有索引**：翻到书末尾的索引页，"暴力破解 → 第 673 页"，直接翻过去——这就是**索引查询**。

数据库的索引就是这样的"目录"。它让查询不用扫描整张表，而是快速定位到目标数据。

---

## 13.2 索引的本质

索引是一种**数据结构**，它保存"列的值 → 数据所在位置"的映射。

```sql
CREATE INDEX idx_ip ON login_logs(ip);
```

这句话给 `login_logs` 表的 `ip` 列建了索引。之后查询：

```sql
SELECT * FROM login_logs WHERE ip = '45.33.22.11';
```

MySQL 不用扫描全表，而是通过索引快速找到所有 ip='45.33.22.11' 的行。

> **小白问**：索引是不是把所有数据复制了一份？
> 差不多是这个意思——索引占用额外的存储空间，保存排好序的列值和对应的行位置。所以索引是**用空间换时间**。

---

## 13.3 为什么是 B+ 树

 MySQL 的 InnoDB 引擎用 **B+ 树**作为索引结构。为什么不用哈希表、红黑树？

### 先排除哈希表

哈希表查找 O(1)，很快，但**不支持范围查询**：

```sql
WHERE ip > '192.168.1.0' AND ip < '192.168.1.255'
```

哈希表无法高效处理这种范围。数据库大量使用范围查询，所以不用哈希表做通用索引（但 Memory 引擎支持 HASH 索引）。

### B+ 树的特点

```
             [10 | 20 | 30]              ← 根节点（只存键，不存数据）
            /    |     |    \
   [1|5|9] [11|15|19] [21|25|29] [31|...]  ← 叶子节点（存键+数据指针）
      ↕        ↕          ↕         ↕
   双向链表连接所有叶子节点
```

B+ 树的关键特性：

1. **多路平衡**：一个节点能存多个键，树很"矮"（通常 3-4 层），查找快
2. **叶子节点存数据**：所有数据都在叶子节点，查询路径长度一致
3. **叶子节点双向链表**：范围查询时，找到起点后沿链表顺序扫描即可

为什么适合数据库：

- **单点查询快**：从根到叶子，3-4 次 IO（磁盘 IO 是瓶颈）
- **范围查询快**：叶子节点链表顺序扫
- **排序快**：叶子节点本身有序
- **磁盘友好**：一个节点通常对应一个磁盘页（16KB），一次 IO 读一整个节点

> **小白问**：3 层 B+ 树能存多少数据？
> 假设一个节点存 1000 个键，3 层能索引 1000³ = 10 亿条记录。而查找只需要 3 次磁盘 IO。这就是 B+ 树的威力。

## 13.4 聚簇索引 vs 二级索引

### 聚簇索引（Clustered Index）

InnoDB 中，**主键就是聚簇索引**。叶子节点直接存**整行数据**。

```
主键 B+ 树：
  叶子节点 [id=1] → 整行数据（ip, status, os...）
```

特点：

- 数据按主键顺序物理存储
- 主键查询极快（找到叶子节点就拿到整行）
- 一张表只有一个聚簇索引

### 二级索引（Secondary Index）

普通索引（CREATE INDEX 建的）的叶子节点存的是**主键值**，不是整行数据。

```
二级索引 B+ 树（ip）：
  叶子节点 [ip='45.33.22.11'] → 主键 id=5
```

用二级索引查询的流程：

1. 在 ip 索引树找到 ip 对应的主键 id
2. 再到主键索引树找到整行数据

第二步叫**回表**。

```sql
CREATE INDEX idx_ip ON login_logs(ip);

-- 这条查询需要回表
SELECT * FROM login_logs WHERE ip = '45.33.22.11';
```

### 覆盖索引（Covering Index）

如果查询的列都在索引里，就不需要回表——叫覆盖索引：

```sql
CREATE INDEX idx_ip_time ON login_logs(ip, login_time);

-- 只查 ip 和 login_time，都在索引里，无需回表
SELECT ip, login_time FROM login_logs WHERE ip = '45.33.22.11';
```

覆盖索引能显著提升性能。**生产优化常用手段**。

> **小白问**：为什么 `SELECT *` 不好？
> 现在你知道了——`SELECT *` 会强制回表（除非索引覆盖所有列）。只查需要的列，有机会用覆盖索引，避免回表。

## 13.5 创建和管理索引

```sql
-- 建表时创建
CREATE TABLE t (
    id INT PRIMARY KEY,
    ip VARCHAR(64),
    INDEX idx_ip (ip),
    UNIQUE KEY uk_ip_time (ip, login_time)
);

-- 建表后添加
CREATE INDEX idx_ip ON login_logs(ip);
-- 或
ALTER TABLE login_logs ADD INDEX idx_ip (ip);

-- 删除索引
DROP INDEX idx_ip ON login_logs;
-- 或
ALTER TABLE login_logs DROP INDEX idx_ip;

-- 查看索引
SHOW INDEX FROM login_logs;
```

### 索引类型

| 类型 | 说明 | 写法 |
|------|------|------|
| 普通索引 | 最基本 | `INDEX idx (col)` |
| 唯一索引 | 值唯一 | `UNIQUE KEY uk (col)` |
| 联合索引 | 多列组合 | `INDEX idx (col1, col2)` |
| 前缀索引 | 只索引前 N 个字符 | `INDEX idx (col(10))` |
| 全文索引 | 全文搜索 | `FULLTEXT KEY ft (col)` |

### 前缀索引

对长字符串列（如 URL、TEXT），只索引前 N 个字符，省空间：

```sql
CREATE INDEX idx_url_prefix ON logs(url(100));
```

但前缀索引的选择性要够（前 N 个字符要能区分大部分行），否则效果差。

---

## 13.6 最左前缀原则（重点）

联合索引 `(a, b, c)` 的 B+ 树是先按 a 排序，a 相同时按 b，b 相同时按 c。因此查询必须从最左边的列开始，才能用上索引。

```sql
CREATE INDEX idx_abc ON t(a, b, c);
```

| 查询条件 | 能否用索引 | 说明 |
|---------|-----------|------|
| `WHERE a=1` | ✅ | 用 a |
| `WHERE a=1 AND b=2` | ✅ | 用 a, b |
| `WHERE a=1 AND b=2 AND c=3` | ✅ | 用 a, b, c 全部 |
| `WHERE b=2` | ❌ | 没有 a，用不上 |
| `WHERE b=2 AND c=3` | ❌ | 没有 a |
| `WHERE a=1 AND c=3` | ⚠️ | 只用 a，c 用不上（b 断了） |
| `WHERE a>1 AND b=2` | ⚠️ | 只用 a（范围后不能用 b） |

**关键结论**：

1. 联合索引的列顺序很重要——把最常用的、选择性高的列放前面
2. 范围查询（>, <, BETWEEN, LIKE 'x%'）后面的列用不上索引
3. 跳过前面的列，后面的列用不上

> **小白问**：那我该把哪列放前面？
> 经验法则：**等值查询的列放前面，范围查询的列放后面**。比如 `WHERE ip='x' AND time > '2026-01-01'`，索引建 `(ip, time)` 比 `(time, ip)` 好。

## 13.7 索引失效的常见情况

即使建了索引，以下情况也会让索引失效（全表扫描）：

| 情况 | 示例 | 原因 |
|------|------|------|
| 对列做函数运算 | `WHERE YEAR(created_at)=2026` | 破坏了索引的有序性 |
| 隐式类型转换 | `WHERE ip = 123`（ip 是字符串） | 类型不匹配 |
| 前置 % 的 LIKE | `WHERE username LIKE '%admin'` | 前缀不确定 |
| OR 连接非索引列 | `WHERE ip='x' OR os='y'`（os 无索引） | 一列无索引则全表扫 |
| 使用 != / NOT IN | `WHERE status != 'UP'` | 优化器可能放弃索引 |
| 违反最左前缀 | 见 13.6 | — |

**改写示例**：

```sql
-- 不好：函数导致索引失效
SELECT * FROM logs WHERE YEAR(created_at) = 2026;

-- 好：用范围查询
SELECT * FROM logs
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';
```

第 22 章会用 EXPLAIN 详细分析索引是否生效。

## 13.8 索引不是越多越好

每加一个索引：

- 占额外磁盘空间
- INSERT/UPDATE/DELETE 时要维护索引（变慢）
- 优化器要选择索引，太多会增加决策成本

**原则**：

1. 给**查询频繁**的列建索引（WHERE、JOIN ON、ORDER BY 的列）
2. 给**选择性高**的列建索引（不同值多，如 IP、用户 ID；别给性别这种只有 2 个值的列建）
3. 联合索引优先于多个单列索引
4. 定期用 EXPLAIN 检查，删掉没用的索引

```sql
-- 查看索引使用情况（MySQL 8.0）
SELECT * FROM sys.schema_unused_indexes;
```

## 13.9 索引设计实战：安全日志表

场景：安全日志表 `login_logs`，常见查询：

1. 按 IP 查登录记录
2. 按时间范围查
3. 按 IP + 时间查（最频繁）

索引设计：

```sql
CREATE TABLE login_logs (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    ip VARCHAR(64) NOT NULL,
    username VARCHAR(64),
    login_time DATETIME NOT NULL,
    result ENUM('SUCCESS','FAILED') NOT NULL,
    INDEX idx_ip_time (ip, login_time),   -- 覆盖场景1和3
    INDEX idx_time (login_time)            -- 覆盖场景2
);
```

- `idx_ip_time` 联合索引：按 IP 查（最左前缀）、按 IP+时间查（完整使用）
- `idx_time`：按时间范围查（比如"过去 1 小时所有失败登录"）

这就是根据查询模式设计索引的思路——**先看查询，再建索引**。

## 13.10 本章总结

| 知识点 | 内容 |
|--------|------|
| 索引本质 | 用空间换时间的"目录"；列值→行位置的映射 |
| B+ 树 | 多路平衡、叶子存数据、叶子双向链表；适合范围查询和磁盘 IO |
| 聚簇索引 | 主键；叶子存整行；一表一个 |
| 二级索引 | 普通索引；叶子存主键；查询需回表 |
| 覆盖索引 | 查询列都在索引里，无需回表；`SELECT *` 破坏覆盖 |
| 创建 | `CREATE INDEX` / `ALTER TABLE ADD INDEX` / `SHOW INDEX` |
| 最左前缀 | 联合索引从最左列开始用；等值列在前，范围列在后 |
| 索引失效 | 函数运算、隐式转换、前置%、OR 非索引列、!=、违反最左前缀 |
| 索引取舍 | 查询频繁+选择性高的列；联合优先；不是越多越好 |
