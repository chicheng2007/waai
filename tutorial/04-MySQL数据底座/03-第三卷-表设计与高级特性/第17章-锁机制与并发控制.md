# 第 17 章 锁机制与并发控制

## 本章目标

读完这一章，你将能够：

- 理解锁的作用——保证并发安全
- 区分共享锁和排他锁

- 知道死锁怎么产生、怎么避免
- 理解乐观锁和悲观锁

---

## 17.1 为什么需要锁

多个事务同时操作同一数据时，需要锁来协调，防止数据错乱。

类比：公共厕所的门锁——一个人进去后锁上门，其他人得等他出来。数据库锁类似，但更复杂（有共享/排他、行级/表级之分）。

---

## 17.2 锁的基本类型

### 共享锁（Shared Lock，S 锁）

也叫**读锁**。多个事务可以同时持有共享锁读同一数据，但**不能写**。

```sql
SELECT * FROM hosts WHERE id = 1 LOCK IN SHARE MODE;  -- MySQL 8.0 也支持 FOR SHARE
```

多个事务都能加 S 锁读，互相不阻塞。

### 排他锁（Exclusive Lock，X 锁）

也叫**写锁**。一个事务持有 X 锁时，其他事务**既不能读也不能写**（在 InnoDB 里普通 SELECT 用 MVCC 可以不阻塞读，但写会阻塞）。

```sql
SELECT * FROM hosts WHERE id = 1 FOR UPDATE;  -- 加排他锁
```

UPDATE、DELETE、INSERT 语句会自动加 X 锁。

### 锁的兼容性

| 当前锁 \ 请求锁 | S 锁 | X 锁 |
|----------------|------|------|
| S 锁 | ✅ 兼容 | ❌ 冲突 |
| X 锁 | ❌ 冲突 | ❌ 冲突 |

简单记：**读读兼容，读写互斥，写写互斥**。

---

## 17.3 锁的粒度

### 表锁（Table Lock）

锁整张表。一个事务锁了表，其他事务不能改这张表的任何行。

- 开销小，加锁快
- 并发度低
- MyISAM 引擎用表锁

### 行锁（Row Lock）

只锁需要修改的行。其他事务可以改表里其他行。

- 开销大，加锁慢
- 并发度高
- InnoDB 引擎用行锁

```sql
-- InnoDB 中，这条 UPDATE 只锁 id=1 这一行
UPDATE hosts SET status='DOWN' WHERE id=1;
```

**关键：行锁必须走索引才能生效！**

```sql
-- id 是主键，走索引，行锁
UPDATE hosts SET status='DOWN' WHERE id=1;

-- ip 没索引，全表扫描，会锁住全表（退化成表锁）
UPDATE hosts SET status='DOWN' WHERE ip='192.168.1.10';
```

这就是为什么索引对并发很重要——没有索引的 UPDATE 会锁全表，严重阻塞其他事务。

> **小白问**：怎么知道我的 UPDATE 走没走索引？
> 用第 22 章讲的 EXPLAIN。看 `type` 和 `key` 列就能判断。

## 17.4 间隙锁与 next-key lock

InnoDB 在 REPEATABLE READ 隔离级别下，用**间隙锁（Gap Lock）** 防止幻读。

### 什么是间隙锁

间隙锁锁的是**索引记录之间的间隙**，而不是记录本身。

```sql
-- 假设 hosts 表 id 有 1, 3, 5
SELECT * FROM hosts WHERE id BETWEEN 1 AND 5 FOR UPDATE;
```

不仅锁住 id=1,3,5 这三行，还锁住 (1,3)、(3,5)、(5,+∞) 这些**间隙**——防止其他事务在这些间隙插入新行（防幻读）。

### next-key lock

next-key lock = 行锁 + 间隙锁。InnoDB 默认用 next-key lock 锁定，既锁记录又锁间隙，解决幻读。

> **注意**：间隙锁只在 REPEATABLE READ 级别下生效。READ COMMITTED 级别下没有间隙锁（所以有幻读问题）。

### 实战影响

间隙锁可能导致意外的锁等待：

```sql
-- 事务 A
SELECT * FROM hosts WHERE id > 10 FOR UPDATE;  -- 锁住 id>10 的所有间隙

-- 事务 B（会阻塞！）
INSERT INTO hosts (ip) VALUES ('1.1.1.1');  -- id 会分配 >10 的值，落在被锁的间隙里
```

这就是为什么有时"明明改的是不同行"却被阻塞——间隙锁在起作用。

## 17.5 死锁

### 什么是死锁

两个事务互相持有对方需要的锁，谁也不肯释放，形成循环等待。

```
事务 A: 锁住行1，想锁行2
事务 B: 锁住行2，想锁行1
→ 互相等待 → 死锁
```

示例：

```sql
-- 事务 A
UPDATE accounts SET balance=balance-100 WHERE id=1;  -- 锁住 id=1
UPDATE accounts SET balance=balance+100 WHERE id=2;  -- 想锁 id=2

-- 事务 B（同时执行）
UPDATE accounts SET balance=balance-50 WHERE id=2;   -- 锁住 id=2
UPDATE accounts SET balance=balance+50 WHERE id=1;   -- 想锁 id=1 → 死锁！
```

MySQL 检测到死锁后，会**回滚其中一个事务**（代价较小的），让另一个继续。报错：

```
ERROR 1213 (40001): Deadlock found when trying to get lock
```

### 查看死锁日志

```sql
SHOW ENGINE INNODB STATUS;
```

在输出里找 `LATEST DETECTED DEADLOCK` 部分，能看到死锁的详细信息。

### 避免死锁

1. **固定访问顺序**：所有事务按同样顺序访问表/行（比如都先锁 id 小的，再锁 id 大的）
2. **事务要短**：减少持锁时间
3. **一次锁够所有资源**：避免分多次加锁
4. **降低隔离级别**：用 READ COMMITTED 减少间隙锁
5. **加索引**：让 UPDATE 走索引，避免锁全表
6. **重试机制**：程序里捕获死锁错误，自动重试

## 17.6 悲观锁与乐观锁

这是应用层实现并发控制的两种思路。

### 悲观锁（Pessimistic Lock）

假设冲突一定会发生，提前加锁。数据库的 `FOR UPDATE`、行锁就是悲观锁。

```sql
-- 查出来并加排他锁，别人改不了
SELECT * FROM accounts WHERE id=1 FOR UPDATE;
-- 处理后更新
UPDATE accounts SET balance=... WHERE id=1;
COMMIT;
```

适合：**写多**、冲突频繁的场景。

### 乐观锁（Optimistic Lock）

假设冲突很少发生，不加锁，更新时检查版本号。

```sql
-- 表里加 version 列
SELECT id, balance, version FROM accounts WHERE id=1;
-- 假设读到 version=5，balance=1000

-- 更新时带 version 条件
UPDATE accounts
SET balance=900, version=version+1
WHERE id=1 AND version=5;
```

如果 `version` 已经被别人改了（不再是 5），UPDATE 影响 0 行，说明冲突了，重试。

适合：**读多写少**、冲突少的场景。性能比悲观锁好（不加锁）。

> **小白问**：乐观锁和 CAS 有什么关系？
> 乐观锁就是 CAS（Compare And Swap）思想在数据库的应用——"如果值还是我读到的那个，就更新；否则重试"。

## 17.7 FOR UPDATE 实战：抢任务

安全扫描平台里，多个 worker 抢任务：

```sql
START TRANSACTION;

-- 找出一个待处理任务并加锁，防止被其他 worker 抢到
SELECT id, target FROM scan_tasks
WHERE status = 'PENDING'
ORDER BY priority DESC
LIMIT 1
FOR UPDATE SKIP LOCKED;  -- MySQL 8.0：跳过已被锁的行

-- 更新为运行中
UPDATE scan_tasks SET status='RUNNING' WHERE id = 刚查到的id;

COMMIT;
```

`SKIP LOCKED`（MySQL 8.0）让多个 worker 并发抢任务时，跳过别人已锁定的行，各自拿不同任务——高效且不会冲突。这是任务队列的经典实现。

## 17.8 锁监控

```sql
-- 查看当前事务
SELECT * FROM information_schema.innodb_trx;

-- 查看锁等待
SELECT * FROM performance_schema.data_lock_waits;

-- MySQL 5.7 用这个
SELECT * FROM information_schema.innodb_lock_waits;

-- 查看 InnoDB 状态（含死锁信息）
SHOW ENGINE INNODB STATUS;
```

遇到"查询卡住"时，用这些命令排查是谁持锁、谁在等待。

| 知识点 | 内容 |
|--------|------|
| 锁的作用 | 保证并发安全 |
| 共享锁 S | 读锁；读读兼容、读写互斥；`LOCK IN SHARE MODE` |

| 悲观锁 | 提前加锁；`FOR UPDATE`；写多用 |
| 乐观锁 | 版本号/CAS；读多写少用 |
| 锁监控 | innodb_trx / data_lock_waits / SHOW ENGINE INNODB STATUS |
