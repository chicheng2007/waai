# 第 21 章 审计与日志

> **伦理声明**：本章用于合法授权的日志分析与安全运营。

## 本章目标

读完这一章，你将能够：

- 理解审计的重要性——"谁在什么时候做了什么"
- 配置和解读各类 MySQL 日志
- 用 binlog 做数据恢复和审计追踪
- 用日志分析发现异常行为
- 建立数据库审计方案

---

## 21.1 为什么需要审计

安全领域有句话：**"没有日志，就没有安全"**。

如果数据库被攻击了，你不知道：

- 谁登录了
- 执行了什么 SQL
- 数据被改了还是被偷了
- 攻击是什么时候开始的

没有日志，就无法发现入侵、无法追责、无法恢复、无法改进。审计是安全运营的"眼睛"。

合规要求（如等保 2.0、GDPR、PCI-DSS）也都明确要求数据库审计。

---

## 21.2 MySQL 的日志体系

| 日志 | 记录内容 | 主要用途 |
|------|---------|---------|
| 错误日志（error log） | 启动/运行错误 | 排障 |
| 通用查询日志（general log） | 所有 SQL 语句 | 全面审计（开销大） |
| 慢查询日志（slow log） | 慢 SQL | 性能优化、发现异常 |
| 二进制日志（binlog） | 所有数据变更 | 恢复、复制、审计 |
| 中继日志（relay log） | 主从复制用 | 复制 |
| 审计日志（audit log） | 细粒度审计 | 合规（插件） |

---

## 21.3 通用查询日志

记录**所有**连接和 SQL 语句——最全面的审计，但性能开销大。

```sql
-- 查看状态
SHOW VARIABLES LIKE 'general_log%';

-- 开启（临时）
SET GLOBAL general_log = ON;
SET GLOBAL general_log_file = '/var/log/mysql/general.log';

-- 输出目的地：FILE / TABLE
SET GLOBAL log_output = 'TABLE';  -- 存到 mysql.general_log 表
```

存到 TABLE 方便用 SQL 查询分析：

```sql
SELECT event_time, user_host, argument
FROM mysql.general_log
WHERE argument LIKE '%DELETE%'
ORDER BY event_time DESC;
```

> **注意**：通用日志记录所有 SQL（包括明文密码的修改语句），文件可能很大且含敏感信息。生产环境按需开启，注意日志文件的权限保护。

---

## 21.4 慢查询日志

记录执行时间超过阈值的 SQL：

```sql
SHOW VARIABLES LIKE 'slow_query%';
SHOW VARIABLES LIKE 'long_query_time';

-- 设置
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 2;  -- 超过 2 秒
```

慢查询日志的价值：

1. **性能优化**：找出慢 SQL 优化（第 22 章）
2. **安全发现**：异常的慢查询可能是攻击（如盲注的 SLEEP、全表扫描的注入）

分析慢日志用 `mysqldumpslow`：

```bash
mysqldumpslow -s t /var/log/mysql/slow.log   # 按时间排序
mysqldumpslow -s c /var/log/mysql/slow.log   # 按次数排序
```

## 21.5 二进制日志（binlog）

binlog 记录所有**数据变更**（INSERT/UPDATE/DELETE 及表结构变更），不记录 SELECT。

```sql
SHOW VARIABLES LIKE 'log_bin';
SHOW BINARY LOGS;
```

### binlog 的三大用途

**1. 数据恢复**

误删数据后，用 binlog 恢复到删除前的状态：

```bash
# 先做全量备份，再用 binlog 做增量恢复
mysqlbinlog mysql-bin.000123 --stop-datetime="2026-01-15 09:59:59" | mysql -u root -p
```

第 23 章详细讲备份恢复。

**2. 主从复制**

从库读取主库的 binlog 同步数据（第 24 章）。

**3. 审计追踪**

binlog 记录了谁在什么时候改了什么数据。用 `mysqlbinlog` 查看：

```bash
mysqlbinlog mysql-bin.000123 | grep -i "DELETE FROM users"
```

### binlog 格式

```sql
SHOW VARIABLES LIKE 'binlog_format';
```

| 格式 | 说明 |
|------|------|
| STATEMENT | 记录 SQL 语句（体积小，但可能有不确定性） |
| ROW | 记录每行数据的变化（安全准确，推荐） |
| MIXED | 混合 |

推荐 ROW 格式——准确记录每行变化，审计更可靠。

## 21.6 审计插件

MySQL 社区版没有官方审计插件，但可以用：

- **MariaDB Audit Plugin**（兼容 MySQL）
- **Percona Audit Log Plugin**
- **McAfee MySQL Audit Plugin**

安装后能记录：登录、查询、表变更、权限变更等，输出到文件或 syslog。

企业版 MySQL 有官方 Enterprise Audit 插件，功能更全。

## 21.7 用日志发现攻击

### 场景 1：发现暴力破解

分析通用日志或应用日志，统计失败登录：

```sql
-- 如果登录日志在数据库里
SELECT ip, COUNT(*) AS fail_count
FROM login_logs
WHERE result='FAILED' AND login_time >= NOW() - INTERVAL 1 HOUR
GROUP BY ip
HAVING fail_count > 50
ORDER BY fail_count DESC;
```

### 场景 2：发现 SQL 注入尝试

在通用日志里搜索注入特征：

```sql
SELECT event_time, user_host, argument
FROM mysql.general_log
WHERE argument LIKE '%OR 1=1%'
   OR argument LIKE '%UNION SELECT%'
   OR argument LIKE '%SLEEP(%'
   OR argument LIKE '%information_schema%'
ORDER BY event_time DESC;
```

### 场景 3：发现异常数据变更

用 binlog 监控敏感表的变更：

```bash
mysqlbinlog mysql-bin.000123 | grep -iE "DELETE|DROP|TRUNCATE" 
```

如果看到非预期时间的删表操作，可能是入侵。

### 场景 4：发现异常账号行为

```sql
-- 非工作时间的操作（比如凌晨 3 点）
SELECT event_time, user_host, argument
FROM mysql.general_log
WHERE HOUR(event_time) BETWEEN 0 AND 5
ORDER BY event_time DESC;
```

## 21.8 建立审计表（应用层审计）

除了 MySQL 自带日志，可以在应用层建审计表，记录业务级操作：

```sql
CREATE TABLE audit_trail (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    actor VARCHAR(64) NOT NULL COMMENT '操作者',
    action VARCHAR(64) NOT NULL COMMENT '操作类型',
    target VARCHAR(255) COMMENT '操作对象',
    detail JSON COMMENT '详情',
    ip VARCHAR(64) COMMENT '来源IP',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_actor_time (actor, created_at),
    INDEX idx_action (action)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='审计追踪表';
```

应用每次敏感操作都写一条审计记录。配合触发器（第 15 章）或应用代码，实现完整审计链。

> **安全设计**：审计表应该**只能追加，不能修改或删除**（append-only）。用权限控制：应用账号只有 INSERT 权限，没有 UPDATE/DELETE 权限。这样即使应用被攻破，攻击者也无法抹掉审计记录。

## 21.9 日志管理最佳实践

1. **集中存储**：日志发到独立的日志服务器（SIEM），防止攻击者删除本地日志
2. **权限保护**：日志文件只有管理员可读，避免敏感信息泄露
3. **定期轮转**：用 logrotate 防止日志撑爆磁盘
4. **保留期限**：按合规要求保留（如等保要求 6 个月）
5. **监控告警**：对异常日志实时告警（如大量失败登录、删表操作）
6. **时间同步**：用 NTP 保证服务器时间一致，便于关联分析

## 21.10 本章总结

| 知识点 | 内容 |
|--------|------|
| 审计重要性 | 没有日志就没有安全；发现入侵、追责、恢复、合规 |
| 日志体系 | 错误/通用/慢查询/binlog/中继/审计日志 |
| 通用日志 | 记录所有 SQL；开销大；可存 TABLE 用 SQL 分析 |
| 慢查询日志 | 优化性能 + 发现异常慢查询（盲注） |
| binlog | 数据变更记录；恢复、复制、审计；推荐 ROW 格式 |
| 审计插件 | MariaDB/Percona/McAfee；企业版官方审计 |
| 攻击发现 | 暴力破解、注入特征、异常变更、异常时间操作 |
| 审计表 | 应用层 append-only 审计；只给 INSERT 权限 |
| 日志管理 | 集中存储、权限保护、轮转、保留、告警、时间同步 |
