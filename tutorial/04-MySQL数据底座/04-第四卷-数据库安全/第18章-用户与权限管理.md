# 第 18 章 用户与权限管理

> **伦理声明**：本章及后续安全章节的所有技术，仅用于合法授权的学习、测试与研究。请在本地靶场或获得书面授权的环境练习，严禁用于未授权系统。

## 本章目标

读完这一章，你将能够：

- 理解 MySQL 的权限模型和最小权限原则
- 创建用户、设置密码、修改密码
- 用 GRANT / REVOKE 授予和回收权限
- 理解权限的层级（全局/库/表/列）
- 知道生产环境的账号最佳实践

---

## 18.1 为什么需要权限管理

你装好 MySQL 后一直用 root 账号——它拥有所有权限，能删库、改配置、看所有数据。这很危险：

- 应用如果用 root 连接，一旦应用有 SQL 注入漏洞，攻击者就拿到最高权限
- 多人共用一个账号，出事无法追溯是谁干的
- 误操作（比如忘写 WHERE 的 DELETE）后果灾难性

正确做法：**最小权限原则**——每个账号只拥有完成工作所需的最小权限。

---

## 18.2 MySQL 的权限模型

MySQL 的权限是分层级的：

| 层级 | 语法 | 示例 |
|------|------|------|
| 全局 | `*.*` | 所有库所有表 |
| 数据库级 | `库名.*` | 某个库的所有表 |
| 表级 | `库名.表名` | 某张表 |
| 列级 | `库名.表名(列)` | 某列 |
| 存储过程/函数 | `库名.过程名` | 某个过程 |

权限信息存在 `mysql` 系统库的几张表里：`user`、`db`、`tables_priv`、`columns_priv`。

> **注意**：不要直接改这些系统表！用 GRANT/REVOKE/CREATE USER 语句，MySQL 会自动维护权限表。

## 18.3 创建用户

```sql
CREATE USER 'app_user'@'localhost' IDENTIFIED BY 'StrongPass@123';
```

语法：

- `'用户名'@'主机'`：用户名和允许登录的主机
- `IDENTIFIED BY`：密码

**主机部分很重要**：

| 写法 | 含义 |
|------|------|
| `'user'@'localhost'` | 只能本机登录 |
| `'user'@'%'` | 任意主机登录（`%` 是通配符） |
| `'user'@'192.168.1.%'` | 只能从该网段登录 |

安全建议：**不要用 `'user'@'%'`**，尽量限制来源主机。

### 查看用户

```sql
SELECT user, host FROM mysql.user;
```

### 修改密码

```sql
ALTER USER 'app_user'@'localhost' IDENTIFIED BY 'NewStrongPass@456';
```

MySQL 8.0 推荐用 ALTER USER，老版本的 `SET PASSWORD` 已废弃。

### 删除用户

```sql
DROP USER 'app_user'@'localhost';
```

### 密码策略

MySQL 8.0 有密码强度校验插件。查看：

```sql
SHOW VARIABLES LIKE 'validate_password%';
```

可以配置最小长度、复杂度要求。生产环境务必开启强密码策略。

## 18.4 授予权限：GRANT

```sql
-- 给 app_user 授予 security_lab 库的所有权限
GRANT ALL PRIVILEGES ON security_lab.* TO 'app_user'@'localhost';

-- 只给查询权限（只读账号，最安全）
GRANT SELECT ON security_lab.* TO 'readonly'@'localhost';

-- 给特定表的增删改查权限
GRANT SELECT, INSERT, UPDATE, DELETE ON vulnscan.scan_results TO 'scanner'@'localhost';

-- 给特定列的权限
GRANT SELECT (ip, status) ON security_lab.hosts TO 'limited'@'localhost';
```

授权后一般不用 FLUSH PRIVILEGES（GRANT 会自动刷新），但如果直接改了权限表需要执行：

```sql
FLUSH PRIVILEGES;
```

### 常见权限

| 权限 | 说明 |
|------|------|
| SELECT | 读数据 |
| INSERT | 插入数据 |
| UPDATE | 更新数据 |
| DELETE | 删除数据 |
| CREATE | 建库建表 |
| DROP | 删库删表 |
| ALTER | 改表结构 |
| INDEX | 建索引 |
| EXECUTE | 执行存储过程 |
| ALL PRIVILEGES | 所有权限（除 GRANT OPTION） |
| GRANT OPTION | 能把权限授给别人（谨慎！） |

---

## 18.5 回收权限：REVOKE

```sql
-- 回收删除权限
REVOKE DELETE ON security_lab.* FROM 'app_user'@'localhost';

-- 回收所有权限
REVOKE ALL PRIVILEGES ON security_lab.* FROM 'app_user'@'localhost';
```

### 查看权限

```sql
SHOW GRANTS FOR 'app_user'@'localhost';
```

## 18.6 角色（Role，MySQL 8.0+）

角色是权限的集合，方便批量管理。就像"岗位"——先定义岗位的权限，再把人分配进去。

```sql
-- 创建角色
CREATE ROLE 'app_read', 'app_write';

-- 给角色授权
GRANT SELECT ON security_lab.* TO 'app_read';
GRANT SELECT, INSERT, UPDATE ON security_lab.* TO 'app_write';

-- 把角色赋给用户
GRANT 'app_read' TO 'analyst'@'localhost';

-- 激活角色（需要设置默认角色或手动激活）
SET DEFAULT ROLE 'app_read' TO 'analyst'@'localhost';
-- 或当前会话激活
SET ROLE 'app_read';

-- 查看角色权限
SHOW GRANTS FOR 'app_read';
```

角色让权限管理清晰很多——改角色权限，所有相关用户自动生效。

## 18.7 生产环境账号最佳实践

### 1. 按用途建不同账号

| 账号 | 权限 | 用途 |
|------|------|------|
| app_rw | 业务库的 CRUD | 应用程序读写 |
| app_ro | SELECT | 报表、分析 |
| backup | SELECT, LOCK TABLES | 备份 |
| dba_admin | ALL（仅本地） | 管理 |

### 2. 应用账号不用 root

```sql
-- 好的做法
CREATE USER 'secapp'@'localhost' IDENTIFIED BY '随机强密码';
GRANT SELECT, INSERT, UPDATE, DELETE ON vulnscan.* TO 'secapp'@'localhost';
```

### 3. 限制来源主机

```sql
-- 只允许应用服务器 IP
CREATE USER 'secapp'@'10.0.0.%' IDENTIFIED BY '...';
```

### 4. 定期审计账号

```sql
-- 查看所有用户及权限
SELECT user, host FROM mysql.user;
SHOW GRANTS FOR 'someuser'@'host';

-- 找出没有密码的账号（危险！）
SELECT user, host FROM mysql.user WHERE authentication_string = '';
```

### 5. 删除匿名账号和测试账号

MySQL 安装后可能有匿名账号：

```sql
SELECT user, host FROM mysql.user WHERE user = '';
-- 如果有，删掉
DROP USER ''@'localhost';
```

`mysql_secure_installation` 命令会自动做这些安全初始化。

## 18.8 权限与 SQL 注入的关系

为什么权限管理是安全防线的第一环？

假设应用用 root 账号连接数据库，且存在 SQL 注入漏洞：

```sql
-- 攻击者在输入框注入：
' OR 1=1; DROP TABLE users; --
```

如果应用账号有 DROP 权限，表就没了。如果应用账号只有 SELECT 权限，攻击者的破坏被限制在"读数据"范围内。

**最小权限原则 = 纵深防御**。即使应用层有漏洞，数据库权限也能限制损失。

> **思考**：为什么生产环境的应用账号不该有 FILE 权限？
> FILE 权限允许读写服务器文件。SQL 注入 + FILE 权限 = 攻击者能读 `/etc/passwd` 或写入 webshell。这是严重的安全隐患。

---

## 18.9 一个完整的账号配置示例

```sql
-- 1. 创建应用读写账号（限制来源）
CREATE USER 'secapp'@'10.0.0.%' IDENTIFIED BY 'App@Pass2026!Secure';

-- 2. 授予最小权限
GRANT SELECT, INSERT, UPDATE, DELETE ON vulnscan.* TO 'secapp'@'10.0.0.%';

-- 3. 创建只读分析账号
CREATE USER 'analyst'@'10.0.0.%' IDENTIFIED BY 'Analyst@Pass2026!';

-- 4. 只读权限
GRANT SELECT ON vulnscan.* TO 'analyst'@'10.0.0.%';

-- 5. 验证
SHOW GRANTS FOR 'secapp'@'10.0.0.%';
SHOW GRANTS FOR 'analyst'@'10.0.0.%';
```

## 18.10 本章总结

| 知识点 | 内容 |
|--------|------|
| 最小权限原则 | 只给账号完成工作所需的最小权限 |
| 权限层级 | 全局 `*.*` / 库 `库.*` / 表 / 列 / 过程 |
| 创建用户 | `CREATE USER 'u'@'host' IDENTIFIED BY 'pwd'` |
| 主机限制 | localhost / `%` / 网段；避免 `%` |
| 授权 | `GRANT 权限 ON 范围 TO 用户` |
| 回收 | `REVOKE 权限 ON 范围 FROM 用户` |
| 查看 | `SHOW GRANTS FOR 用户` |
| 角色 | MySQL 8.0+；权限集合，批量管理 |
| 最佳实践 | 按用途分账号、不用 root、限制主机、定期审计、删匿名账号 |
| 安全关联 | 最小权限限制 SQL 注入的损失 |
