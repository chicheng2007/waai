# 第 24 章 主从复制与高可用

## 本章目标

读完这一章，你将能够：

- 理解主从复制的原理
- 搭建一主一从复制
- 理解读写分离
- 了解常见的高可用方案
- 知道复制延迟的问题与处理

---

## 24.1 为什么需要主从复制

单台数据库的问题：

- **性能瓶颈**：所有读写都压在一台机器上
- **单点故障**：这台机器挂了，服务全停
- **数据安全**：只有一份数据，机器坏了数据没了

主从复制解决这些问题：

- 主库（Master）负责写
- 从库（Slave/Replica）复制主库数据，负责读
- 读写分离，分担压力
- 主库挂了可以切换到从库

```
        写入          复制          读取
应用 ──────────▶ 主库 ──────────▶ 从库 ◀──────── 应用
                (Master)          (Replica)
```

---

## 24.2 主从复制原理

复制基于 **binlog**（第 21、23 章讲过）：

```
1. 主库把所有数据变更写入 binlog
2. 从库的 I/O 线程连接主库，读取 binlog，写入自己的 relay log（中继日志）
3. 从库的 SQL 线程读取 relay log，重放 SQL，同步数据
```

三个线程：

- 主库：binlog dump 线程（发送 binlog 给从库）
- 从库：I/O 线程（拉取 binlog）
- 从库：SQL 线程（重放数据）

> **小白问**：为什么从库用两个线程（I/O + SQL）？
> 解耦。I/O 线程只管快速拉取 binlog 存到本地，SQL 线程慢慢重放。即使重放慢，也不影响拉取，主库不用等从库。

## 24.3 搭建一主一从

### 主库配置

```ini
# my.cnf
[mysqld]
server-id=1
log-bin=mysql-bin
binlog_format=ROW
```

重启主库，创建复制账号：

```sql
CREATE USER 'repl'@'从库IP' IDENTIFIED BY 'Repl@Pass123';
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'从库IP';
```

查看主库状态：

```sql
SHOW MASTER STATUS;
```

记下 `File`（如 mysql-bin.000001）和 `Position`（如 154）——从库要从这个位置开始复制。

### 从库配置

```ini
# my.cnf
[mysqld]
server-id=2          # 必须与主库不同
relay-log=relay-bin
read_only=ON         # 从库只读
```

重启从库，配置复制：

```sql
CHANGE MASTER TO
    MASTER_HOST='主库IP',
    MASTER_USER='repl',
    MASTER_PASSWORD='Repl@Pass123',
    MASTER_LOG_FILE='mysql-bin.000001',
    MASTER_LOG_POS=154;

START SLAVE;
```

查看复制状态：

```sql
SHOW SLAVE STATUS\G
```

关键指标：

- `Slave_IO_Running: Yes`
- `Slave_SQL_Running: Yes`

两个都是 Yes 说明复制正常。

> **MySQL 8.0.23+ 新语法**：用 `CHANGE REPLICATION SOURCE TO` 和 `START REPLICA`，`SHOW REPLICA STATUS`。老语法仍兼容。

## 24.4 复制延迟

主从复制是**异步**的，从库可能落后主库几秒到几分钟——这叫**复制延迟**。

查看延迟：

```sql
SHOW SLAVE STATUS\G
-- 看 Seconds_Behind_Master
```

### 延迟的原因

- 从库硬件差
- 从库执行慢查询
- 主库写入太快
- 大事务

### 延迟的影响

写完立即读可能读不到——用户改了资料，刷新页面还是旧的（因为读的是延迟的从库）。这叫"读写不一致"。

### 处理方案

1. **关键读走主库**：对一致性要求高的读（如刚改完就查），强制读主库
2. **半同步复制**：主库等待至少一个从库确认收到 binlog 才返回（减少数据丢失，但不消除延迟）
3. **并行复制**：从库多线程重放（MySQL 8.0 默认开启）
4. **监控延迟**：延迟过大告警

```sql
-- 开启并行复制（从库）
SET GLOBAL slave_parallel_workers = 4;
```

## 24.5 读写分离

架构：

```
写操作 → 主库
读操作 → 从库（可以多个）
```

实现方式：

1. **应用层**：程序里判断读写，选择连接主库或从库（如用 ProxySQL、MyCat）
2. **中间件**：ProxySQL、MaxScale 等代理自动分流
3. **框架支持**：某些 ORM 支持读写分离配置

Python 示例（简单版）：

```python
# 伪代码
def execute(sql):
    if sql.strip().upper().startswith('SELECT'):
        conn = slave_conn  # 读从库
    else:
        conn = master_conn  # 写主库
    return conn.execute(sql)
```

> **注意**：读写分离引入一致性问题。刚写完就读从库可能读不到。解决办法：写后短时间内读主库，或接受最终一致性。

## 24.6 高可用方案

主从复制是基础，高可用（HA）要保证**主库故障时自动切换**。

### 方案对比

| 方案 | 说明 | 特点 |
|------|------|------|
| MHA | Master High Availability | 成熟，自动故障切换 |
| Keepalived + 主从 | VIP 漂移 | 简单，常用 |
| Orchestrator | 复制拓扑管理 + 故障切换 | 功能强，有 Web 界面 |
| MySQL Group Replication | 官方组复制 | 多主/单主，强一致 |
| InnoDB Cluster | 官方完整方案（GR + MySQL Router + Shell） | 官方推荐 |
| MGR + ProxySQL | 组复制 + 代理 | 生产常用 |

### 故障切换流程

```
1. 监控发现主库宕机
2. 选举一个从库作为新主库
3. 提升从库为可写（STOP SLAVE; RESET MASTER; SET read_only=OFF）
4. 其他从库指向新主库
5. 应用连接切换到新主库（VIP 或 DNS）
```

###  Keepalived 简单方案

用 VIP（虚拟 IP）指向主库，主库挂了 VIP 漂移到从库：

```ini
# keepalived.conf 简化
vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_ipaddress {
        10.0.0.100    # VIP，应用连这个 IP
    }
    track_script {
        check_mysql
    }
}
```

主库挂了，Keepalived 自动把 VIP 漂移到从库，应用无感知（几乎）。

## 24.7 GTID 复制（MySQL 5.6+）

传统复制靠 binlog 文件名 + position 定位，主从切换时容易出错。**GTID（Global Transaction ID）** 给每个事务一个全局唯一 ID，简化复制和故障切换。

```ini
[mysqld]
gtid_mode=ON
enforce_gtid_consistency=ON
```

配置从库时不用指定文件名和 position：

```sql
CHANGE MASTER TO
    MASTER_HOST='主库IP',
    MASTER_USER='repl',
    MASTER_PASSWORD='...',
    MASTER_AUTO_POSITION=1;
```

GTID 让故障切换更简单可靠——从库自动知道该从哪个事务开始同步。

## 24.8 复制的监控

```sql
-- 查看复制状态
SHOW SLAVE STATUS\G

-- 查看主库 binlog
SHOW BINARY LOGS;

-- 查看从库延迟
SELECT Seconds_Behind_Master FROM ...;

-- 用性能表监控（MySQL 8.0）
SELECT * FROM performance_schema.replication_connection_status;
SELECT * FROM performance_schema.replication_applier_status;
```

**监控要点**：

- I/O 和 SQL 线程是否都在运行
- 延迟是否过大
- 是否有复制错误（Last_Error）
- 从库是否只读
