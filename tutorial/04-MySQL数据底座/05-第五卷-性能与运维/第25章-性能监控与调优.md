# 第 25 章 性能监控与调优

## 本章目标

读完这一章，你将能够：

- 知道监控哪些关键指标
- 用 SHOW 命令和性能视图查看数据库状态
- 理解关键参数的配置与调优
- 建立性能问题的排查思路

---

## 25.1 性能调优的思路

调优不是"改参数让它变快"这么简单。科学的调优流程：

```
1. 监控 → 发现瓶颈（哪里慢）
2. 分析 → 定位原因（为什么慢）
3. 优化 → 针对性改进（SQL/索引/配置/硬件）
4. 验证 → 确认效果（变快了吗）
5. 循环 → 持续监控
```

**没有监控就没有优化**。先测量，再优化，别凭感觉。

---

## 25.2 关键监控指标

| 类别 | 指标 | 说明 |
|------|------|------|
| 连接 | 连接数、活跃连接 | 连接数爆满是常见问题 |
| 查询 | QPS、慢查询数 | 查询负载 |
|  InnoDB | 缓冲池命中率 | 内存命中率，越低越慢 |
| 锁 | 锁等待、死锁数 | 并发问题 |
| 复制 | 延迟 | 主从同步状态 |
| 资源 | CPU、内存、磁盘 IO、网络 | 系统瓶颈 |

## 25.3 用 SHOW 查看状态

```sql
-- 查看服务器状态（几百个指标）
SHOW STATUS;

-- 查看全局变量（配置项）
SHOW VARIABLES;

-- 查看 InnoDB 状态
SHOW ENGINE INNODB STATUS\G

-- 查看当前连接/进程
SHOW PROCESSLIST;

-- 查看表状态
SHOW TABLE STATUS;
```

### 实用的状态查询

```sql
-- QPS 相关
SHOW GLOBAL STATUS LIKE 'Questions';     -- 总查询数
SHOW GLOBAL STATUS LIKE 'Uptime';        -- 运行秒数
-- QPS = Questions / Uptime

-- 连接数
SHOW GLOBAL STATUS LIKE 'Connections';   -- 总连接数
SHOW GLOBAL STATUS LIKE 'Threads_connected';  -- 当前连接数
SHOW GLOBAL STATUS LIKE 'Max_used_connections';  -- 历史最大连接数

-- 慢查询
SHOW GLOBAL STATUS LIKE 'Slow_queries';

-- InnoDB 缓冲池
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';
```

缓冲池命中率计算：

```
命中率 = 1 - (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)
```

命中率应该 > 99%。低了说明内存不够或缓冲池太小。

### SHOW PROCESSLIST

查看当前正在执行的查询——排查卡顿的利器：

```sql
SHOW PROCESSLIST;
```

能看到：谁在连接、在执行什么 SQL、执行多久了、状态是什么。

发现卡住的查询可以杀掉：

```sql
KILL 查询ID;
```

> **小白问**：数据库卡住了怎么办？
> 先看 `SHOW PROCESSLIST`，找到执行时间很长的查询（Time 列很大），看它在干什么。如果是慢 SQL，KILL 掉，然后去优化它（第 22 章）。如果是锁等待，看第 17 章排查锁。

## 25.4 Performance Schema 与 sys 库

MySQL 自带的性能监控数据库：

- **performance_schema**：底层性能数据（事件、锁、等待）
- **sys**：基于 performance_schema 的易读视图（MySQL 5.7+）

sys 库的常用视图：

```sql
-- 最耗时的 SQL
SELECT * FROM sys.statements_with_runtimes_in_95th_percentile;

-- 全表扫描的查询
SELECT * FROM sys.statements_with_full_table_scans;

-- 未使用的索引
SELECT * FROM sys.schema_unused_indexes;

-- 冗余索引
SELECT * FROM sys.schema_redundant_indexes;

-- 锁等待
SELECT * FROM sys.innodb_lock_waits;

-- 最费内存的表
SELECT * FROM sys.memory_global_by_current_bytes;
```

这些视图是 DBA 的"仪表盘"，直接告诉你哪里有问题。

## 25.5 关键配置参数调优

配置在 `my.cnf` / `my.ini` 的 `[mysqld]` 段。

### 内存相关

```ini
# InnoDB 缓冲池（最重要！）
innodb_buffer_pool_size = 4G    # 设为物理内存的 50%-75%

# 日志缓冲
innodb_log_buffer_size = 64M

# 排序缓冲
sort_buffer_size = 4M

# 连接缓冲（按需）
join_buffer_size = 4M
read_buffer_size = 2M
```

**innodb_buffer_pool_size 是最重要的参数**。InnoDB 把数据和索引缓存在这里，越大命中率越高。专用数据库服务器可以设到内存的 70-80%。

### 连接相关

```ini
max_connections = 500          # 最大连接数
thread_cache_size = 50         # 线程缓存
wait_timeout = 600             # 空闲连接超时（秒）
```

`max_connections` 太小会报 "Too many connections"，太大浪费内存。根据并发量设置。

### InnoDB 相关

```ini
innodb_flush_log_at_trx_commit = 1  # 1最安全，2性能高
sync_binlog = 1                     # 1最安全，0/100性能高
innodb_file_per_table = ON          # 每张表独立文件
innodb_io_capacity = 2000           # IO 能力（SSD 设大）
innodb_flush_neighbors = 0          # SSD 关闭邻接页刷新
```

** durability vs 性能的权衡**：

| 设置 | 安全性 | 性能 |
|------|--------|------|
| `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` | 最高（不丢数据） | 较低 |
| 都设为 2 | 较高（宕机可能丢 1 秒） | 较高 |
| 都设为 0 | 低 | 最高 |

金融/支付类必须双 1；一般业务可以考虑折中。

### 慢查询相关

```ini
slow_query_log = 1
long_query_time = 2
log_queries_not_using_indexes = ON
```

## 25.6 系统层面的监控

```bash
# CPU
top / htop

# 内存
free -h

# 磁盘 IO
iostat -x 1
iotop

# 磁盘空间
df -h

# 网络
netstat / ss
```

数据库慢不一定是数据库的问题——可能是磁盘 IO 满了、CPU 被其他进程占了、网络带宽不够。系统层面也要看。

## 25.7 性能问题排查流程

假设"数据库变慢了"，按这个流程排查：

```
1. 确认现象：慢在哪？（全部慢 / 某些查询慢 / 特定时段慢）
2. SHOW PROCESSLIST：有没有卡住的查询？
3. 慢查询日志：哪些 SQL 慢？
4. EXPLAIN：慢 SQL 的执行计划？（第 22 章）
5. 索引检查：该建的索引建了吗？索引失效了吗？（第 13、22 章）
6. 锁检查：有锁等待/死锁吗？（第 17 章）
7. 资源配置：缓冲池够大吗？连接数够吗？
8. 系统资源：CPU/内存/磁盘 IO/网络有没有瓶颈？
9. 复制延迟：有主从复制吗？延迟大吗？（第 24 章）
10. 优化 + 验证 + 持续监控
```

## 25.8 常见性能问题与解决

| 问题 | 现象 | 解决 |
|------|------|------|
| 全表扫描 | 查询慢，EXPLAIN type=ALL | 建索引 |
| 索引失效 | 有索引但没用 | 修正 SQL（第 22 章自查表） |
| 回表太多 | 查询慢，覆盖索引没利用 | 用覆盖索引 |
| 锁等待 | 查询卡住 | 优化事务、固定访问顺序、加索引 |
| 连接数满 | Too many connections | 调大 max_connections、检查连接泄露 |
| 缓冲池不足 | 命中率低，磁盘 IO 高 | 调大 buffer_pool_size |
| 深分页 | LIMIT 大偏移慢 | 延迟关联（第 22 章） |
| 大表 | 表太大查询慢 | 分区、分表、归档旧数据 |
| 复制延迟 | 从库数据旧 | 并行复制、关键读走主库 |

## 25.9 监控工具推荐

| 工具 | 说明 |
|------|------|
| Prometheus + Grafana | 开源监控方案，业界标准 |
| mysqld_exporter | Prometheus 的 MySQL 采集器 |
| Percona Monitoring (PMM) | Percona 出品的 MySQL 监控平台 |
| Zabbix | 老牌监控，支持 MySQL |
| mysqltuner | 一键检查配置，给建议 |
| pt-toolkit | Percona 工具集，含很多诊断工具 |

mysqltuner 快速检查：

```bash
perl mysqltuner.pl
```

它会分析你的配置给出优化建议——**建议仅供参考，别盲目照搬**。

## 本章练习

1. 用 `SHOW GLOBAL STATUS` 计算你数据库的 QPS 和缓冲池命中率。
2. 执行 `SHOW PROCESSLIST`，理解每一列的含义。
3. 查询 sys 库的 `statements_with_full_table_scans`，看有没有全表扫描的查询。
4. 查询 `sys.schema_unused_indexes`，看有没有从未使用的索引。
5. 用 mysqltuner 检查你的配置，理解它的建议（不要盲目应用）。
6. 制造一个慢查询，用本章的排查流程找到原因并优化。
7. 思考：innodb_buffer_pool_size 为什么是最重要的参数？
8. 思考：innodb_flush_log_at_trx_commit 和 sync_binlog 的"双 1"配置有什么权衡？
