# ch08 数据增强与合成

> **本章目标**：当数据太少、类别太不平衡时，学会用增强和合成的方法"凭空"造出更多高质量训练数据。本章融入 CTF-Dojo 论文的核心思路——**先构建可验证的环境，再从成功轨迹中收集数据**，教你在取证场景里造出"经得起验证"的数据。

## 8.1 为什么需要数据增强

前三章我们从 9500 条正常日志 + 500 条异常日志里造出了指令数据。但问题来了：

- **异常样本太少**：500 条异常里，登录爆破只有 50 条，模型根本学不充分；
- **场景单一**：所有日志都是我们那套模板生成的，真实世界的日志千变万化；
- **指令有限**：问法再多，也是我们自己想的那几种。

数据增强（Data Augmentation）就是解决这些问题的：**从已有数据出发，造出更多、更丰富的数据**。

三种主要思路：

1. **简单变换**：对现有数据做扰动、重组；
2. **模型合成**：用大模型生成新样本；
3. **环境生成**：搭建可验证的环境，从真实交互中采集轨迹（CTF-Dojo 式）。

第三种最强大，也最复杂。我们先从前两种说起。

---

## 8.2 简单增强：从已有数据变出新数据

### 技术一：参数扰动

对日志里的数值做小幅随机扰动，保持标签不变。

```python
import random

def augment_log(line):
    """对日志的大小字段做扰动，标签不变"""
    import re
    def perturb(m):
        size = int(m.group(1))
        # ±10% 扰动
        new_size = int(size * random.uniform(0.9, 1.1))
        return f"size={new_size}"
    return re.sub(r'size=(\d+)', perturb, line)

# 原始
line = "2026-10-15 02:03:11 DENY 203.0.113.5->10.0.2.10:23 size=60"
# 增强后
print(augment_log(line))
```

这样一条能变出好几条，缓解样本不足。

### 技术二：模板改写

同一事件，用不同的表达方式描述：

```python
templates = [
    "{ip} 在 {time} 访问了 {port} 端口",
    "来源 {ip} 于 {time} 发起对端口 {port} 的连接",
    "检测到 {ip} 对 {port} 端口的连接请求（{time}）",
]

def rewrite(ip, time, port):
    t = random.choice(templates)
    return t.format(ip=ip, time=time, port=port)
```

### 技术三：回译（Back Translation）

把中文文本翻译成英文再翻译回来，得到表达不同但语义相同的新样本。可以用本地模型或翻译 API 做。这招对"指令"的多样性特别有用。

### 技术四：过采样少数类

对样本极少的类别（如登录爆破），直接复制并做轻微扰动：

```python
# 找到少数类
minority = df[df["label_detail"] == "brute_force"]
# 复制 5 份并扰动
augmented = []
for _, row in minority.iterrows():
    for _ in range(5):
        new_line = augment_log(row["raw_line"])
        augmented.append({**row.to_dict(), "raw_line": new_line})
```

**提醒**：简单增强容易引入"重复模式"，模型可能学会识别扰动痕迹而不是真实特征。不要过度使用，增强后的数据要人工抽查。

## 8.3 模型合成：让大模型造数据

用大模型生成新样本，是近年很流行的做法。

### 用大模型生成日志

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:1234/v1", api_key="not-needed")

prompt = """请生成 10 条模拟的防火墙日志，要求：
1. 格式：时间 动作 来源IP->目标IP:端口 size=大小
2. 其中包含 3 条端口扫描、3 条登录爆破、4 条正常流量
3. IP 使用 10.x.x.x 和 203.0.113.x 保留地址段
4. 时间集中在 2026-10-15
每行一条，不要编号，不要解释。"""

resp = client.chat.completions.create(
    model="local-model",
    messages=[{"role": "user", "content": prompt}],
    temperature=0.8,
    max_tokens=1000
)
print(resp.choices[0].message.content)
```

**注意模型合成的风险**：

1. **格式可能不对**：模型生成的日志可能不符合你的精确格式，要写一个校验函数过滤；
2. **事实可能错**：模型可能生成不合逻辑的日志（比如大小是负数），要检查；
3. **分布可能偏**：模型倾向生成"看起来典型"的样本，反而丢失了真实数据的多样性。

所以模型合成的数据**必须验证**——这也是下一节的主题。

### 用大模型扩充回答

上一章我们用模板生成回答，比较死板。可以让大模型生成多种表达方式：

```python
prompt = f"""下面是同一结论的三种不同表述，风格不同：
1. 简洁版
2. 详细版
3. 面向管理层的非技术版

结论：这是端口扫描行为，来源 IP 203.0.113.5 在短时间访问大量端口。

三种表述："""
```

这样能极大丰富回答的多样性，让模型学会"见人说话"。

## 8.4 CTF-Dojo 式思路：可验证的环境生成

前面两种增强方法有个共同弱点：**生成的数据没有客观验证**。你怎么知道模型生成的日志是"对的"？怎么知道增强后的标签还准确？

CTF-Dojo 论文给出了一个更可靠的范式：**构建可执行环境 → 让 Agent 在里面解题 → 用客观信号（flag）验证成功 → 只收集成功的轨迹**。

把它的思路迁移到取证数据合成，是这样的：

```
1. 搭建可复现的取证环境（如用 Docker 起一个有漏洞的服务）
2. 让 Agent（或脚本）在环境里执行攻击/取证操作
3. 用客观信号验证（如是否拿到 flag、是否触发预期告警）
4. 只保留成功的轨迹，记录完整过程
5. 把这些轨迹转成训练数据
```

### 关键：客观验证信号

CTF-Dojo 用 flag 是否正确作为验证信号。取证场景里可以用：

- **告警是否触发**：如果我们的检测规则/模型正确识别了攻击，就算成功；
- **日志特征是否匹配**：合成的攻击日志是否包含预期特征（端口扫描应有"多端口、短时间、同来源"）；
- **复现结果是否一致**：同一环境下重复实验，结果是否稳定。

```python
def verify_scan_log(log_lines):
    """验证生成的端口扫描日志是否真的符合扫描特征"""
    # 提取同一来源访问的端口集合
    from collections import defaultdict
    ports_by_ip = defaultdict(set)
    for line in log_lines:
        # 解析出 IP 和端口
        ...
    # 检查：是否有某个 IP 访问了超过 10 个不同端口
    for ip, ports in ports_by_ip.items():
        if len(ports) >= 10:
            return True, ip
    return False, None

# 只有验证通过的数据才保留
if verify_scan_log(generated_logs)[0]:
    keep(generated_logs)
```

这样造出来的数据，**每一条都经过客观验证**，质量远高于"模型凭空生成"。

> **出处**：CTF-Dojo 的方法来自论文 *Training Language Model Agents to Find Vulnerabilities with CTF-Dojo*（arXiv:2508.18370v2）。该论文用 658 道容器化 CTF 题，从 1,006 条经验证的成功轨迹中筛出 486 条训练数据，让 Qwen3-32B 的平均 Pass@1 从 20.3% 提升到 31.9%。详见本仓库 [reference/CTF-Dojo 论文解读.md](../reference/CTF-Dojo-论文解读.md)。

### 迁移到取证的三个要点

1. **环境要可复现**：用 Docker 固定依赖和版本，保证每次生成的环境一样；
2. **验证要客观**：不要靠模型自己判断"对不对"，要靠规则、flag、告警这些硬信号；
3. **只要成功轨迹**：失败的过程不进训练集——这和 rejection sampling 的思路一致。

这就是 CTF-Dojo 论文给我们的最大启示：**数据的质量，来自验证的严格，而不是数量的堆砌**。486 条经验证的数据，效果胜过 9000 多条弱标注数据。

## 8.5 增强的"度"：别把数据造坏了

数据增强有个悖论：造太多，模型学到假模式；造太少，数据不够用。怎么把握？

| 增强方法 | 推荐强度 | 风险 |
|---|---|---|
| 参数扰动 | 每条造 2-5 条 | 低 |
| 模板改写 | 每条造 3-8 条 | 中（可能不自然） |
| 模型合成 | 控制在总量的 30% 内 | 高（需严格验证） |
| 环境生成 | 不限（有客观验证） | 低（但成本高） |

**黄金法则**：增强后的数据，一定要做和原始数据一样的清洗与质量检查（ch06）。增强不是"免检通道"。

## 8.6 动手任务

1. **参数扰动**：写一个 `augment.py`，对登录爆破类样本做 5 倍扰动扩充，让它的数量和正常类接近。
2. **模型合成**：用本地 Qwen 生成 50 条模拟日志，写一个校验函数过滤掉格式不对的。看通过率多少？
3. **验证信号**：为端口扫描日志写一个验证函数 `verify_scan_log`（8.4 节），确保生成的日志真的符合扫描特征。
4. **对比实验**：训练前（只有原始数据）和训练后（加了增强数据）的效果对比——这个要等 ch13 学了评估再做，现在先把数据准备好。
5. **记录出处**：在 DATA.md 里记录哪些数据是合成的、用了什么方法、怎么验证的。

## 8.7 小结

- 数据增强解决样本少、类别不平衡、场景单一的问题；
- 简单增强：参数扰动、模板改写、回译、过采样；
- 模型合成：让大模型造日志/回答，但必须校验格式和事实；
- **CTF-Dojo 式思路**：可复现环境 + 客观验证 + 只要成功轨迹，数据质量来自验证的严格；
- 增强要适度，增强数据同样要清洗和检查；
- 记住那个数字：486 条经验证数据 ≈ 9000 多条弱标注数据的效果。
