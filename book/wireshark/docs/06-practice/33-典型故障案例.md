# 第三十三章 典型故障案例分析

本章通过几个真实场景的模拟案例，展示如何用前面学到的知识和方法论排查网络故障。每个案例都包含现象、抓包分析、结论和解决思路。

## 33.1 案例一：网站打不开——DNS 解析失败

**现象**：用户反馈「QQ 能上，但网页打不开」。

**抓包分析**：

1. 在用户主机抓包，过滤 `dns || tcp`。
2. 看到客户端发送 DNS 查询 `www.example.com`，但没有收到响应。
3. 多次重发 DNS 查询（同样的 Transaction ID 变化），均无响应。
4. 没有后续的 TCP  SYN 包。

**结论**：DNS 服务器不可达或防火墙拦截了 UDP 53 端口。QQ 能上是因为 QQ 用 IP 直连或内置 DNS，不依赖系统 DNS。

**解决**：检查 DNS 服务器配置和防火墙规则，更换公共 DNS（如 114.114.114.114）测试。

## 33.2 案例二：连接被重置——服务器端口未开放

**现象**：客户端连接服务失败，提示「连接被拒绝」。

**抓包分析**：

1. 过滤 `tcp.flags.syn == 1 && tcp.flags.ack == 0`，看到客户端发送 SYN。
2. 紧接着收到服务器回复 `[RST, ACK]`。
3. 没有 SYN+ACK。

**结论**：服务器的 80 端口没有服务监听（或防火墙明确拒绝，返回 RST）。如果有防火墙静默丢弃，则表现为 SYN 无响应（超时），而非 RST。

**解决**：检查服务是否启动、端口是否正确、防火墙是否放行。

## 33.3 案例三：网页加载慢——大量重传

**现象**：访问网站很慢，尤其加载图片时。

**抓包分析**：

1. 过滤 `tcp`，Follow 相关的 TCP 流。
2. 专家信息中大量 `Retransmission` 和 `Duplicate ACK`。
3. I/O Graph 显示流量曲线呈锯齿状（传输—停顿—传输）。
4. 重传率约 8%。
5. RTT Graph 显示 RTT 从 30ms 波动到 200ms。

**结论**：网络链路存在严重丢包，导致 TCP 反复重传，有效吞吐量大幅下降。

**进一步定位**：检查是单向还是双向丢包（看客户端→服务器和服务器→客户端哪个方向重传多），检查网线、无线信号、中间设备端口错误计数。

## 33.4 案例四：大文件传输失败——PMTUD 问题

**现象**：小文件能传，大文件卡住不动。HTTPS 网站能打开首页，但下载附件失败。

**抓包分析**：

1. 抓包看到客户端发送大包（接近 1500 字节），设置了 DF 标志。
2. 这些大包没有被确认，反复重传。
3. 过滤 `icmp.type == 3 && icmp.code == 4`，看到「目的不可达，需要分片」的 ICMP 消息（可能被防火墙丢弃了，客户端没收到）。
4. 小包（如握手包）正常传输。

**结论**：路径上存在 MTU 小于 1500 的链路，PMTUD 失败（ICMP 被拦截），导致大包被丢弃且发送方不知道。

**解决**：

- 允许 ICMP Type 3 Code 4 通过防火墙。
- 或在主机/应用层面调小 MTU（如 1400）。
- 或启用 TCP MSS Clamping（在路由器上调整 MSS）。

## 33.5 案例五：间歇性断连——ARP 欺骗

**现象**：局域网用户频繁掉线，尤其访问网关时。

**抓包分析**：

1. 过滤 `arp`，观察 ARP 流量。
2. 看到大量 ARP 响应，声称网关 IP（192.168.1.1）对应不同的 MAC 地址。
3. 某个 MAC 地址频繁发送免费 ARP（Gratuitous ARP）。
4. 结合 TCP 分析，发现客户端与错误 MAC 建立连接后通信异常。

**结论**：局域网存在 ARP 欺骗攻击（可能是感染了病毒的主机），网关 MAC 被伪造，导致流量被劫持到错误主机。

**解决**：定位并隔离 attack 主机，启用交换机端口安全（Port Security）、DHCP Snooping、动态 ARP 检测（DAI）等防护措施。

## 33.6 案例六：HTTPS 握手失败——密码套件不匹配

**现象**：某客户端访问 HTTPS 站点失败，浏览器提示「无法建立安全连接」。

**抓包分析**：

1. 过滤 `tls`，看到 ClientHello。
2. 服务器回复 Alert 消息：`handshake failure`。
3. 检查 ClientHello 中的密码套件列表，发现都是较旧的套件；服务器只支持 TLS 1.3 的新套件。

**结论**：客户端和服务器没有共同的密码套件/TLS 版本，协商失败。

**解决**：升级客户端（浏览器/系统）到支持 TLS 1.2/1.3 的版本。

## 33.7 案例七：视频会议卡顿——抖动

**现象**：视频会议音画不同步、卡顿，但网页浏览正常。

**抓包分析**：

1. 识别视频流量（通常基于 UDP，端口在动态范围）。
2. I/O Graph 显示流量波动剧烈。
3. 如果是 RTP，用 `Telephony → RTP → Stream Analysis` 分析丢包、抖动。
4. 发现抖动（jitter）较大，部分包延迟到达。

**结论**：网络抖动导致实时应用质量下降。网页浏览对抖动不敏感（TCP 会重传），但实时音视频无法容忍。

**解决**：配置 QoS，为实时流量优先转发；检查是否有链路拥塞。

## 33.8 案例八：数据泄露疑似——异常外联

**现象**：安全团队发现某内网主机持续连接外部陌生 IP。

**抓包分析**：

1. Conversations 按字节数排序，发现该主机与某公网 IP 有大量双向流量。
2. 过滤该 IP，观察通信模式：定期小包（心跳）夹杂大包（数据传输）。
3. DNS 查询显示该 IP 对应的域名是新注册的可疑域名。
4. 导出对象或 Follow Stream 查看内容（如未加密则暴露数据）。

**结论**：疑似主机被入侵，存在 C2 通信和数据外泄。

**解决**：隔离主机，取证分析，溯源攻击路径。

## 33.9 小结

- DNS 失败：有查询无响应，导致后续连接不发生。
- 端口未开放：SYN 后收到 RST（明确拒绝）或无响应（静默丢弃）。
- 大量重传：链路丢包，吞吐量下降。
- PMTUD 失败：大包不通、小包通，ICMP 被拦截。
- ARP 欺骗：网关 MAC 被伪造，导致劫持。
- 握手失败：密码套件/版本不兼容。
- 视频卡顿：抖动影响实时应用。
- 异常外联：安全事件的抓包特征。
