# 第三十一章 性能分析

网络性能问题（慢、卡、丢包）是最常见的故障类型之一。本章系统介绍如何用 Wireshark 分析网络性能：时延、吞吐量、重传、窗口、零窗口，以及如何综合判断瓶颈位置。

## 31.1 性能问题的分类

网络性能问题大致分为：

| 类型 | 表现 | 常见原因 |
| --- | --- | --- |
| 高时延 | 响应慢、RTT 大 | 距离远、路由绕行、拥塞 |
| 抖动 | 时延波动大 | 拥塞、队列波动、无线干扰 |
| 丢包 | 重传、连接中断 | 链路质量差、拥塞、设备故障 |
| 低吞吐 | 传输慢 | 窗口小、丢包、链路带宽不足 |
| 连接失败 | 超时、RST | 防火墙、服务不可用 |

## 31.2 时延分析

### 31.2.1 RTT（往返时间）

RTT 是衡量网络延迟的核心指标。Wireshark 中：

```
tcp.analysis.ack_rtt              # ACK 包对应的 RTT
```

用第二十七章的 RTT Graph 观察趋势。

**RTT 参考值**：

- 局域网：< 1ms
- 同城：< 10ms
- 国内跨省：10~50ms
- 跨洲：100~300ms

### 31.2.2 应用层时延

除了网络 RTT，还要看应用层响应时间：

- DNS 查询耗时：从查询到响应的时间。
- HTTP 响应时间：从请求到第一个响应包的时间（TTFB，Time To First Byte）。
- 服务响应时间：用 `Statistics → Service Response Time`。

**关键区分**：慢是「网络慢」还是「服务器慢」？

- 网络慢：RTT 大。
- 服务器慢：RTT 正常，但服务器响应前的停顿长。

## 31.3 吞吐量分析

吞吐量 = 单位时间传输的数据量。

- 用 I/O Graph 看整体流量趋势。
- 用 TCP Stream Graphs → Throughput 看单个连接的速率。
- 理论上限估算：TCP 吞吐量 ≈ 窗口大小 / RTT。

例如窗口 64KB、RTT 50ms，理论上限约 64KB/0.05s = 1.28MB/s ≈ 10Mbps。如果要达到 1Gbps，需要窗口约 6MB——这就是窗口扩大因子（Window Scale）的重要性。

## 31.4 重传与丢包分析

重传是丢包的直接证据：

```
tcp.analysis.retransmission           # 重传率
tcp.analysis.fast_retransmission      # 快速重传
tcp.analysis.duplicate_ack            # 重复 ACK
```

**重传率** = 重传包数 / 总包数。一般：

- < 1%：正常。
- 1%~5%：链路质量一般。
- \> 5%：明显问题。

重传的原因：

- 物理链路问题（网线、光纤、无线干扰）。
- 网络拥塞（路由器队列溢出）。
- 设备故障（端口错误、缓冲区溢出）。
- 抓包丢包（假象，见第二十八章）。

## 31.5 窗口与流量控制

```
tcp.window_size < 1000                # 小窗口
tcp.analysis.zero_window              # 零窗口
tcp.analysis.window_update            # 窗口更新
```

**零窗口分析**：

- 接收方应用处理慢，缓冲区满。
- 发送方暂停，等待窗口更新。
- 持续零窗口 = 接收方瓶颈。

用 Window Size Graph 可视化窗口变化。

## 31.6 综合判断瓶颈位置

分析性能问题时的判断逻辑：

```
1. 有重传吗？
   ├─ 有 → 检查重传率、位置（单向还是双向）
   │        ├─ 单向重传 → 该方向链路问题
   │        └─ 双向重传 → 中间网络拥塞
   └─ 无 → 进入下一步

2. RTT 高吗？
   ├─ 高 → 网络延迟问题（距离/路由/拥塞）
   └─ 正常 → 进入下一步

3. 窗口小或零窗口吗？
   ├─ 是 → 接收方处理慢（应用/主机瓶颈）
   └─ 否 → 进入下一步

4. 服务器响应慢吗？
   ├─ 是 → 服务器/应用问题
   └─ 否 → 检查客户端或带宽限制
```

## 31.7 实战案例：下载速度不达标

**现象**：用户下载文件只有 2Mbps，正常应该 20Mbps。

**分析步骤**：

1. 抓包，过滤 `tcp.stream eq N` 选中下载流。
2. Throughput Graph 显示速率稳定在 2Mbps。
3. RTT Graph 显示 RTT 约 20ms（正常）。
4. 重传率 < 0.1%（正常）。
5. Window Size Graph 显示接收窗口长期只有 8KB。
6. 计算：8KB / 0.02s = 400KB/s ≈ 3.2Mbps，与实际吻合。

**结论**：接收窗口太小限制了吞吐量。原因可能是接收方未启用窗口扩大因子（Window Scale），或应用接收缓冲区设置过小。这不是网络问题，而是主机/应用配置问题。

## 31.8 小结

- 性能问题分时延、抖动、丢包、低吞吐、连接失败等类型。
- RTT 反映网络延迟，需区分网络慢和服务器慢。
- 吞吐量 ≈ 窗口 / RTT，窗口扩大因子对高速网络至关重要。
- 重传是丢包的证据，重传率 > 5% 需重点关注。
- 零窗口说明接收方处理慢，是接收端瓶颈。
- 综合判断：重传 → RTT → 窗口 → 服务器响应，逐步定位瓶颈。
